# 文档版本原子切换与后台治理入口

## 背景与目标

- 背景：现有后台创建新版本时直接设为 `effective`，并在入库尚未完全完成时废弃旧版本；页面未暴露独立的生效切换操作。
- 目标：新版本先以草稿完成入库，管理员再通过明确操作切换生效版本；旧版本只在切换成功时废弃。
- 成功标准：版本链始终可见、原始资料不覆盖、失败入库不影响旧有效版本。

## 范围

- 包含：版本创建默认草稿、后端版本切换接口、管理后台代理、版本弹窗操作与状态展示、回滚复用版本切换、流程文档。
- 不包含：新增数据表／迁移、定时生效、跨服务分布式事务、删除旧版本原始资料。

## 用户与行为

### AC-01：创建新版本不影响当前有效版本

- 前置条件：存在一份 `effective` 文档。
- 操作：管理员在版本治理弹窗提交新版本正文。
- 预期结果：新版本完成索引后为 `draft`，旧版本继续为 `effective`。
- 验证方式：后端服务测试与后台版本列表检查。

### AC-02：管理员可切换生效版本

- 前置条件：版本链中存在完成索引的 `draft` 或 `confirmed` 版本。
- 操作：管理员点击「设为生效」。
- 预期结果：目标版本变为 `effective`，同链其他版本变为 `deprecated`，并同步关键词与 Karpathy 生命周期索引。
- 验证方式：后端服务测试、接口契约测试与页面构建。

### AC-03：回滚使用同一切换规则

- 前置条件：版本链中存在已废弃历史版本。
- 操作：管理员点击「回滚到此版本」。
- 预期结果：被选版本成为唯一 `effective` 版本，其他链上版本废弃。
- 验证方式：后端服务测试。

### AC-04：后台可见且可操作

- 前置条件：管理员拥有 `admin:documents:write` 权限。
- 操作：打开「版本治理」弹窗。
- 预期结果：可查看版本状态，并对非当前有效版本执行「设为生效」或「回滚到此版本」。
- 验证方式：前端 TypeScript、生产构建与页面代码审阅。

## 边界与约束

- PostgreSQL 内的文档元数据与块生命周期必须在同一事务中切换；ES／Karpathy 属于事务后同步，失败需报错而不能伪称成功。
- 仅允许已存在、属于同一版本链、且有 Chunk 的版本生效。
- 不触及环境变量、数据库 schema、迁移、文件删除或 Git 历史。

## 待确认项与假设

- 假设：`draft`／`confirmed` 表示已完成索引但尚未作为当前规范生效。
- 假设：管理员的现有 `admin:documents:write` 权限可用于生效切换。
