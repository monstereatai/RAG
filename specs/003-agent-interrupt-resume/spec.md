# Agentic 问答真暂停恢复与通用循环断点恢复

## 背景与目标

- 背景：生产工作流已有独立的审批、修订和恢复状态机；但 Agentic 问答图的 `humanApprovalNode` 仅返回 `pending`，仍会流向 reflection，`resumeGraph` 也以普通输入重新 invoke，无法证明只执行暂停后的节点。通用 `AgentLoopService` 虽会记录 Redis 快照，但每次 `run` 都从新 `initialState`、新计数开始，不能在进程重启后安全续跑。
- 目标：让显式开启的 Agentic 问答审批真正暂停并通过 LangGraph 原生 `interrupt`／`Command` 恢复；让通用 Agent Loop 按持久化的执行位置、剩余步骤／工具预算和已确认状态恢复，且不将未知写操作重复执行。
- 成功标准：审批期间不得执行 reflection 或任何后续节点；批准或拒绝后从同一 thread 的检查点恢复；通用循环重启后能从最近成功检查点继续并保留剩余预算；无快照、快照损坏、身份不匹配和未知副作用均安全失败或要求人工处置。

## 范围

- 包含：Agentic 问答图的原生中断／恢复、审批请求与恢复 API 契约、运行状态查询、通用 Agent Loop 快照 schema 与恢复入口、Redis 快照完整性校验、写工具幂等／未知结果门禁、单元与集成回归测试、使用和架构文档、`ROADMAP.md` 真实进度记录。
- 不包含：数据库 schema／迁移、`.env`／密钥、生产部署、Chat 以外业务工作流的重构、自由 swarm 多 Agent、跨服务消息总线、删除既有接口或 Git 提交。

## 用户与行为

### AC-01：Agentic 审批真实暂停

- 前置条件：已认证用户发起 `enableInterrupt=true` 的 Agentic 问答，生成节点已产出可审阅答案。
- 操作：工作流到达人工审批节点。
- 预期结果：服务返回或流式发送可审阅的中断信息，LangGraph 为该 `threadId` 持久化中断检查点；reflection、retry 和最终回答事件均不发生。
- 验证方式：定向集成测试断言节点调用序列与检查点状态。

### AC-02：审批恢复不重跑已完成节点

- 前置条件：存在同一用户拥有的待审批 thread。
- 操作：用户提交批准或拒绝决定。
- 预期结果：使用 `Command({ resume })` 从中断节点恢复；批准仅执行后续 reflection／结束路径，拒绝直接安全结束；已完成的检索、生成和外部读工具不重新调用。
- 验证方式：定向集成测试以节点与工具调用次数断言，覆盖批准、拒绝、重复恢复和错误 threadId。

### AC-03：通用 Agent Loop 保留预算恢复

- 前置条件：循环已在某成功轮后写入 Redis 快照，服务进程已丢失内存状态。
- 操作：使用受控恢复入口继续同一 `threadId`／`runId`／actor。
- 预期结果：从下一轮开始执行，已消耗步骤数与工具调用数不重置，总超时／剩余预算按恢复策略计算；已完成动作不重复执行。
- 验证方式：单元测试模拟 Redis 快照和新服务实例，断言 `decide`／工具调用次数、步骤、工具预算和最终状态。

### AC-04：恢复安全门禁

- 前置条件：快照缺失、格式损坏、已过期、actor／runId 不匹配，或上轮写工具结果为 unknown。
- 操作：请求恢复。
- 预期结果：不盲目从头重跑；返回可区分的不可恢复／需人工核对错误，并保留审计事件。未知写结果必须先由既有幂等记录或结果查询确认。
- 验证方式：负向单元测试和恢复 API 测试。

### AC-05：兼容与可观测性

- 前置条件：现有未开启审批的问答、现有 Agent Loop 调用方和生产工作流仍在使用。
- 操作：运行既有正常路径和新增恢复路径。
- 预期结果：默认 Chat 行为不改变；已有 `resumeGraph` 调用方按兼容 DTO 获得相同响应结构；新增事件、状态与失败原因可由运营 API 查询；生产工作流不受影响。
- 验证方式：定向回归、类型检查、构建和手动 API smoke。

## 边界与约束

- 权限：恢复操作必须校验 thread／run 的 owner；不得接受客户端传入的历史状态、预算或工具结果。
- 幂等：`interrupt()` 所在节点恢复时会从节点开头重执行，因此中断前不得执行副作用；对写工具保持既有幂等与 unknown 阻断策略。
- 数据完整性：移除通用 Loop 的字符串截断快照；超出容量时应明确拒绝持久化／恢复，不能保存不可解析 JSON。
- 超时：进程重启后不能恢复原进程已消耗的 wall-clock 时间；恢复请求使用新的恢复时间窗，但保留步骤和工具调用预算，并在文档明确说明。
- 现有项目规范：不修改 `.env`、依赖版本、数据库 schema 或生产配置；只修改经批准 Plan 列出的文件。

## 待确认项与假设

- 假设：Chat 审批仅用于显式开启的人工复核，不改变默认问答直接完成的行为。
- 假设：恢复通用 Loop 时，`runId` 由服务端生成或校验；旧调用方未传 `runId` 时仅允许恢复纯读／无副作用循环，否则拒绝恢复并要求新建运行。
- 待确认：恢复接口是复用既有 Chat／Agent API，还是新增运营 API；Plan 阶段根据现有 Controller 和前端调用确定最小兼容方案。
- 待确认：恢复后的 wall-clock 超时语义采用“新恢复窗口”而不是累积跨进程时长；这是唯一可由现有快照可靠支撑的定义。
