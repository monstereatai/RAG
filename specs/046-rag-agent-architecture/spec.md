# 当前阶段 Spec：Evidence Policy 边界与基线审计

## 背景与目标

- 背景：用户指定的架构重构任务书以较早仓库状态为基线。当前代码已有 `EvidenceBundle` 和统一 Chat/文档组件，但 Agentic RAG 仍通过类型断言和可选方法探测调用 `KarpathyRagService` 的证据策略方法。
- 目标：先以真实代码建立模块/契约/质量基线，再把通用证据排序、充分性判断和证据优先摘要收敛到显式 Evidence Policy；保留既有服务入口和行为。
- 成功标准：本阶段记录准确的当前实现与验证基线；Agentic 的通用证据策略调用有强类型共享服务，不再静默退回到与主实现不同的排序/判断逻辑。

## 范围

- 包含：P0 真实调用链、候选模块、外部契约和验证基线文档；P1a Evidence Policy 最小拆分、旧 Facade 委托与定向测试。
- 不包含：回答生成/引用链整体迁移（列在路线图 P1b）；文档入库、Context、Agent Runtime、Chat 与运营 API 改造（列在 P2-P5）；删除文件、数据库 Schema/迁移、依赖升级、CI/CD、`.env`、UI 重设计和生产部署。

## 用户与行为

### AC-01：基线和审计可复核

- 前置条件：仓库存在旧任务书所列的基线和当前本地修改。
- 操作：查看 `docs/refactor/00-baseline.md`、`01-module-audit.md`、`02-target-architecture.md` 和契约记录。
- 预期结果：文档以当前 HEAD/源码为准，区分已完成能力、仍存耦合、未运行验证与外部阻塞；不把用户已有修改归入本任务。
- 验证方式：与当前 Git 状态、源码调用点、现有测试和本次命令结果逐项对照。

### AC-02：Agentic 使用共享证据策略

- 前置条件：Agentic 处理检索候选、评估充分性或创建证据优先摘要。
- 操作：运行 Agentic 检索/生成节点。
- 预期结果：排序、充分性和证据摘要由明确的 Evidence Policy 提供；Karpathy 旧方法保留兼容委托；不再使用可选方法探测和另一套排序回退。
- 验证方式：Evidence Policy 单测、Agentic/Karpathy 定向测试和 backend build。

### AC-03：外部行为保持兼容

- 前置条件：客户端继续调用现有 Simple/Auto/Agentic 接口。
- 操作：核对响应、引用、检索诊断和流事件。
- 预期结果：本阶段不改变 HTTP/SSE/AG-UI、DTO、ACL、RRF/rerank 分数含义、引用 ID、数据库 Schema 或索引行为。
- 验证方式：Diff 审阅、已有契约/定向测试；真实入口环境不可用时如实记录阻塞。

### AC-04：范围与验证基线可追溯

- 前置条件：实施本阶段。
- 操作：执行计划登记的单测、构建和 Diff 检查。
- 预期结果：只改计划文件；已有全量 Jest/lint 失败与本次新增失败区分记录。
- 验证方式：状态门禁、命令日志和 `verify.md`。

## 边界与约束

- 兼容性：`KarpathyRagService` 的公开旧方法继续存在；不改任何 API、SSE/AG-UI 事件、数据库结构、索引或权限语义。
- 安全与隐私：不读取/记录密钥；不碰 `.env`、`agent-course/`、用户运行时资料或现有未提交内容。
- Git：计划批准后创建任务书指定分支 `refactor/rag-agent-architecture`；不 stash/reset/clean，不提交或推送。
- 验证：只对改动文件做 lint 对照；已知全量基线失败不通过无关修改清零。
