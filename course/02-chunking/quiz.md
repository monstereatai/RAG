## 四、代码阅读题（2 分）

9. `splitTableBlock` 处理以下输入（`contentBudget` 足够容纳标签+表头+2 行，装不下第 3 行）：

```
内容类型：配置表
表格列：奖励 / 概率 / 地区
表格行：奖励=金币；概率=50%；地区=全部
表格行：奖励=皮肤；概率=10%；地区=东南亚
表格行：奖励=礼包；概率=40%；地区=台湾服
```

问：输出几个 chunk？第 2 个 chunk 的前两行是什么？为什么必须这样设计？

---

## 参考答案（先做完再看）

1. **错**。主要手段是**上下文重叠**：章节路径前缀每个 chunk 重复（§3.3）、表头每个表格 chunk 复用（§3.6）。字符 overlap 只是兜底——重读口播稿最后一句。
2. **错**。分隔行是语法噪音，`normalizeTables` 直接丢弃（§3.2）。
3. **错**。代码块是保护块，允许整块超预算输出——腰斩的代码比超长的代码危害大得多，这是显式 trade-off（§3.4）。
4. **B**。标题栈遇同级标题弹栈：`# C` 的 level=1，`headingPath.slice(0, 0)` 清掉 B，再压入 C（§3.3）。选 A 说明你把栈当成了只压不弹的列表。
5. **B**。`章节路径：员工手册 > 薪酬制度` 每个chunk都要拼，prefix 的长度必须从预算里扣除（§3.4）。
6. **B**。丢的不是表头字符，是**列名语境**——`50%` 单独出现没有意义，`概率=50%` 才有（坑点 1）。
7. 两个原因：① 表格语义化产生的 `表格列：/表格行：` 行是后续结构识别的输入——若先分节，表格行已散落在不同 section，归一化无从下手；② 序列化必须在字符预算计算**之前**完成，否则按原始 markdown 长度算的预算全部失真。
8. 检索侧：`项目=绩效奖金` 让"绩效奖金怎么算"这类 query 的 BM25 与向量匹配都直接命中（列名+值同现）；生成侧：LLM 拿到的是自包含的事实句，不需要推断"第三列是地区"——引用与回答都更可靠（§3.2）。
9. **2 个 chunk**。第 2 个 chunk 前两行是：
   ```
   内容类型：配置表
   表格列：奖励 / 概率 / 地区
   ```
   新 chunk 必须复用 `[内容类型标签, 表头行]`（`baseLines`）——不带表头的裸数据行就是坑点 1 的翻版。`current.length > baseLines.length` 保证第一行数据不会触发开组（§3.6、TODO ③）。
