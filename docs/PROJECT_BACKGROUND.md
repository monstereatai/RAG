# 游戏官网／活动产研一体化 AI Agent 工作台：项目背景

更新时间：2026-08-03

## 一、项目是什么

这是一个面向游戏官网、营销活动页、H5、小程序和版本专题页的产研一体化 RAG 与 Agent 工作台，主要服务产品、UI、前端、后端和测试团队。

它不是面向玩家的客服机器人，也不是只负责“上传文档后聊天”的通用知识库。系统以游戏活动从需求提出到上线复盘的完整链路为主线，把散落在 PRD、设计稿说明、接口文档、组件规范、埋点方案、测试用例、上线清单和历史复盘中的知识组织起来，并进一步把知识转成可评审、可实现、可验证的产研交付物。

一句话定位：

> 用 RAG 提供可信、可引用的项目知识，用 Agent 编排跨角色协作流程，让游戏官网和活动需求更快地从想法变成可上线方案。

## 二、业务背景

游戏业务中的官网和活动项目通常具有周期短、版本多、角色多、变化快的特点。一次新角色宣发、周年庆、抽奖、充值返利或版本更新，往往同时涉及：

- 产品定义活动目标、玩法规则、用户流程和异常边界。
- UI 设计页面结构、视觉表现、素材规格、多端适配和多语言布局。
- 前端实现交互状态、接口联调、埋点、性能优化、兼容与降级。
- 后端提供活动配置、资格校验、奖励发放、库存、防刷和补偿机制。
- 测试覆盖正常路径、边界条件、异常恢复、地区差异和上线验收。

实际工作中，问题往往不在“没有文档”，而在于文档分散、版本混杂、口径不一致、历史经验难复用：

- PRD 改过多轮，但开发和测试未必拿到同一版本。
- 设计规范、素材尺寸和多语言限制散落在设计稿、聊天记录和旧项目中。
- 接口字段、错误码、埋点和活动状态机分别由不同角色维护，缺少统一上下文。
- 同类活动重复建设，每次都重新整理页面模块、接口清单和测试项。
- 新成员不了解历史决策，只能反复询问资深成员。
- 大模型可以快速生成内容，但没有可靠证据时容易把规则、概率和接口细节编成确定答案。

因此，本项目要解决的不是单点问答问题，而是产研知识断裂和跨角色交付不一致的问题。

## 三、目标用户与核心价值

| 角色 | 典型问题 | 系统提供的价值 |
|---|---|---|
| 业务负责人 | 活动是否具备上线条件？各岗位依赖和风险是什么？ | 从目标、方案、设计、研发、测试、运营到复盘统一判断，输出跨岗位依赖、风险和决策清单。 |
| 产品 | 同类活动以前怎么做？规则是否缺边界？需求能否直接评审？ | 检索历史方案和业务模板，补齐流程、状态、异常、地区差异与风险项，生成 PRD 检查清单。 |
| UI | 页面需要哪些模块？素材尺寸和多端适配有什么约束？ | 汇总页面结构、组件规范、素材要求、多语言长度和 PC／H5／小程序适配规则。 |
| 前端 | 页面怎么拆？需要哪些接口、状态、埋点和兼容处理？ | 生成技术拆解、组件建议、状态机、接口依赖、埋点清单、性能预算和异常降级方案。 |
| 后端 | 资格、库存、发奖、防刷和补偿怎样设计？ | 检索历史接口与领域规则，补齐接口契约、幂等、状态流转、错误码、审计和补偿边界。 |
| 测试 | 哪些路径最容易漏？不同地区、设备和活动阶段怎么验？ | 基于 PRD、设计和接口证据生成测试矩阵、边界用例、异常用例、回归范围和上线检查清单。 |
| 活动运营 | 活动节奏、配置、素材、渠道和效果指标如何组织？ | 汇总运营排期、配置校验、渠道触达、异常监控和复盘指标。 |
| 项目经理 | 里程碑、负责人、依赖、风险和交付物如何推进？ | 生成项目计划、依赖关系、风险台账、变更项和站会清单。 |

各岗位不是分别使用孤立工具，而是围绕同一个活动项目、同一版本知识和同一条交付链路协作。

### 岗位预设与系统基础身份

系统的基础身份始终是“业务负责人”：理解产品、UI／UX、前端、后端、测试、运营和项目管理的全流程，能主动识别上下游影响和跨岗位依赖。

为了避免用户首次进入后不知道如何使用，用户端提供八个岗位预设：业务负责人、产品经理、UI／UX 设计师、前端开发工程师、后端开发工程师、测试工程师、游戏活动运营和项目经理。每个预设包含岗位职责、常用任务、可点击示例问题和回答结构。

岗位预设不是权限角色，也不是八套独立 Agent。它在统一业务负责人能力之上调整当前服务对象、输出重点和 `roleScope` 检索偏好；未标角色的公共文档仍可召回，回答仍需指出跨岗位依赖。用户选择结果保存在本地，下次进入可继续使用。

## 四、系统串联的业务流程

```text
活动目标与玩法
  -> PRD 完整性检查
  -> 页面结构与素材需求
  -> 前后端技术拆解
  -> 接口、状态机与埋点设计
  -> 测试用例与验收清单
  -> 上线检查与异常处置
  -> 数据反馈与项目复盘
  -> 知识、评测集和 Bad Case 回流
```

### 1. 需求阶段

系统帮助产品检索历史活动、玩法模板、地区规则和风险案例，识别目标、用户、活动周期、奖励、资格、库存、异常状态等缺失信息，并生成可继续评审的需求初稿。

### 2. 设计阶段

系统把玩法规则转成信息架构、页面模块和素材清单，为 UI 提供历史页面模式、品牌与组件规范、多端尺寸、多语言长度和无障碍要求，并保留来源引用。

### 3. 开发阶段

系统根据已确认的 PRD、设计说明和技术规范，辅助前后端生成页面拆分、接口清单、状态机、错误处理、埋点、性能预算和联调检查项。通过 MCP 或 API，可让 AI 编程工具在编码前主动获取项目上下文。

### 4. 测试与上线阶段

系统将规则、页面状态、接口契约和历史事故组合成测试矩阵，覆盖未登录、资格不足、重复领取、库存耗尽、接口超时、奖励延迟、跨时区、多语言和多端兼容等场景，并生成上线、灰度、回滚和客服 FAQ 检查项。

### 5. 复盘阶段

用户反馈、点踩记录、失败轨迹、测试遗漏和线上问题进入 Bad Case 池，经人工确认后转成知识修订、检索优化样本和回归评测题，使系统随项目推进持续改进。

## 五、知识库沉淀什么

项目不应把每次活动的临时数值当成永恒知识，而要同时管理“稳定方法”和“项目事实”。

### 稳定方法知识

- 活动类型：节假日、周年庆、版本更新、新角色、预约、回流、拉新和留存。
- 营销玩法：抽奖、签到、充值返利、礼包、兑换码、排行榜、分享裂变和邀请助力。
- 页面模式：PC 官网、H5、小程序、专题页、角色页、会场页、新闻、FAQ 和下载页。
- 工程规范：组件、接口、错误码、埋点、SEO、性能、CDN、兼容、安全和发布检查。
- 交付模板：PRD 检查表、素材清单、技术方案、接口清单、测试矩阵和复盘模板。

### 项目事实知识

- 当前活动的生效版本、地区、渠道、语言、时间范围和负责人。
- 已确认的玩法规则、资格条件、奖励配置、页面状态和接口契约。
- PRD、设计稿、接口文档、测试用例、变更记录和上线结论之间的关联。
- 已废弃版本、冲突事实、待确认事项和最终决策来源。

具体概率、奖励数值、预算、法务与地区口径必须来自当前生效文档或人工确认，系统证据不足时应拒答或明确标记“待确认”。

## 六、为什么同时需要 RAG 和 Agent

### RAG 负责“知道依据在哪里”

RAG 负责解析文档、结构化切片、权限过滤、混合召回、重排、上下文组装和引用校验。它解决的是查得准、找得全、引用能支撑答案的问题。

### Agent 负责“按什么步骤完成任务”

Agent 负责理解目标、选择工具、拆分步骤、维护状态、检查结果和决定继续、回退或请求人工确认。它解决的是复杂任务如何被稳定执行，而不是替代知识证据。

例如，“抽奖接口的错误码是什么”适合直接检索；“为东南亚服新角色抽奖 H5 生成完整技术方案”则需要 Agent 串联活动理解、页面结构、接口、埋点、地区适配、风险检查和测试验收。

## 七、核心方案与技术难点来源

结合本项目业务背景，技术难点不是为了堆叠名词，而是由以下真实矛盾推导出来：

| 业务矛盾 | 方案方向 | 要解决的核心问题 |
|---|---|---|
| 多角色长流程容易乱序、重试或死循环 | LangGraph 强约束状态机、Checkpoint、人工介入 | 控制执行顺序、预算、退出条件和中断恢复。 |
| 简单查表与复杂方案都走完整链路，延迟和成本过高 | simple／auto／agentic 分层路由 | 在准确性可控的前提下选择 Fast Path 或 Research Path。 |
| API、错误码、表格和语义描述的检索特征不同 | 结构保护切片、Dense + BM25／ES、RRF、Rerank | 同时保证专有词精确召回、语义召回和最终排序质量。 |
| 活动版本多、对话长，旧规则容易污染当前结论 | 短期会话记忆、长期知识、摘要压缩和版本过滤 | 控制 Token，并避免把历史版本当成当前事实。 |
| Prompt 或检索改动容易修好 A、破坏 B | 自动化 RAG／Agent Evals | 用召回、忠实度、引用、任务完成度和稳定性指标做回归。 |
| 点踩、测试遗漏和线上问题无法持续反哺系统 | Bad Case 捕获、归因、人工审核和数据回流 | 把失败样本转成知识修复或评测资产，而不是盲目注入 Prompt。 |
| Agent 是黑盒，答错后无法判断问题在哪一层 | Trace、Span、检索／工具／LLM 指标和轨迹回放 | 区分解析、召回、重排、上下文、模型和工具调用故障。 |

上述七类难点对应附带材料中的技术主线，但项目实现与简历表达必须以仓库中的真实代码、验证结果和 `ROADMAP.md` 为准。

## 八、产品形态

系统由相互独立但通过 API 协作的服务组成：

- `rag-backend`：负责知识入库、检索、问答、Agent 编排、图谱、记忆、评测和可观测能力。
- `admin-backend`：负责管理后台的用户、角色、权限、菜单、日志、通知、系统配置，以及对 RAG 运营接口的代理与聚合。
- `admin`：面向知识与系统运营人员，提供文档治理、检索分析、问答运营、GraphOps、评测、审计和配置界面。
- `frontend`：面向产品、UI、前端、后端和测试的日常知识问答与方案协同入口。
- `rag-cli` 与 `rag-mcp-server`：面向脚本、自动化流程和 AI 编程工具提供上下文与任务能力。

服务之间通过明确的 HTTP／SSE／MCP 契约协作，不共享业务代码，不要求管理后台与 RAG 核心服务绑定部署。

## 十、成功标准

项目价值不能只用“模型回答看起来不错”衡量，应至少覆盖四层指标：

| 层级 | 关键指标 |
|---|---|
| 检索质量 | Recall@K、MRR、NDCG、关键词命中、版本与权限过滤正确率。 |
| 回答质量 | Faithfulness、答案正确率、引用覆盖率、引用蕴含率、拒答准确率。 |
| Agent 质量 | 任务完成率、步骤合法率、工具成功率、死循环率、恢复成功率。 |
| 业务价值 | 需求澄清时间、技术方案准备时间、测试遗漏率、重复沟通次数、历史方案复用率。 |

当前仓库中的本地仿真评测用于证明工程链路和评测方法可运行；真实业务价值仍需使用真实项目问题、专家标准答案、实际活动交付数据和用户反馈持续验证。

## 十一、项目边界

- 系统辅助产研决策，不替代产品、设计、研发、测试和业务负责人最终签署。
- 系统不会把无来源的奖励概率、预算、法务口径或接口字段生成成确定事实。
- RAG 不替代项目管理、设计协作、代码仓库、接口管理和测试平台，而是连接这些系统中的知识上下文。
- Agent 优先用于需要多步骤、多工具和状态管理的任务；确定性流程仍应由普通工作流或代码执行。
- Bad Case 回流需要归因和人工审核，不能把用户点踩内容未经治理直接写入生产知识或 System Prompt。

## 十二、简历与面试表达边界

附带材料中的“完成率 95%+”“Recall@5 92%”“Router 准确率 98%”“Token 成本降低 90%”等数字，可作为评测目标或方案示例，不能在没有对应数据集、运行记录和对照实验时写成项目真实结果。

面试时建议按以下顺序讲清楚：

1. 背景：游戏官网和活动项目角色多、版本多、资料分散，交付口径容易不一致。
2. 目标：让五类角色围绕同一项目知识，把需求转成可评审、可实现、可测试的方案。
3. 对比：纯搜索不能完成复杂任务，纯大模型缺乏证据，纯 ReAct 长流程不稳定。
4. 选择：用 Hybrid RAG 保障证据，用 LangGraph 管理复杂流程，用评测和可观测建立质量闭环。
5. 结果：只陈述仓库已验证的工程指标；真实业务收益明确说明仍需真实项目数据验证。
