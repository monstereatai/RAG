# 项目背景与产品边界

## 项目定位

本项目为游戏官网、营销活动页、H5、小程序和版本专题页的产研团队提供知识问答与任务协作能力。RAG 负责返回有来源的项目知识；工作流与 Agent 负责把知识组织成可评审、可实现、可验证的交付物。

系统面向内部产研与运营团队，不是玩家客服，也不以通用聊天作为目标。现有实现包括 RAG Backend、管理后台、用户前台、RAG CLI 和 MCP Server；具体模块边界见[系统架构](architecture/ARCHITECTURE.md)。

## 要解决的问题

- 活动 PRD、页面规范、接口、埋点、测试和复盘分散在不同资料中，版本口径难保持一致。
- 同类活动重复建设，岗位间的交付依赖、异常边界和验收项容易遗漏。
- 单独使用大模型时，缺少来源的规则、数值和接口结论可能被说成事实。
- 多步骤任务需要可暂停、可审批、可恢复、可追溯的执行过程。

## 服务对象与输出

| 角色 | 常见输入 | 期望输出 |
| --- | --- | --- |
| 业务负责人／项目经理 | 活动目标、时间、范围 | 依赖、风险、里程碑和决策清单 |
| 产品 | 玩法与业务目标 | 需求缺口、流程、规则与异常边界 |
| UI／UX | 页面和视觉约束 | 页面模块、素材规格、多端与多语言检查项 |
| 前端／后端 | 已确认需求、接口和技术规范 | 页面状态、接口依赖、状态机、埋点和降级方案 |
| 测试 | 需求、设计和接口契约 | 测试矩阵、边界用例、回归范围和上线检查项 |
| 运营 | 活动节奏、配置和渠道 | 排期、配置校验、监控及复盘指标 |

岗位预设只改变服务对象、输出重点和检索偏好，不代表 IAM 权限角色，也不构成彼此独立的 Agent。

## 贯穿业务流程

```text
活动目标与玩法
  → 需求澄清与 PRD 检查
  → 页面结构与素材需求
  → 前后端方案、接口与埋点
  → 测试矩阵与上线验收
  → 运营反馈与项目复盘
  → 经审核的知识与评测样本回流
```

每一步应使用对应版本的资料并保留来源。奖励概率、预算、法务口径、活动规则和接口字段必须由当前有效资料或人工确认支撑；证据不足时明确待确认或拒答。

## 产品边界

- 系统帮助团队整理与执行工作，不替代业务、设计、研发、测试人员签署最终结论。
- RAG 提供证据，不保证未经真实业务集验证的答案质量或业务收益。
- Agent 用于需要多步骤、工具或持久状态的任务；确定性步骤优先由代码和工作流执行。
- 用户反馈与失败轨迹须经归因和审核，不能未经治理直接写入生产知识或提示词。
