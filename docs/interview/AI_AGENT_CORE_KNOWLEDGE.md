# AI Agent / RAG 核心知识人话版

> 用途：这不是题库，也不是术语表。目标是让你真的理解，面试时能用自己的话说出来。每个知识点都按“人话理解 -> 面试说法 -> 项目对应”来记。

## 先记住一条主线

AI 应用面试绕来绕去，其实都在问一件事：

```text
大模型本身不可靠，你怎么把它放进一个可靠的工程系统里？
```

这个可靠系统要解决 6 个问题：

1. **资料从哪来**：RAG、工具、记忆。
2. **资料准不准**：召回、重排、引用、评测。
3. **模型怎么行动**：Agent、状态机、工具调用。
4. **出错怎么收住**：拒答、降级、超时、预算。
5. **过程怎么看见**：日志、指标、trace、Debug。
6. **上线怎么维护**：配置、权限、部署、回归测试。

面试官问任何题，你都先想它属于哪一类。

## 0. 万变不离其宗的底层框架

> 面试题会变，项目形态会变，但 AI 应用工程的核心问题基本不变。你要记住的不是某个库怎么用，而是下面这些不变的判断框架。

### 0.1 AI 应用的本质

**一句话**

```text
AI 应用不是让模型自由发挥，而是把不稳定的模型能力，放进一个有数据、有工具、有边界、有反馈的工程系统里。
```

所有问题都可以拆成 7 层：

1. **输入层**：用户问什么？文档从哪来？数据干不干净？
2. **理解层**：query 怎么 normalize、改写、分类、路由？
3. **证据层**：向量、BM25/ES、图谱、工具、记忆能不能找到可靠资料？
4. **决策层**：走 simple RAG、Agentic RAG、GraphRAG、Web Search 还是拒答？
5. **生成层**：怎么组织上下文、控制 prompt、生成答案？
6. **校验层**：引用是否存在？claim 是否被支撑？低相关要不要拒答？
7. **运营层**：怎么观测、评测、回放、降级、修复失败样本？

面试官问“你怎么做 RAG / Agent / 工具调用 / 准确率 / 遇到问题”，本质都在问这 7 层中的一层或几层。

### 0.2 RAG 的不变核心

RAG 永远不是“向量库 + 大模型”，而是：

```text
数据处理 -> 检索证据 -> 排序筛选 -> 上下文组装 -> 答案生成 -> 证据校验 -> 失败回流
```

每一步都有核心问题：

- 数据处理：文档是否结构化？chunk 是否保留标题、条款、版本、生效期、来源？
- 检索证据：正确证据有没有被召回？中文、缩写、错别字、编号、金额怎么办？
- 排序筛选：噪声证据会不会挤进 prompt？rerank 有没有提升？
- 上下文组装：给模型的是不是刚好够用，而不是越多越好？
- 答案生成：有没有要求基于证据回答？有没有区分确定结论和不足说明？
- 证据校验：引用编号存在不等于引用能支撑答案。
- 失败回流：失败样本有没有进入评测集，而不是靠下次手工再试？

面试时可以这样收束：

```text
我关注的不是模型能不能生成一段话，而是正确证据有没有找到、是否排在前面、答案是否忠实于证据、证据不足时是否能收住。
```

### 0.3 向量、ES、图谱的分工

这三个不要讲成谁替代谁，它们解决的是不同问题。

| 能力 | 解决什么 | 不擅长什么 | 项目里的位置 |
|---|---|---|---|
| 向量检索 | 语义相似、表达不同但意思接近 | 编号、金额、版本、精确条件、否定 | Milvus 语义召回 |
| BM25/ES | 关键词、专有名词、制度条款、中文分词、字段检索 | 同义表达、隐含语义 | BM25/Elasticsearch 关键词召回 |
| 图谱 | 实体关系、多跳关系、上下游、依赖、归属 | 原文证据支撑、开放语义理解 | Neo4j GraphRAG 线索扩展 |

核心判断：

```text
向量负责“意思像不像”，ES 负责“词和条件准不准”，图谱负责“关系连不连得上”。最终答案仍然要回到文档证据。
```

### 0.4 Agent 的不变核心

Agent 不是“更聪明的 Chatbot”，而是：

```text
目标 -> 状态 -> 决策 -> 工具 -> 观察 -> 下一步 -> 终止
```

判断一个 Agent 是否工程化，看 8 件事：

- 目标是否明确，不是随便聊天。
- 状态是否显式保存，不靠模型记忆。
- 每一步 action 是否可解释。
- 工具参数是否有 schema 校验。
- observation 是否真的进入下一轮状态。
- 是否有停止条件，不会死循环。
- 是否有预算：次数、时间、token、费用、工具调用数。
- 是否可观测：trace、日志、事件流、失败原因。

面试时可以这样说：

```text
我不会把 Agent 做成自由推理黑盒，而是用 LangGraph/FSM 思路把节点、状态、分支、重试和终止条件显式建模。灵活性交给模型，可控性交给工程。
```

### 0.5 工具调用的不变核心

工具调用不是模型直接执行能力，而是：

```text
模型提出工具名和参数 -> 宿主系统校验 -> 宿主执行 -> 结果回填给模型/状态机
```

工具调用必须有 7 个边界：

- **schema**：参数结构必须可校验。
- **权限**：用户是否有资格调用。
- **超时**：外部工具不能拖死主链路。
- **重试**：可以重试，但不能无限重试。
- **幂等**：写操作不能重复造成副作用。
- **审计**：谁在什么时候调用了什么工具。
- **降级**：工具不可用时要有 fallback 或明确错误。

一句话：

```text
Tool 是能力，Agent 只是提出调用意图，真正执行和兜底必须由宿主工程负责。
```

### 0.6 GraphRAG 的不变核心

GraphRAG 不是普通 RAG 的升级版，而是补关系型问题的短板。

适合：

- 谁依赖谁？
- A 和 B 有什么关系？
- 某个能力由哪些系统支撑？
- 某个节点的上下游是什么？
- 多个实体之间能否连成路径？

不适合：

- 原文细节解释。
- 大段制度条款总结。
- 没有稳定实体和关系定义的自由问答。
- 真实图谱数据很脏或很空的场景。

一句话：

```text
GraphRAG 的价值来自高质量实体、关系、别名、置信度和业务 schema，不是来自“接了 Neo4j”。
```

### 0.7 评测的不变核心

不要只报“准确率”。AI 应用评测要先问：

```text
你评的是召回、排序、生成、拒答、引用，还是用户满意度？
```

RAG 常见评测拆法：

- **Retrieval**：Hit Rate、Recall@K、MRR。
- **Rerank**：NDCG、Top1/Top3 命中、排序提升。
- **Generation**：Answer Relevance、Faithfulness、Claim Support。
- **Citation**：引用编号是否存在、引用是否支撑结论。
- **Refusal**：无答案问题是否拒答，误答率是多少。
- **Operation**：无结果率、负反馈率、引用失败率、成本、延迟。

情感分析也同理，不要乱报 accuracy：

```text
如果没有定义标签、标注集、样本分布和评估方法，就不能说准确率。类别不均衡时 accuracy 容易虚高，更应该看 precision、recall、F1 和混淆矩阵。
```

### 0.8 AI Coding 的不变核心

AI Coding 不是让 AI 随便改代码，而是：

```text
规则 -> 计划 -> 小步修改 -> 验证 -> 文档同步 -> 失败复盘
```

核心原则：

- 先写规则：CLAUDE、ROADMAP、目录约定、红线。
- 让 AI 从真实代码和文档出发，不靠猜。
- 每次只改能追溯到需求的内容。
- 改完必须跑验证，不把“看起来能跑”当完成。
- 不静默 mock，不绕过错误，不擅自改 env/schema/部署。
- 失败超过两轮要换策略：查官方文档、看参考实现、对比 diff。
- 把失败样本和解决过程沉淀成文档或测试。

一句话：

```text
AI Coding 的价值不是替你思考，而是把明确目标下的搜索、改动、验证和文档同步提速；架构边界、风险判断和验收标准仍然要由工程负责人把控。
```

### 0.9 面试万能归因法

遇到任何追问，先归到这 8 个维度：

| 面试问题 | 归因维度 | 回答重点 |
|---|---|---|
| 项目怎么做 RAG | 证据链路 | 数据、检索、重排、生成、校验 |
| 向量/ES/图谱怎么用 | 检索分工 | 语义、关键词、关系各司其职 |
| 多 Agent 怎么协作 | 状态机 | 目标、状态、工具、观察、终止 |
| 工具怎么调用 | 宿主执行 | schema、权限、超时、审计、降级 |
| 遇到什么问题 | 风险治理 | 召回、幻觉、空态、流式、依赖 |
| 准确率多少 | 评测定义 | 先定义任务、标签、指标、数据集 |
| AI Coding 怎么用 | 工程流程 | 规则、小步、验证、文档、红线 |
| 上线怎么保证稳定 | 生产化 | 监控、降级、预算、回归、权限 |

最后记住这句话：

```text
所有 AI 工程问题，本质都在问：输入是否可靠，证据是否可靠，决策是否可控，输出是否可验，失败是否可收。
```

### 0.10 AI 应用开发必会方案地图

面试官问「切割策略有哪些」时，往往不是只想听 chunking。他是在看你有没有方案意识：同一个问题有哪些路线、各自优缺点是什么、你为什么选当前方案、怎么证明选对了。

万能回答框架：

```text
我会先看业务问题和评测指标，再列候选方案，按准确率、延迟、成本、可维护性、安全边界和可观测性做取舍。最后不会只说“用了某个库”，而是讲清楚当前项目为什么这么选、怎么降级、怎么评测。
```

| 必会知识点 | 常见方案 | 优点 | 缺点 | 面试怎么选择 |
|---|---|---|---|---|
| 文档解析 | 纯文本抽取、Pipeline OCR/版面解析、端到端文档模型、多模态大模型 | 从低成本到高精度都有路可选 | 越复杂越贵，越依赖模型和算力 | 普通 Markdown/DOCX 走结构化解析，复杂 PDF/扫描件再接 OCR/视觉模型，必须保留页码、source span、表格结构 |
| 文档切片 | 固定长度、递归字符、结构化切分、Parent-child、语义切分、多模态切分 | 可以在召回精度和上下文完整性之间取舍 | 只按 token 切容易切断语义 | 企业制度、合同、活动方案优先结构切分，长度只是兜底，metadata 比参数更重要 |
| Embedding 选型 | 通用 embedding、中文/领域 embedding、多语种 embedding、自训练 embedding | 通用模型上手快，领域模型更贴业务 | 维度、成本、延迟、语种和领域泛化要权衡 | 先用稳定中文 embedding 建 baseline，再用业务评测集看 Recall@K、MRR、成本和延迟，不凭榜单盲选 |
| 向量库 / 索引 | FAISS、Milvus、Qdrant、Chroma、pgvector、Pinecone | 原型、单机、分布式、托管各有适配 | 部署复杂度和过滤能力差异大 | 原型可用 Chroma/FAISS，生产大规模选 Milvus/Qdrant，需要 SQL 事务和轻量部署可选 pgvector |
| 关键词检索 | BM25、Elasticsearch、OpenSearch、数据库全文索引 | 专有名词、编号、代码、埋点名命中稳 | 不懂语义，同义表达弱 | 不要和向量二选一，企业 RAG 应该保留 BM25/ES 作为精确召回 |
| 混合检索 | 向量 + BM25、RRF 融合、加权融合、图检索融合 | 同时覆盖语义和精确词 | 分数不可比，融合和去重复杂 | 多路召回后用 RRF 更稳，因为它看排名，不强行比较不同检索器分数 |
| Query 处理 | normalize、改写、扩展、多查询、问题拆解、HyDE | 能解决短 query、口语化和跨文档问题 | 会增加延迟和 token，改写错会带偏 | 简单问题少改写，复杂问题再做 query augment / decomposition，并限制查询数量 |
| Rerank | Cross-encoder、LLM rerank、规则加权、来源权威加权 | 能显著提高证据排序 | 成本和延迟增加，外部服务可能失败 | topK 多召回，topN 小范围 rerank，失败时保留融合结果降级 |
| 上下文组装 | topK 直塞、按文档聚合、parent 扩展、MMR 去冗余、压缩摘要 | 决定模型最后看到什么 | 塞太多会污染上下文，塞太少会漏条件 | 按证据质量、来源、版本、权限组装，必要时补 parent，同源重复要压缩 |
| Lost in the Middle | 控制 chunk 数、重排顺序、前后放核心证据、map-reduce、摘要压缩 | 减少长上下文遗忘 | 压缩可能丢证据 | 不盲目依赖长上下文，先把高质量证据排前，再让答案引用到具体片段 |
| 幻觉控制 | 低相关拒答、引用必需、claim support、事实冲突检测、reflection | 让回答可验证 | 会牺牲覆盖率和流畅度 | 企业知识库宁可拒答，也不要无证据确定回答 |
| RAG 评测 | Hit Rate、Recall@K、MRR、NDCG、Faithfulness、Citation Accuracy、Claim Support | 能定位是召回、排序还是生成问题 | 需要标准题库和证据标注 | 至少拆成检索、排序、生成、拒答、权限、延迟成本六类指标 |
| 数据更新 | 全量重建、增量更新、content hash、版本号、tombstone、双写队列 | 保证知识新鲜和索引一致 | 分布式一致性和回滚复杂 | 用 hash 去重，版本 / 生效期入 metadata，删除要清 DB、向量、BM25/ES 和缓存 |
| 权限过滤 | 应用层过滤、检索前过滤、索引级隔离、ABAC/RBAC metadata | 防止越权召回 | 过滤晚了可能泄露候选证据 | 企业 RAG 要在召回阶段就带 userId / tenant / ACL，生成后再做二次校验 |
| 记忆系统 | 短期窗口、摘要记忆、向量长期记忆、图记忆、时间衰减 | 支持多轮和个性化 | 记忆污染、过期和隐私风险 | 会话上下文、用户记忆、业务知识分层存储，不能把历史消息全塞 prompt |
| Agent 架构 | Chain、Workflow、ReAct、Plan-and-Execute、LangGraph/FSM、多 Agent | 从稳定到灵活逐级增强 | 越自治越难控，越容易慢和不确定 | 固定业务流程用 Workflow，复杂检索决策用 Agentic，生产优先显式状态机 |
| Tool Calling / MCP | Function Calling、HTTP Tool、MCP Server、Code/Browser Tool | 扩展模型行动能力 | 权限、超时、注入、幂等风险 | 模型只提出调用意图，宿主负责 schema、权限、超时、审计和降级 |
| 多 Agent | 单 Agent、Supervisor、角色分工、辩论/评审、A2A | 专业分工清楚 | 状态同步、冲突仲裁和成本复杂 | 业务链路先用 Supervisor + 子 Agent 管线，A2A 属于后续平台化方向 |
| 模型选择 / 路由 | 单模型、多供应商、大小模型路由、fallback、成本路由 | 平衡效果、成本和稳定性 | 多模型一致性和配置治理复杂 | 默认稳定低成本模型，复杂任务可切强模型，必须有超时和 fallback |
| Prompt / 上下文工程 | Prompt 模板、few-shot、结构化输出、上下文压缩、工具召回 | 直接影响可控性 | Prompt 容易漂移，缺版本会难回归 | Prompt 要版本化、可回放、可评测，不能靠临场调词 |
| 微调 / RAG / Prompt | Prompt 调行为，RAG 补知识，SFT/LoRA 学风格和格式，RLHF/DPO 调偏好 | 各自解决不同问题 | 微调不能解决知识实时更新 | 企业知识问答优先 RAG，稳定格式或工具调用再考虑 SFT/LoRA |
| 推理性能 | Streaming、KV Cache、Batching、量化、vLLM、自建或 API | 能优化体验和成本 | 自建模型运维成本高 | 应用岗要懂原理和取舍，项目用 Provider API + SSE，生产自建再看吞吐和合规 |
| 可观测性 | 日志、trace、step event、Prometheus、反馈、回放 | 能定位问题和做回归 | 埋点设计成本高 | 每次回答要能看见检索、rerank、工具、生成、token、引用和失败原因 |
| 安全治理 | Prompt injection、工具权限、secret 脱敏、审计、人工确认 | 防止数据泄露和越权执行 | 会增加流程复杂度 | 检索内容当不可信数据，写操作和高风险工具必须 human-in-the-loop |
| 多模态 RAG | OCR、ASR、图片 caption、表格结构化、视频抽帧、视觉向量 | 能处理 PDF/PPT/图片/音视频 | 成本高，source span 更难维护 | 首版先把 OCR/ASR 转文本入库，复杂场景再补视觉向量和跨模态检索 |
| 成本 / 延迟 | 缓存、路由、topK 控制、rerank topN、并行、降级、预算 | 让系统可用可运营 | 过度压缩会伤效果 | 简单问题走 fast path，复杂问题才进 agentic；每层都要有预算和指标 |

## 1. RAG 到底是什么？

**人话理解**

RAG 就像开卷考试。大模型是考生，知识库是书。  
如果你把整本书乱塞给它，它还是会乱答。RAG 真正要做的是：先找到最相关的几页，排好顺序，再让模型根据这几页回答，并且标出来答案来自哪一页。

**面试怎么说**

```text
RAG 不是简单的“向量库 + 大模型”。它的核心是把外部知识变成模型可使用、可验证、可追溯的上下文。完整链路是文档解析、切片、索引、召回、重排、上下文组装、生成、引用校验和评测回归。
```

**项目里怎么对应**

- 文档上传后解析 Markdown/TXT/PDF/DOCX。
- 切成 chunk，并保存 heading path、source span、doc version、生效期等 metadata。
- 用 BM25 / Elasticsearch / Milvus 混合召回。
- 用 DashScope Rerank 重排。
- 生成答案后检查引用和 claim 支撑。

## 2. 为什么不能只用向量检索？

**人话理解**

向量检索像“意思差不多就找出来”。  
但企业知识库里很多问题不是意思差不多就行，比如金额、版本号、系统缩写、制度编号、日期。  
“2025 版报销 500” 和 “2026 版报销 650” 语义很像，但业务结果完全不同。

**面试怎么说**

```text
纯向量检索适合语义相似，但对编号、金额、版本、专有名词、否定条件不够稳。企业 RAG 一般要做 hybrid retrieval，用 BM25/ES 保证关键词和结构化事实，用向量检索补语义召回，再用 reranker 做精排。
```

**项目里怎么对应**

- BM25 负责关键词和中文分词。
- Elasticsearch 负责中文 IK 分词和字段检索。
- Milvus 负责语义向量召回。
- 三者融合后再重排。

## 3. 召回、排序、重排分别是什么？

**人话理解**

你去图书馆找资料：

- **召回**：先把可能相关的书都找出来。
- **排序**：把最可能有用的书放前面。
- **重排**：找了 20 本候选书后，再仔细看一遍目录，把最适合回答问题的 5 本放到最前。

**面试怎么说**

```text
召回追求 recall，宁愿多捞一些候选；排序和 rerank 追求 precision，把真正相关的证据排到前面。Reranker 的价值是减少初召噪声进入 prompt，提升引用质量和答案稳定性，但它有成本，所以要限制 topN 和开关。
```

**项目里怎么对应**

- 初召：BM25 / ES / Milvus。
- 重排：DashScope Rerank。
- 成本控制：`AGENTIC_MAX_RERANK_TOP_N`、`AGENTIC_RERANK_ENABLED`。

## 4. RAG 召回怎么评测？

**人话理解**

不要只看最后答案像不像。  
要先问：正确资料找到了吗？找到了排第几？模型有没有真的根据资料回答？

**面试怎么说**

```text
我会把 RAG 评测拆成三层。检索层看 Hit Rate、Recall@K、MRR，确认标准证据有没有进 topK；排序层看 NDCG、MRR，确认 rerank 后证据是否更靠前；生成层看 answer relevance、faithfulness、citation accuracy、claim support。企业场景还要单独评拒答题、冲突题、版本题和跨文档题。
```

**这些指标怎么理解**

- `Hit Rate`：有没有找到正确证据。
- `Recall@K`：前 K 条里有没有覆盖正确证据。
- `MRR`：第一条正确证据排第几，越靠前越好。
- `NDCG`：整体排序质量。
- `Faithfulness`：答案有没有忠实于资料。
- `Citation Accuracy`：引用编号是否真对应证据。
- `Claim Support`：每个关键结论有没有证据支撑。

**项目里怎么对应**

- `eval:rag:quality`：总质量门禁。
- `eval:rag`：业务回归集。
- `eval:rag:project`：真实后端上传、问答、评分、清理。
- `eval:rag:maturity`：本地工程成熟度评分。

## 5. 切片怎么做？

**人话理解**

切片就像把一本书拆成便签。  
拆太大，不容易精准找到答案；拆太小，句子没上下文，看不懂。  
所以不能只按字数切，要按标题、段落、表格、条款这些结构切。

更准确地说，切片不是一个单独算法，而是 RAG 数据治理的一部分。它决定了后面能不能召回、能不能引用、能不能做权限过滤、能不能处理版本冲突。

**面试怎么说**

```text
我不会只按固定 token 数粗切。切片要先看文档类型和业务问题：制度、合同、活动方案、技术规范要优先按标题、条款、表格、列表、代码块这些结构切，再用 token 长度兜底。小 chunk 用来精准召回，parent chunk 或同章节上下文用来补完整语义；每个 chunk 还要带 heading path、section id、clause id、table ref、source span、doc version、生效期、来源权威和权限信息。这样后面检索、引用、拒答、版本治理才能闭环。
```

**常见方案怎么选**

| 方案 | 人话理解 | 什么时候用 | 风险 |
|------|----------|------------|------|
| 固定长度切分 | 每隔一段字数切一刀 | 原型、普通纯文本 | 容易切断语义，是 baseline，不是企业 RAG 最终方案 |
| 递归字符切分 | 先按段落/句子/空格切，不够再硬切 | 通用文档兜底 | 只能理解文本边界，不理解业务结构 |
| 结构化切分 | 按标题、条款、表格、列表、代码块切 | 制度、合同、技术文档、活动方案 | 解析成本高，但最适合企业知识库 |
| Parent-child chunk | 小块检索，大块补上下文 | 长章节、跨段规则、复杂说明文 | 需要额外存 parent，并做好上下文扩展 |
| 语义切分 | 用 embedding 或模型判断话题边界 | 长文章、主题跳转明显的资料 | 成本高、稳定性受模型影响，不适合首版全量依赖 |
| 多模态专用切分 | 表格按行列、图片 OCR、音视频按时间轴 | PDF、PPT、扫描件、会议音频 | 需要按模态保存 source span、页码、时间戳 |

**为什么参数不是核心**

- `chunkSize` 太大：召回不够精准，prompt 成本高，引用定位粗。
- `chunkSize` 太小：规则被拆散，条件和例外丢失。
- `overlap` 太大：重复片段多，排序和 prompt 都变脏。
- `overlap` 太小：跨边界信息容易丢。

所以面试里不要只说「我们设了 500/50」。更好的说法是：参数只是兜底，真正关键是结构、metadata 和后续上下文扩展。

**项目当前策略**

项目里当前是：

1. 先做 Markdown 结构识别，标题生成 `headingPath`。
2. 表格转成「表格列 / 表格行」的键值语义，避免表格检索时只剩竖线。
3. 条款编号提取成 `clauseId`，比如「第一条」。
4. 用递归字符切分兜底，分隔优先级是段落、换行、中文句号、英文句号、空格。
5. 默认 `chunkSize=500`、`chunkOverlap=50`。
6. 落库保存 `parentChunkId`、`sectionId`、`tableRef`、`sourceStart/sourceEnd`、版本、生效期和来源权威。

**举例怎么讲**

```text
比如差旅制度里有“住宿上限 650 元”，但下一句写“仅限一线城市”。如果只按固定长度切，金额和适用条件可能分开，模型会答漏条件。所以我会先按章节和条款切，保留“财务制度 > 差旅报销”这种 heading path，再把表格行列转成键值文本。检索时小 chunk 命中金额，回答时可以补同章节上下文，最后引用还能回到 source span。
```

**怎么判断切得好不好**

- 检索指标：Hit Rate、Recall@K、MRR，确认标准证据有没有进 topK。
- 排序指标：NDCG、rerank 后 MRR，确认正确 chunk 是否排前。
- 生成指标：claim support、citation accuracy，确认答案能被 chunk 支撑。
- 运营指标：无结果率、引用失败率、负反馈、重复 chunk 比例、平均 prompt token。
- 专项样本：表格题、条款题、版本冲突题、权限题、跨章节题、无答案拒答题。

**项目里怎么对应**

- `document_chunks` 保存父子 chunk。
- `headingPath` 保存标题路径。
- `sourceStart/sourceEnd` 支持回到原文。
- `docVersion/effectiveAt/expiredAt` 支持制度版本。
- `sourceAuthority` 支持来源权威。
- 表格会被转成行列键值文本，条款编号会进入 chunk 内容和 metadata。

## 6. 怎么提高 RAG 召回准确率？

**人话理解**

别一上来就换模型。召回不准通常是全链路问题：文档脏、切片差、查询没改写、索引单一、排序差、没有评测集。

**面试怎么说**

```text
我会从六层优化：数据侧做清洗、去重、结构化切片和 metadata；查询侧做 query normalize、同义词、缩写、错别字、query expansion；检索侧做 BM25/ES + vector hybrid；排序侧做 reranker、来源权威、生效期、权限过滤；生成侧做低相关拒答和引用校验；评测侧把失败样本沉淀成回归集。
```

**项目里怎么对应**

- 中文错别字归一化。
- BM25 + ES + Milvus 混合检索。
- Rerank 重排。
- 来源权威和生效期 metadata。
- 项目级仿真实业务评测。

## 7. Agent 和 Chatbot 有什么区别？

**人话理解**

Chatbot 像客服聊天窗口，主要负责回答。  
Agent 像一个办事的人，它知道目标，会拆步骤，会查资料，会调用工具，会看结果，再决定下一步。

**面试怎么说**

```text
Chatbot 主要是对话入口，核心是生成回复。Agent 是围绕目标工作的执行系统，它有状态、有规划、有工具、有观察结果、有下一步决策和终止条件。企业里 Agent 的关键不是“更聪明”，而是可控：能调用什么工具、什么时候停止、失败怎么降级、过程怎么审计。
```

**项目里怎么对应**

- simple RAG 更像稳定问答。
- agentic RAG 有 routing、query augment、retrieval、web search、rerank、generate、reflection。
- auto 模式会控制什么时候进入 Agentic。

## 8. ReAct、Tool Calling、LangGraph 怎么区分？

**人话理解**

- `Tool Calling`：模型说“我要调用这个工具，参数是这些”。
- `ReAct`：模型边想边做，做完看结果，再想下一步。
- `LangGraph/FSM`：把整个流程画成状态机，每一步、分支、循环、停止条件都明确。

**面试怎么说**

```text
固定流程用 Chain；明确单步 API 调用用 Tool Calling；任务路径不确定、需要边推理边查工具时可以用 ReAct；如果要生产级上线，我更倾向用 LangGraph/FSM，把状态、分支、循环、重试、中断和恢复显式建模。ReAct 负责灵活性，FSM 负责可控性。
```

**项目里怎么对应**

- Agentic RAG 用 LangGraph 思路做状态编排。
- MCP/Bocha/Rerank/Speech 都是外部工具能力。
- 通过 `AGENTIC_*` 配置限制 Agent 预算。

## 9. Agent 死循环怎么办？

**人话理解**

Agent 死循环就像一个人一直重复“我再查一下”，但永远不交付。  
根因通常是：目标不清、工具结果看不懂、没有停止条件、状态没更新。

**面试怎么说**

```text
我会把 Agent 死循环当成状态机失控处理。硬边界包括 max steps、max tool calls、max retries、timeout、token/cost budget；软边界包括检测重复 action-observation、状态没有新增信息就终止、工具连续失败就 fallback。高风险任务进入 human-in-the-loop。死循环路径要记录 trace，并沉淀成回归用例。
```

**项目里怎么对应**

- 限制最大重试。
- 限制扩展 query 数。
- 限制检索 query 数。
- 限制 web search 结果数。
- auto 模式对超长 query 回退 simple。

## 10. Agent 怎么调用外部工具？

**人话理解**

不是模型自己真的去操作世界。  
模型只是提出“我要调用什么工具、参数是什么”，真正执行的是后端系统。后端要校验参数、权限、超时、审计。

**面试怎么说**

```text
Agent 调工具常见方式有 Function Calling、Tool Calling、ReAct、MCP、LangChain Tool、HTTP API Tool、Code Interpreter、Browser/File Tool。关键不是能不能调，而是宿主系统要做 schema 校验、权限控制、超时、重试、幂等、审计和降级。
```

**项目里怎么对应**

- Bocha Web Search：联网搜索工具。
- DashScope Rerank：重排工具。
- MCP：标准工具 server 接入。
- Tencent Speech：ASR/TTS 外部能力。

## 11. MCP 是什么？

**人话理解**

MCP 就像给 Agent 插外设的标准接口。  
以前每个工具都要单独适配，现在工具可以作为 MCP server 暴露，Agent 通过标准协议发现和调用。

**面试怎么说**

```text
MCP 解决的是 Agent 和外部工具的标准化连接问题。工具通过 MCP server 暴露，Agent 不需要知道工具内部实现，只需要知道 tool schema、transport 和调用方式。工程上还要处理鉴权、超时、错误降级和工具列表观测。
```

**项目里怎么对应**

- 支持配置 MCP server。
- 默认不开启，避免本地开发被 MCP 依赖阻塞。
- 有 MCP smoke 和配置校验。

## 12. Skill 是什么？和 Tool 有什么区别？

**人话理解**

Tool 是工具，比如搜索、读文件、调接口。  
Skill 是使用工具的方法论，比如“调试外部 API 时先查官方文档，再逐字段对比 headers/body”。

**面试怎么说**

```text
Tool 解决能不能做，Skill 解决会不会按正确流程做。Skill 不是工具本身，而是可复用工作流，规定什么时候用哪些工具、按什么顺序用、遵守什么边界、如何验证结果。
```

**项目里怎么对应**

- `skills/` 目录加载 `SKILL.md`。
- 支持 token 匹配和 Qwen Embedding 语义匹配。
- 无 key 时回退本地 token 匹配。

## 13. 记忆方案怎么选？

**人话理解**

不要把所有聊天记录都叫记忆。  
当前正在想的东西、当前会话上下文、跨会话长期偏好、历史事件，应该存在不同地方。

**面试怎么说**

```text
我会按记忆类型选介质。当前推理状态放 graph state 或 prompt；当前会话放 Redis Checkpointer 或 message history；跨会话稳定事实和偏好放 Mem0 或数据库；历史问答相似召回放向量库；审计记录放 PostgreSQL。不能把所有历史聊天无脑塞进 prompt，也不能把临时推测写成长久记忆。
```

**怎么记**

| 类型 | 人话 | 适合放哪 |
|---|---|---|
| 工作记忆 | 当前这次正在想什么 | prompt / graph state |
| 短期记忆 | 当前会话前几轮说了什么 | Redis / message history |
| 长期记忆 | 用户长期稳定偏好 | Mem0 / DB |
| 语义记忆 | 稳定事实 | DB / vector store |
| 情节记忆 | 发生过的事件 | event log / DB |

**项目里怎么对应**

- Redis Checkpointer 保存线程状态。
- ConversationEmbeddingService 保存历史 QA 向量。
- Mem0Provider 管长期记忆。
- 所有记忆都要按 userId 隔离。

## 14. Context Engineering 是什么？

**人话理解**

Context Engineering 就是“怎么给模型准备上下文”。  
不是越多越好，而是把当前任务最需要的信息放进去，把噪声挡在外面。

**面试怎么说**

```text
上下文工程不是简单拼 prompt，而是选择、压缩、排序和注入信息。跨会话压缩时要保留用户目标、关键事实、约束边界、已完成/未完成状态、用户偏好、来源和时间。压缩结果最好可追溯，避免把一次 hallucination 固化成长期记忆。
```

**项目里怎么对应**

- 检索 chunk 后组装上下文。
- 对话历史向量化后按相关性注入。
- Agentic 流程按节点传递状态。

## 15. 为什么要拒答？

**人话理解**

企业知识库里，胡说比不说更危险。  
如果没有资料支撑，正确动作不是编一个像真的答案，而是说知识库里没有依据。

**面试怎么说**

```text
拒答是企业 RAG 的安全边界。检索为空、相关性低、引用缺失、claim 没有证据支撑、事实冲突无法判断时，都不应该输出确定性答案。否则模型流畅表达会掩盖证据不足。
```

**项目里怎么对应**

- 低相关拒答。
- 无相关文档拒答。
- 引用编号校验。
- claim-level 支撑校验。
- 片段抽取式保守回退。

## 16. 生产化要考虑什么？

**人话理解**

Demo 只要跑通一次。  
生产系统要考虑：外部服务挂了怎么办、慢了怎么办、花钱太多怎么办、答错怎么定位、权限怎么隔离。

**面试怎么说**

```text
AI 应用生产化核心是可控、可观测、可恢复。要处理 LLM、Embedding、Rerank、Search、Vector DB 的失败；要有超时、重试、降级、熔断、缓存、token/cost 预算；还要有指标、trace、日志脱敏、权限隔离、审计和评测门禁。
```

**项目里怎么对应**

- Milvus 超时快速降级 BM25。
- Bocha/Rerank 无 key 不阻塞主链路。
- Redis 不可用回退内存。
- Prometheus 指标。
- traceparent。
- 多租户隔离。

## 17. Provider 抽象是什么？

**人话理解**

不要把某个模型、某个向量库写死在业务里。  
用统一接口包一层，以后可以换实现。但能换不代表随便换，换 embedding 可能要重建索引。

**面试怎么说**

```text
Provider 抽象是把 LLM、Embedding、VectorStore、Rerank、Speech、Search、Memory 这些能力封装成统一接口。它解决接入灵活性，但切换 provider 还要考虑 embedding 维度、索引、schema、历史数据兼容和评测回归。
```

**项目里怎么对应**

- LLMProvider。
- EmbeddingProvider。
- VectorStoreProvider。
- SpeechProvider。
- 可配置 Bocha、DashScope、Tencent、Milvus 等外部能力。

## 18. AI 前端到底难在哪？

**人话理解**

AI 前端不是聊天框。  
用户需要知道：系统在干什么、为什么这样答、引用在哪里、失败原因是什么、能不能中断或重试。

**面试怎么说**

```text
AI 前端的价值是把模型的不确定过程产品化。除了聊天输入框，还要处理 SSE 流式响应、中间状态展示、工具调用过程、引用展示、Debug 面板、拒答解释、多模式切换、登录态、EventSource token、用户中断、重试和反馈。
```

**项目里怎么对应**

- SSE 流式聊天。
- 路由追踪。
- Debug 检索分数面板。
- 引用展示。
- simple / agentic / auto 模式切换。
- Web Speech 输入和 TTS 播放。

## 19. 数据治理为什么重要？

**人话理解**

RAG 的上限不只取决于模型，也取决于资料本身。  
如果资料是旧的、重复的、互相矛盾的、权限混乱的，再好的模型也会被喂坏。

**面试怎么说**

```text
企业 RAG 的数据治理包括文档版本、生效期、来源权威、权限范围、重复文档、事实冲突和删除同步。模型回答之前要知道哪份资料更新、哪份资料更权威、当前用户有没有权限看。否则系统不是答不准，而是会把过期或越权内容说得很确定。
```

**项目里怎么对应**

- 文档 metadata 有 `docVersion`、`effectiveAt`、`expiredAt`、`sourceAuthority`。
- `fact_conflicts` 记录事实冲突。
- 文档删除会同步清理数据库、chunk、BM25、向量侧数据。
- 多租户隔离按 `userId` 贯穿数据库、Redis、Milvus、BM25。

## 20. 权限和安全边界怎么讲？

**人话理解**

RAG 不只是“能不能答”，还要看“这个人能不能看”。  
如果一个普通员工问到了管理员文档，模型答出来就是事故。

**面试怎么说**

```text
企业 RAG 权限不能只在接口层做一次判断，检索层也要做权限过滤。关系库、缓存、向量库、关键词索引都要带租户或用户维度。工具调用也要有权限边界，不同 Agent 或不同用户能调用的工具应该不同。
```

**项目里怎么对应**

- JWT 认证保护接口。
- EventSource 用 query token 兼容 SSE。
- PostgreSQL / Redis / Milvus / BM25 都按 `userId` 隔离。
- Jobs 写操作用 admin 角色守卫。

## 21. 缓存和成本怎么控制？

**人话理解**

AI 应用贵，不只是模型贵。Embedding、Rerank、Web Search、长上下文、Agent 多轮工具调用都会花钱、拖慢速度。

**面试怎么说**

```text
成本控制要从缓存、预算和路由三方面做。缓存 embedding、查询结果和会话状态；预算限制 max steps、tool calls、rerank topN、web search 数量和 token；路由上普通问题走 simple RAG，复杂问题才走 Agentic，避免所有请求都进入高成本链路。
```

**项目里怎么对应**

- Embedding 缓存。
- Redis 会话缓存。
- Agentic 有 `AGENTIC_*` 成本边界。
- auto 模式不会默认把普通问题交给 Agentic。
- Prometheus 记录 LLM 调用耗时和 token 估算。

## 22. 模型选择怎么讲？

**人话理解**

不是模型越大越好。  
不同位置需要不同模型：生成答案、生成 embedding、rerank、分类、提取结构化信息，要求都不一样。

**面试怎么说**

```text
我会按任务选模型。生成答案看推理和表达；embedding 看语义召回效果、维度和成本；rerank 看排序效果和延迟；分类和结构化抽取可以用更便宜更稳定的模型。模型切换必须跑评测回归，因为模型升级可能提升一类问题，同时破坏另一类问题。
```

**项目里怎么对应**

- Qwen/OpenAI-compatible LLM。
- Qwen Embedding。
- DashScope Rerank。
- Provider 抽象允许替换模型。
- `eval:rag:quality` 用于模型变更后的回归验证。

## 23. 多模态 RAG 怎么理解？

**人话理解**

资料不一定都是纯文本。PDF 里有表格，图片里有截图，语音里有会议内容。多模态 RAG 就是把这些信息也变成可检索、可引用的证据。

**面试怎么说**

```text
多模态 RAG 的关键是先把不同模态转成可索引的结构。语音先 ASR 成文本，图片或扫描 PDF 需要 OCR，表格要保留行列结构，图片可以保存描述和原始位置。最终仍然要回到可召回、可引用、可验证的证据链。
```

**项目里怎么对应**

- 支持 PDF/DOCX 文档解析。
- 腾讯云 ASR/TTS 已接入。
- 表格 chunk 会保留结构提示。
- 复杂扫描件和图片 OCR 是后续可增强方向。

## 24. GraphRAG 什么时候有用？

**人话理解**

普通 RAG 像查资料。GraphRAG 像查关系网。  
如果问题问“谁和谁有关”“上下游是什么”“哪个系统依赖哪个部门”，图谱更合适。

**面试怎么说**

```text
GraphRAG 适合关系型、多跳问题，比如组织关系、系统依赖、合同主体、项目负责人、上下游链路。它不替代普通 RAG，而是补足实体关系推理。真正价值不在 Neo4j 能不能跑，而在实体类型、关系类型、别名、置信度、版本和生效期这些业务图谱治理。
```

**项目里怎么对应**

- Neo4j Provider。
- 实体关系抽取。
- 图谱导入和查询接口。
- 别名和关系置信度。
- 真实业务图谱数据源仍是落地关键。

## 25. 人工介入什么时候需要？

**人话理解**

不是所有事情都应该让 Agent 自动做完。  
涉及钱、权限、删除、发布、合同、生产环境，就应该让人确认。

**面试怎么说**

```text
Human-in-the-loop 是 Agent 的安全阀。低风险任务可以自动执行，高风险任务要中断等待审批，比如删除数据、生产发布、转账、权限变更。工程上要支持 interrupt、保存状态、审批后 resume，并记录审计日志。
```

**项目里怎么对应**

- Agentic RAG 支持 interrupt / resume。
- 项目规则里红线操作需要确认。
- Jobs 和工具调用都有权限边界。

## 26. 线上迭代怎么做？

**人话理解**

RAG 和 Agent 不是上线就结束。  
用户每次问错、答偏、拒答失败，都是新的训练样本和回归样本。

**面试怎么说**

```text
AI 应用上线后要持续运营评测集。把线上失败问题分类：召回失败、排序失败、上下文污染、模型幻觉、权限问题、工具失败、超时问题。每类失败都要回到数据、检索、prompt、工具或评测集里修复，并在质量门禁里防止回归。
```

**项目里怎么对应**

- 业务回归集。
- 项目级仿真实业务评测。
- Qwen LLM-as-Judge 可选评估。
- `ROADMAP.md` 记录真实缺口和验证结果。

## 27. 常见坑怎么主动讲？

**人话理解**

面试官喜欢听你踩过什么坑，因为坑能证明你不是只看教程。  
但讲坑不能只吐槽，要讲原因、修复、验证。

**面试怎么说**

```text
我遇到过几类典型坑：纯向量召回会混入旧版本制度；弱关键词会误召回导致无答案题被回答；LLM 生成的引用看起来存在但 claim 不一定被支撑；Milvus 本地 search 可能 timeout；Agent 如果没有预算容易循环。我的处理是 query normalize、中文短语重合闸门、claim-level 引用校验、向量失败降级 BM25、Agentic 成本边界和评测回归。
```

**项目里怎么对应**

- 版本冲突题修复。
- 弱词误召回修复。
- LLM 引用不合格回退片段抽取式答案。
- Milvus timeout 降级。
- Agentic 成本边界。

## 28. 高级面试要讲“决策过程”

**人话理解**

高级岗位不是考你背不背概念，而是看你能不能做技术判断。  
只说“我用了 Milvus、Rerank、LangGraph”不够，要说清楚：为什么要用、当时还有什么选择、你怎么比较、最后效果如何。

**面试怎么说**

```text
我一般会按背景、问题、候选方案、方案对比、最终选择、落地细节、验证结果、遗留边界这条线讲。这样面试官能看到我不是照搬技术栈，而是基于业务问题做了权衡。
```

**项目里怎么对应**

- 背景：企业知识库需要查得准、答得稳、引用能撑住、不会瞎编。
- 问题：纯向量召回、无引用答案、Agent 成本失控、外部依赖不稳定。
- 对比：simple RAG / Agentic RAG、BM25 / ES / Milvus、Chain / ReAct / LangGraph。
- 选择：普通问题走 simple，复杂问题走 Agentic；检索走 hybrid；Agent 用 LangGraph/FSM 管边界。
- 效果：本地成熟度 93/100，项目级仿真实业务评测 28/28。

## 29. 项目叙事模板

以后讲任何技术点，都按这个模板：

```text
1. 背景：当时业务/系统遇到什么问题？
2. 目标：我要解决什么，不解决什么？
3. 方案候选：有哪些可选方案？
4. 对比权衡：每个方案的优点、缺点、风险是什么？
5. 我的选择：为什么选这个，不选其他？
6. 落地实现：具体怎么做？
7. 验证效果：用什么指标、测试或线上反馈证明有效？
8. 遗留边界：还有什么没解决，后续怎么做？
```

最短版本：

```text
背景是什么 -> 我比较了哪些方案 -> 为什么这么选 -> 怎么落地 -> 效果如何 -> 还有什么边界
```

## 30. 示例：为什么选择 Hybrid Retrieval？

**背景**

企业知识库里既有自然语言问题，也有制度编号、金额、日期、系统缩写、版本号。

**候选方案**

- 纯向量检索。
- 纯 BM25 / ES 关键词检索。
- BM25 / ES + 向量混合检索。

**方案对比**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯向量 | 语义召回好，同义表达友好 | 金额、版本、编号容易误召回 |
| 纯关键词 | 精确、可解释、对专有词稳定 | 同义表达、模糊问题召回差 |
| 混合检索 | 同时兼顾语义和精确事实 | 实现复杂，需要融合分和评测 |

**我的选择**

```text
我选择 hybrid retrieval。因为企业知识库不是闲聊，金额、版本、生效期这类精确信息非常关键；但用户提问又经常是口语化的，只靠关键词也不够。所以用 BM25/ES 兜住精确事实，用向量补语义召回，再用 reranker 做精排。
```

**效果**

- 中文召回更稳定。
- 版本、金额、别名题更容易命中。
- 向量失败时还能降级 BM25。
- 项目级仿真实业务评测 28/28 通过。

**边界**

- 融合权重需要评测集调优。
- 向量库 runtime 仍要治理。
- 真实业务题库接入后还要继续回归。

## 31. 示例：为什么普通问题不默认走 Agentic？

**背景**

Agentic RAG 看起来更智能，但会增加延迟、成本和不确定性。

**候选方案**

- 所有问题都走 Agent。
- 所有问题都走 simple RAG。
- simple 为主，复杂问题才走 Agentic。

**方案对比**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全部 Agentic | 能处理复杂问题，流程统一 | 成本高、慢、容易循环、难解释 |
| 全部 simple | 稳定、快、可解释 | 多跳、工具调用、联网问题能力弱 |
| 路由分流 | 稳定性和复杂能力兼顾 | 需要设计路由边界 |

**我的选择**

```text
我选择 simple 为主、Agentic 为增强。普通事实问题走 simple hybrid retrieval，链路短、快、可解释；只有多跳、对比分析、联网、工具调用、规划类问题才进入 Agentic。这样不会为了智能感牺牲稳定性。
```

**效果**

- 普通问答稳定。
- 复杂问题有 Agentic 扩展能力。
- auto 模式不再随便把普通问题交给 Agent。
- Agentic 有 query、tool、rerank、retry 等预算限制。

**边界**

- 路由规则需要持续用真实问题校准。
- 复杂问题仍要观察成本和延迟。

## 32. 示例：为什么用 LangGraph / FSM 管 Agent？

**背景**

Agent 如果只靠 ReAct prompt，容易出现步骤不可控、循环、工具乱调、失败难定位。

**候选方案**

- Chain。
- ReAct。
- LangGraph / FSM。

**方案对比**

| 方案 | 优点 | 缺点 |
|---|---|---|
| Chain | 简单、稳定 | 不适合复杂分支和循环 |
| ReAct | 灵活，适合探索 | 不稳定，终止和状态难管 |
| LangGraph/FSM | 状态、分支、循环、恢复清晰 | 实现成本更高 |

**我的选择**

```text
我选择用 LangGraph/FSM 思路做 Agentic 编排。因为生产级 Agent 不能只有灵活性，还要能看见状态、限制循环、支持中断恢复和失败降级。ReAct 可以作为局部能力，但外层需要状态机管住。
```

**效果**

- 节点清晰：routing、query augment、retrieval、web search、rerank、generate、reflection。
- SSE 可以展示过程。
- 可以加 checkpoint 和 resume。
- 更容易做预算和 trace。

**边界**

- 图复杂后维护成本会上升。
- 节点粒度要控制，不能为了拆而拆。

## 33. 示例：记忆方案怎么选？

**背景**

多轮对话和跨会话场景需要记住上下文，但把所有历史都塞进 prompt 会变慢、变贵，还会污染答案。

**候选方案**

- 全量历史直接塞 prompt。
- 最近 N 轮对话。
- 摘要记忆。
- Redis Checkpointer。
- 长期记忆 / 向量记忆。

**方案对比**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全量历史 | 信息完整 | 贵、慢、噪声大 |
| 最近 N 轮 | 简单 | 容易丢关键事实 |
| 摘要记忆 | 节省上下文 | 摘要可能丢条件或固化错误 |
| Redis Checkpointer | 适合线程状态恢复 | 不是长期知识库 |
| 长期/向量记忆 | 可跨会话检索 | 需要写入筛选和权限控制 |

**我的选择**

```text
我会分层做记忆：当前推理状态放 graph state；当前会话状态用 Redis Checkpointer 或 message history；跨会话稳定事实放 Mem0/DB；历史问答相似召回放向量库。写入长期记忆前必须判断是不是稳定事实，不能把临时猜测写进去。
```

**效果**

- 当前会话可恢复。
- 历史问答可语义召回。
- 长期偏好有独立管理。
- 不把所有历史都塞进 prompt。

**边界**

- 长期记忆需要删除、审计和权限。
- 摘要记忆要避免把错误固化。

## 34. 示例：为什么要做项目级评测？

**背景**

RAG demo 很容易看起来能答，但真实业务会问版本冲突、别名、跨文档、无答案、权限边界。

**候选方案**

- 手工 demo。
- 少量 smoke 测试。
- 离线数据集评测。
- 真实服务回放评测。

**方案对比**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 手工 demo | 快 | 主观、不可回归 |
| smoke 测试 | 能防主链路断 | 覆盖浅 |
| 离线评测 | 快、稳定 | 不验证真实服务链路 |
| 真实回放 | 最接近实际 | 成本高，依赖服务 |

**我的选择**

```text
我会同时做离线评测和真实服务回放。离线评测适合快速门禁，真实回放能验证上传、入库、检索、生成、引用、清理的完整链路。项目级评测要包含版本冲突、跨文档、别名、拒答和引用支撑。
```

**效果**

- `eval:rag:quality` 做总门禁。
- 项目级仿真实业务评测真实调用后端。
- simple/auto 共 28/28 通过。
- 暴露过版本冲突和弱词误召回问题，并修复。

**边界**

- 仿真实业务题不能代替公司真实私有题库。
- 真实业务题库接入后才有真正业务分。

## 35. 12-Factor Agent 怎么讲？

**人话理解**

生产级 Agent 不是「给模型一堆工具让它自由发挥」。
更靠谱的做法是：大部分控制流由确定性代码掌握，LLM 只在理解意图、选择动作、生成结构化决策这些关键点发挥作用。

**面试怎么说**

```text
我会把 Agent 设计成“确定性流程 + LLM 决策点”。LLM 负责把自然语言转成结构化工具调用，应用代码负责状态管理、权限校验、工具执行、错误处理、暂停恢复和审计。这样既保留模型的灵活性，又不会让它完全控制系统流程。
```

**12 个工程原则**

| 原则 | 解决什么 | 面试讲法 |
|---|---|---|
| 自然语言转工具调用 | 不靠解析一段自由文本执行动作 | 模型输出 JSON / tool call，宿主执行 |
| 拥有 Prompt | Prompt 不是框架黑盒 | 模板版本化、可回放、可灰度 |
| 拥有上下文窗口 | 不被动累积历史 | 主动选择 RAG、记忆、工具结果、错误摘要 |
| 工具即结构化输出 | 工具调用本质是生成结构化数据 | schema、enum、required 字段要严格 |
| 统一执行状态和业务状态 | Agent 过程可恢复、可审计 | state 里有任务、步骤、工具结果、错误、预算 |
| 启动 / 暂停 / 恢复 | 支持长任务和人工审批 | launch、pause、resume、status 是基础 API |
| 用工具联系人类 | human-in-the-loop 也结构化 | 请求审批、澄清、确认都作为事件进入状态机 |
| 拥有控制流 | 不让 LLM 任意循环 | 预定义节点、分支、终止条件和预算 |
| 错误压缩进上下文 | 让模型能恢复但不污染上下文 | 错误摘要、失败原因、建议动作，不塞长日志 |
| 小而专注的 Agent | 避免万能 Agent 上下文爆炸 | 子 Agent 职责边界清楚，最后由 Supervisor 汇总 |
| 多入口触发 | Web、CLI、队列、Webhook 共用核心 | channel adapter 和 agent core 分离 |
| 无状态 reducer | 便于测试和水平扩展 | Agent core 接收 state + event，返回新 state |

**项目里怎么对应**

- `simple / auto / agentic` 分层，避免所有问题都进复杂 Agent。
- Agentic RAG 用状态机思想表达 query augment、retrieval、sufficiency、web search、rerank、generate、reflection。
- Redis Checkpointer / message history 支持线程状态恢复。
- Tool / MCP 调用有 schema、超时、降级和审计口径。

**不能这么说**

- 「Agent 全自动自己决定所有流程。」
- 「工具接进来就能自动办事。」
- 「ReAct prompt 写好就能生产上线。」

## 36. Agent Harness 怎么设计？

**人话理解**

模型只是大脑，Harness 是身体、工具、权限、记忆、通道和反馈系统。
同一个模型，放在普通聊天框里只是问答；放进好的 Harness 里，才可能稳定办事。

**面试怎么说**

```text
Agent = Model + Harness。高级 Agent 开发的重点不是只调模型 API，而是设计 Harness：模型抽象、Agent loop、工具注册、记忆、权限策略、通道适配、自驱触发、trace 和 eval。Harness 决定模型能不能在真实业务环境里稳定、可控、可观测地工作。
```

**七层模型**

| 层级 | 作用 | 必会点 |
|---|---|---|
| L1 模型层 | 换模型不改业务 | provider abstraction、模型路由、fallback、token / latency 记录 |
| L2 循环层 | 一次问答变持续工作 | max steps、timeout、stop condition、interrupt / resume、trace id |
| L3 工具层 | 让 Agent 能行动 | tool registry、schema、分页 / 摘要返回、最小权限、审计 |
| L4 记忆层 | 保持任务和用户连续性 | working / episodic / semantic / procedural memory |
| L5 人格 / 策略层 | 跨模型保持边界一致 | `AGENTS.md`、policy、permission、输出模板 |
| L6 通道层 | 接入真实用户入口 | Web、CLI、IM、Email、Webhook、队列，和 core 解耦 |
| L7 自驱层 | Agent 主动检查任务 | cron、heartbeat、monitor、queue worker，要等权限和 eval 成熟后再开 |

**可靠性六件套**

| 机制 | 为什么必须有 |
|---|---|
| Idempotency | 防止重试后重复写入、重复发送、重复扣费 |
| Timeout + Circuit Breaker | 防止慢工具拖垮整条 trajectory |
| Rate-limit aware retry | 限流时指数退避和 provider fallback |
| Cost Guard | 防止循环调用工具烧 token |
| Permission Tier | 读自动、写 dry-run + 审批、不可逆动作显式确认 |
| Observability | prompt、tool call、result、token、latency 全链路可回放 |

## 37. Agent Evaluation Harness 怎么讲？

**人话理解**

LLM 评测看「答得对不对」，Agent 评测看「事情有没有做成」。
Agent 说「我已经创建订单」不算成功，数据库里真的有订单才算成功。

**面试怎么说**

```text
Agent 评测必须评完整任务，而不是只看最终回复。一个 Evaluation Harness 要定义 Task、Trial、Grader、Transcript、Outcome 和 Report；既看模型说了什么，也看工具调用、环境状态和最终业务结果。能用 code-based grader 的先用确定性评分，开放质量再用 LLM judge，人审用来校准。
```

**核心概念**

| 概念 | 含义 | 面试易错点 |
|---|---|---|
| Task | 初始状态 + 成功标准 + 可用工具 | 不是一个 prompt，而是一道完整任务 |
| Trial | 同一 task 的一次执行 | Agent 有随机性，通常要多次 trial |
| Transcript | 对话和工具轨迹 | Agent 说做了不代表真的做了 |
| Outcome | 环境最终状态 | DB、文件、API 调用记录才是硬证据 |
| Grader | 评分器 | code-based、LLM judge、human 各有分工 |
| Report | 汇总结果和失败归因 | 只报准确率不够，要报失败类别 |

**评分器怎么选**

| 评分器 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| Code-based | 确定、快、便宜 | 只能评明确规则 | DB 状态、文件结果、引用编号、工具调用 |
| LLM Judge | 能评开放质量 | 非确定、有偏差、成本高 | 完整性、语气、解释质量、faithfulness |
| Human | 最可靠 | 慢、贵、难规模化 | 标准样本校准、高风险上线决策 |

**高级指标**

- `pass@k`：多次尝试至少一次成功，适合 coding agent。
- `pass^k`：连续 k 次都成功，适合用户面向 Agent。
- `task success rate`：任务是否完成。
- `tool success rate`：工具调用是否正确。
- `step accuracy`：中间步骤是否合理。
- `cost / latency`：每个任务的 token、耗时、工具成本。
- `safety violation rate`：越权、泄露、危险动作比例。

**上线门禁**

```text
Offline diff -> Shadow traffic -> A/B with guardrails -> Phased rollout
```

面试要强调：guardrail 触发才 early stop，不能用主指标反复偷看做 p-hacking。

## 38. Agentic RAG / Deep Research 怎么讲？

**RAG 四代演进**

| 阶段 | 典型流程 | 核心问题 |
|---|---|---|
| Naive RAG | embed -> retrieve topK -> stuff -> generate | 搜一次就答，检索差就生成差 |
| Advanced RAG | query rewrite + hybrid + rerank | 组件增强，但流程固定 |
| Modular RAG | retriever / reranker / generator 可替换 | 工程模块化，但不会自适应 |
| Agentic RAG | Agent 决定搜不搜、搜什么、够不够、要不要再搜 | 把检索控制权交给 Agent，但要受状态机和预算约束 |

**面试怎么说**

```text
Naive RAG 是搜一次就答，Advanced RAG 是搜得更准再答，Modular RAG 是组件可替换，Agentic RAG 是让 Agent 判断是否检索、怎么检索、检索够不够、是否需要二次检索。生产里我不会让它无限自治，而是用状态机、预算和 sufficiency gate 控制。
```

**关键模式**

| 模式 | 做什么 | 优缺点 |
|---|---|---|
| Adaptive Retrieval | 判断是否需要检索 | 省成本，但误判会漏证据 |
| Query Decomposition | 复杂问题拆子问题 | 多跳能力强，但更慢 |
| Multi-step Retrieval | 后一轮基于前一轮结果继续搜 | 能逐步补证据，但要防循环 |
| Self-RAG | 生成过程中判断是否检索、是否支撑 | 粒度细，成本高，通常需要训练或强约束 |
| CRAG | 检索后评估质量，不够就纠错 / web search | 工程更易落地，但评估器很关键 |
| Deep Research | 多轮搜索、多源验证、长报告 | 适合研究任务，不适合所有问答 |

**搜够了怎么判断**

- 新增信息趋近饱和。
- 关键子问题都有证据。
- 多源事实能交叉验证。
- 置信度达到阈值。
- 时间、token、轮数预算到达。
- 仍缺证据时明确不确定，而不是继续编。

## 39. Skills / 程序性记忆怎么讲？

**人话理解**

Tool 是能力，Skill 是会用能力的流程。
Prompt 是这一次怎么做，Memory 是知道了什么，Skill 是以后遇到这类事怎么做。

**四个概念边界**

| 概念 | 本质 | 例子 |
|---|---|---|
| Prompt | 一次性指令 | 这次用专业语气回复 |
| Tool | 原子能力 | `search_docs`、`read_file`、`call_api` |
| Memory | 陈述性知识 | 用户偏好、历史事实 |
| Skill | 程序性知识 | 部署流程、调试 API SOP、面试文档更新流程 |

**Claude Code Skills 机制**

| 设计 | 为什么重要 |
|---|---|
| `SKILL.md` | 用 Markdown 固化流程、边界、步骤和引用资料 |
| YAML frontmatter | 用 name、description、toolsets、platform 做条件激活 |
| Progressive Disclosure | 系统提示词只放索引，正文按需读取，避免 token 爆炸 |
| references / templates / scripts | 大材料按需加载，不一次性塞上下文 |
| 正文以 user message 注入 | 保持 system prompt 稳定，提高 prompt cache 命中 |

**安全边界**

- Skill 是新的供应链入口，不能默认信任社区 Skill。
- 恶意 `SKILL.md` 可能做 prompt injection。
- 要做来源审计、静态扫描、权限隔离、沙箱验证。
- 高风险 Skill 不应自动执行写操作。

## 40. Memory 高级设计怎么讲？

**记忆分类**

| 类型 | 存什么 | 例子 |
|---|---|---|
| Working Memory | 当前任务状态 | 当前步骤、最近工具结果、待办 |
| Episodic Memory | 发生过什么 | 某次会话、某次部署失败轨迹 |
| Semantic Memory | 稳定事实 | 用户偏好、业务规则、实体属性 |
| Procedural Memory | 怎么做 | SOP、Skill、成功调试流程 |

**面试怎么说**

```text
我不会把所有历史都叫 Memory。工作记忆解决当前任务状态，情景记忆记录发生过的事件，语义记忆保存稳定事实，程序性记忆沉淀可复用流程。不同记忆要用不同存储和召回策略，否则会出现记忆污染、过期事实和 token 爆炸。
```

**冲突、过期和遗忘**

| 问题 | 错误做法 | 正确做法 |
|---|---|---|
| 偏好变化 | 直接覆盖旧事实 | 新偏好成为 active，旧偏好降权保留审计 |
| 来源冲突 | 随机选一个 | 记录来源、时间、权威度，无法判断就标不确定 |
| 过期事实 | 直接删除 | 从 active retrieval 退出，保留 archival index |
| 噪声记忆 | 全部长期保存 | 重要性、频率、时效、查询多样性共同决定晋升 |

**工程选型**

- 热的当前状态：Redis / memory。
- 可审计事件：关系库 / JSONL / 对象存储。
- 语义检索：Milvus / Qdrant / pgvector。
- 关键词检索：ES / FTS。
- 关系推理：Neo4j / NebulaGraph。

## 41. 生产 Agent 的数学现实

**面试怎么说**

```text
我不会追求全自主长链路 Agent。多步骤 Agent 有错误复合问题，如果每步 95% 可靠，20 步整体成功率只有约 36%。长对话还会带来上下文成本近似二次增长。所以生产里要限制步骤数，把任务拆成 3-5 个可验证子流程，有明确回滚点、预算、人工确认和评测回归。
```

**关键判断**

| 问题 | 生产做法 |
|---|---|
| 步骤越多越不稳 | 限制 max steps，拆小任务 |
| 长上下文越来越贵 | 压缩、检索、摘要、状态外置 |
| 工具返回太长 | 返回摘要、前 N 条、next token、source id |
| 工具失败 | 结构化错误、重试、熔断、降级 |
| 写操作风险高 | dry-run、人工确认、幂等 key、审计 |
| 评测不稳定 | 多 trial、读 transcript、验 outcome |

## 42. Agent 框架怎么选？

**人话理解**

框架不是越火越好。高级 Agent 开发要能说清楚：我为什么选这个框架，它牺牲了什么，后续怎么扩展。

**面试怎么说**

```text
我不会按 star 数选 Agent 框架，而是按任务形态选。固定链路用 Chain，复杂状态机用 LangGraph，多角色协作可以看 AutoGen / CrewAI，高合规客服类场景可以关注 Parlant，学习原理可以看 Swarm。生产里我更看重状态可控、工具治理、可观测、评测和降级，而不是框架 demo 是否炫。
```

| 框架 / 方案 | 适合场景 | 优点 | 缺点 | 面试取舍 |
|---|---|---|---|---|
| LangChain | 快速原型、RAG 组件拼装 | 生态完整，资料多 | 抽象厚，复杂链路调试难 | 适合搭积木，不适合让复杂 Agent 完全黑盒 |
| LangGraph | 复杂工作流、可恢复 Agent | 状态、分支、循环、checkpoint 清楚 | 学习成本更高 | 生产级 Agentic RAG 优先讲它 |
| AutoGen | 多 Agent 协作、可视化实验 | 多 Agent 能力强，上手快 | 深度定制和生产治理要补 | 适合讲多 Agent 原型，不要替代状态治理 |
| CrewAI | 角色明确的小团队 Agent | 简单、快、适合 demo | 能力边界相对简单 | 适合快速验证，不是复杂生产首选 |
| Swarm | 学习 Agent 原理 | 极简，便于读源码 | 功能基础 | 面试可说用来理解 handoff / routing |
| Parlant | 客服、金融、医疗等合规对话 | 指令遵循和流程约束强 | 场景较聚焦 | 高风险客户场景值得关注 |
| AgentScope | 模块化企业 Agent | 模块边界清楚，适合企业开发 | 生态相对新 | 可作为企业级模块化了解项 |

**项目里怎么对应**

项目选择偏 `LangGraph/FSM`，因为 RAG 问答需要可控节点：routing、query augment、retrieval、sufficiency、web search、rerank、generate、citation、reflection。它牺牲了一点自由度，但换来状态可观测、预算可控、失败可降级。

## 43. Parlant / 合规型 Agent 怎么讲？

**人话理解**

高风险 Agent 不是只追求准确率。
更关键的是：就算失败，也不能失败得太严重。

**面试怎么说**

```text
合规型 Agent 不能只看失败频率，还要看失败严重程度。一个 99% 准确但偶尔越权退款的 Agent，比 85% 准确但只会措辞生硬的 Agent 更危险。金融、医疗、客服、审批场景里，架构要限制最坏失败，而不是寄希望于模型每次都听话。
```

**Parlant 值得记的点**

| 概念 | 说明 | 面试怎么用 |
|---|---|---|
| Guidelines | 业务原则和行为边界 | 不把所有规则塞进一个 prompt，而是按场景匹配最相关指南 |
| Journeys | 有明确阶段的对话流程 | 比如退款、开户、审批、投诉处理 |
| Strict Mode | 严格输出和流程控制 | 高风险场景宁可保守，也不越权承诺 |
| ARQs | Attentive Reasoning Queries，结构化推理查询 | 用预定义问题引导模型恢复关键指令、上下文和验证点 |
| 失败严重程度 | failure severity | 评估 Agent 能不能上线时，比单纯准确率更关键 |

**五类错位风险**

| 风险 | 例子 | 工程对策 |
|---|---|---|
| 跑题 | 客户问退款，回答泛泛科普 | 领域 scope、意图确认 |
| 范围不足 | 不知道自己是哪个业务的客服 | 明确角色和可处理范围 |
| 幻觉 | 编造 24 小时客服 | 引用、工具校验、拒答 |
| 不合规 | 越权承诺补偿 / 退款 | 权限分级、审批、Strict Mode |
| 忽略指令 | 未验证账号就查余额 | 流程门禁、强制工具步骤 |

## 44. Agent 沙箱怎么讲？

**人话理解**

当 Agent 能执行代码、访问文件、控制浏览器或操作桌面时，安全边界必须前置。
云端 Agent 怕搞坏服务器，本地 Agent 怕搞坏用户电脑。

**面试怎么说**

```text
代码执行、浏览器自动化和本地文件访问都不能直接给 Agent 裸权限。我要按风险选择沙箱：本地开发可以用 OS 级 sandbox 或 Docker；执行不可信代码要用 microVM / E2B 这类更强隔离；企业多租户可以用 K8s + gVisor / Kata / OpenSandbox。沙箱要限制文件系统、网络出站、CPU/内存、执行时间、可写目录和 secret 可见性。
```

| 方案 | 适合场景 | 优点 | 缺点 |
|---|---|---|---|
| OS 原生隔离 | 本地低风险开发 | 延迟低，集成简单 | 隔离强度有限 |
| Docker | 内部工具、受控代码执行 | 成熟、易部署 | 容器逃逸和权限配置要小心 |
| microVM / E2B | 不可信代码、生产隔离 | 隔离强，冷启动可控 | 成本和运维复杂 |
| gVisor / Kata | K8s 多租户隔离 | 企业级资源调度 | 平台复杂度高 |
| OpenSandbox | 企业 AI 沙箱平台 | 协议统一，多语言 SDK | 需要平台化接入 |
| Browser / WebContainer | 前端 demo、教育、轻量代码环境 | 交互体验好 | runtime 受限 |

**沙箱必须控的 7 件事**

- 文件系统：只挂载任务目录，默认只读，写目录白名单。
- 网络：默认限制出站，域名白名单。
- Secret：环境变量脱敏，不让模型读真实 key。
- 资源：CPU、内存、磁盘、进程数、执行时长限制。
- 权限：读、写、执行、外部请求分级。
- 审计：记录命令、文件变更、网络请求和输出。
- 清理：任务结束销毁环境或回滚快照。

## 45. 多模态 RAG 证据定位怎么讲？

**人话理解**

多模态 RAG 不是把图片 OCR 成文字就完事。
真正难的是：答案能不能回到原图、原页、原表格、原时间点。

**面试怎么说**

```text
多模态 RAG 的核心是解析、对齐、索引、检索、生成、引用和评测。PDF、扫描件、图片、表格、公式、音视频进入系统后，不仅要转成文本，还要保留 page、bbox、figure、table、caption、timestamp、section 等证据定位信息。否则模型即使答对，也无法让用户验证。
```

| 路线 | 适合场景 | 关键点 |
|---|---|---|
| Text-first | 正文为主，图表少 | OCR / ASR 后进入普通 RAG |
| Layout-aware | PDF、表格、双栏、合同、财报 | 保留阅读顺序、页码、bbox、表格行列 |
| Vision retrieval | 截图、图表、版面本身是证据 | 了解 ColPali / ColQwen 这类视觉文档检索 |
| All-in-one multimodal | 文本、图片、表格、公式混合 | 统一 chunk schema 和 citation schema |
| Agentic document QA | 复杂文档定位和验证 | Agent 多步定位图表、正文、脚注和版本 |

**怎么评测**

- 文本题：答案能否引用正确段落。
- 表格题：行、列、单位、币种是否正确。
- 图表题：figure / caption / 正文解释是否对齐。
- 扫描件：OCR 错字率是否影响答案。
- 音视频：timestamp 是否能回到原片段。
- 视觉检索：可了解 ViDoRe 这类视觉文档检索评测。

## 46. 数据合成 / 评测集构建怎么讲？

**人话理解**

数据合成不是为了显得会算法训练。
对高级 Agent 开发来说，它更重要的价值是：冷启动评测集、补齐边界 case、把失败样本变成回归集。

**面试怎么说**

```text
我对数据合成的理解不是“让 LLM 批量编题”，而是用 LLM 辅助构造可验证的评测和训练样本。核心不在生成，而在验证。企业 Agent 的评测集可以来自生产日志、用户投诉、人工客服升级、业务 SOP、线上失败样本和安全边界 case；冷启动时可以用合成数据扩充覆盖，但必须经过格式、语义、约束、多样性和去污染过滤，不能把合成题冒充真实业务效果。
```

**常见方法**

| 方法 | 做什么 | 应用开发岗怎么讲 |
|---|---|---|
| Self-Instruct | 从少量种子问题扩展更多 instruction / QA | 适合冷启动评测集，解决覆盖不够 |
| Evol-Instruct | 把简单问题变复杂，加约束、加步骤、加场景 | 适合构造复杂追问、多跳、边界问题 |
| Rejection Sampling | 生成多条候选，用 verifier / judge 选好的 | 应用岗只讲质量筛选，不展开训练公式 |
| Constitutional AI | 用规则让模型自我批判和修正 | 可用于安全、合规、拒答样本构造 |
| Distilabel / DataFlow | 标准化数据 pipeline | 说明数据处理要工程化、可组合、可复现 |
| AgenticRAGTracer | 从原子 QA 逐步构造多跳 QA | 重点讲“逐级验证”，不是拼接问题 |

**五道质量防线**

| 防线 | 检查什么 |
|---|---|
| 格式验证 | JSON、tool call、字段、类型、必填项是否合法 |
| 语义验证 | 问题和答案是否对齐，轨迹是否自洽 |
| 约束验证 | 能否用规则、测试、数据库状态、业务校验器验证 |
| 多样性检查 | 是否覆盖不同意图、难度、文档类型、失败模式 |
| 去污染 | 测试集不能泄露进训练 / 生成样本，避免虚高 |

**AgenticRAGTracer 值得记的点**

```text
高质量多跳数据不是把几个问题拼起来，而是从原子事实逐跳构造，并验证每个证据是否必要。Dependency Irreducibility 的意思是：去掉任意一个支持文档，问题就应该答不出来；如果去掉某个文档还能答出来，说明那不是真多跳。
```

**项目里怎么对应**

- 游戏营销 96 问是专项业务回归集，不是线上真实准确率。
- 失败样本要回流到评测集，防止同类问题反复出现。
- 合成数据适合冷启动和覆盖边界，但最终要接真实业务日志、真实活动复盘和人工标注。

## 47. 企业 Agent 落地：为什么工作流优先？

**人话理解**

高级 Agent 开发不是先问“要做几个 Agent”，而是先问“业务工作流怎么变得更好”。
Agent 不是所有问题的最佳答案。有些步骤用规则系统更稳，有些用普通自动化更便宜，有些才适合 Agent。

**面试怎么说**

```text
我不会为了 Agent 而 Agent。企业落地要先拆工作流：哪些步骤是低变化、高标准化的，可以用规则或传统自动化；哪些步骤需要信息聚合、跨文档判断、工具调用和异常处理，才适合 Agent；哪些高风险决策必须人审。Agent 的价值是把 RAG、工具、规则、人工反馈和业务系统编排起来，而不是替代整个流程。
```

**工作流拆解表**

| 工作流类型 | 推荐方案 | 原因 |
|---|---|---|
| 低变化、高标准化 | 规则系统 / 普通自动化 | 稳定、便宜、可解释 |
| 明确问答 / 查制度 | RAG + 引用 + 拒答 | 证据可追溯 |
| 复杂信息聚合 | Agentic RAG / Workflow | 需要拆问题、查工具、综合证据 |
| 写操作 / 审批 / 合规 | Human-in-the-loop | 责任边界不能交给模型 |
| 重复可复用任务 | 可复用 Tool / Skill / Agent 组件 | 避免每个任务造一个新 Agent |

**企业落地 6 条经验**

| 经验 | 面试讲法 |
|---|---|
| 工作流优先 | 先重构流程，再决定哪里放 Agent |
| Agent 不总是最佳答案 | 标准流程用规则更稳 |
| 投资评测体系 | Agent 像新员工，需要 onboarding、考核和反馈 |
| 每一步可追踪验证 | 不只看最终回答，要能定位每个中间步骤 |
| 做可复用组件 | Tool、Skill、Prompt、Eval、Parser 要复用 |
| 人类仍然重要 | 人负责判断、合规、边缘 case 和最终签署 |

**高级回答**

```text
我会把 Agent 当成工作流里的一个角色，而不是整个系统。上线前要给 Agent 明确岗位说明、可用工具、权限范围、评测标准和反馈机制；上线后要持续读 trace、看 outcome、收集失败样本、更新 SOP 和评测集。这样 Agent 才像一个可培养的新员工，而不是一个不可控黑盒。
```

## 48. 万能答题结构

任何题都按这个顺序答：

```text
1. 背景：为什么会有这个问题？
2. 目标：要解决什么，不解决什么？
3. 方案：有哪些可选方案？
4. 对比：优缺点和风险是什么？
5. 选择：为什么最终这么选？
6. 落地：项目里怎么实现？
7. 效果：怎么验证有效？
8. 边界：还有什么没解决？
```

例子：面试官问“RAG 召回怎么评测？”

```text
背景是 RAG 很容易 demo 看起来能答，但不知道证据是不是真的找到了。目标是把召回、排序、生成分开评估。方案上可以只看最终答案，也可以拆链路评测；我选择拆链路，因为这样能定位问题。检索层看 Recall@K、Hit Rate、MRR；排序层看 NDCG 和 rerank 后排序提升；生成层看 faithfulness、citation accuracy、claim support。项目里用 eval:rag:quality、业务回归集和项目级仿真实业务评测做门禁。效果是项目级仿真实业务 28/28 通过。边界是合成数据不能冒充真实业务数据，最终还要接真实题库。
```

## 49. 最小复习清单

面试前先把这些说顺：

- AI 应用的本质：把不稳定的模型能力放进可靠工程系统。
- 所有 AI 工程问题都看五件事：输入是否可靠，证据是否可靠，决策是否可控，输出是否可验，失败是否可收。
- RAG 是开卷考试，不是向量库加模型。
- RAG 主链路：数据处理、检索证据、排序筛选、上下文组装、答案生成、证据校验、失败回流。
- 向量看语义，ES/BM25 看关键词和精确条件，图谱看实体关系。
- 召回看有没有找到，重排看谁排前面。
- 评测拆 retrieval、rerank、generation。
- 不要乱报准确率；先定义任务、标签、样本、指标和评测集。
- 切片先按结构，再按 token 兜底。
- Agent 是目标驱动的任务系统，不是 chatbot。
- Agent 的核心是目标、状态、决策、工具、观察、下一步和终止。
- ReAct 灵活，LangGraph/FSM 可控。
- Agent 死循环靠状态机、预算、重复检测和 fallback。
- Tool 是能力，Skill 是使用能力的流程。
- 工具调用是模型提出意图，宿主系统校验和执行。
- MCP 是 Agent 连接工具的标准协议。
- 记忆要分工作、短期、长期、语义、情节。
- Context Engineering 是选择和压缩上下文。
- 没证据就拒答。
- 生产化要超时、降级、观测、预算、权限、评测。
- 数据治理要处理版本、生效期、来源权威和冲突事实。
- 权限过滤必须贯穿检索层，不能只在接口层。
- 成本控制靠缓存、预算、路由和评测。
- GraphRAG 适合关系型和多跳问题，不替代普通 RAG。
- GraphRAG 的价值来自高质量实体、关系、别名、置信度和业务 schema，不是来自接了 Neo4j。
- Human-in-the-loop 是高风险 Agent 动作的安全阀。
- AI Coding 要按规则、计划、小步修改、验证、文档同步推进，不让 AI 静默 mock 或碰红线。
- 高级面试必须讲清楚背景、方案对比、取舍、落地、效果和边界。
- 12-Factor Agent 的核心是：LLM 只做关键决策，控制流、状态、权限、执行和恢复归应用代码。
- Agent Harness 七层：模型、循环、工具、记忆、人格策略、通道、自驱。
- Evaluation Harness 要区分 Task、Trial、Transcript、Outcome、Grader 和 Report。
- Agent 评测不能只看回复，要验证环境状态和业务结果。
- Agentic RAG 是让 Agent 控制检索策略，但必须受预算、状态机和 sufficiency gate 约束。
- Deep Research 强调多轮搜索、多源交叉验证、信息饱和和长报告，不要把普通 RAG 包装成完整 Deep Research。
- Skill 是程序性记忆，要用渐进式披露和安全审计，不能全塞 System Prompt。
- 生产 Agent 要面对错误复合、长上下文成本、工具工程和企业系统集成复杂性。
- Agent 框架选型按任务形态，不按 star 数：LangGraph 管生产状态机，AutoGen/CrewAI 做协作原型，Parlant 适合合规对话。
- 合规型 Agent 要看失败严重程度，越权承诺比普通答错更危险。
- 代码执行、浏览器自动化、本地文件访问必须进沙箱，控制文件、网络、资源、secret 和审计。
- 多模态 RAG 要保留 page、bbox、figure、table、timestamp，否则答案无法追溯。
- 数据合成对应用岗的重点是评测集冷启动和失败样本回归，核心是验证，不是生成。
- 企业 Agent 落地要工作流优先，先判断规则、RAG、Agent、工具、人审分别放在哪一步。

