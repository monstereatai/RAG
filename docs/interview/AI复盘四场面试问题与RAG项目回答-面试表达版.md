# AI 复盘四场面试：RAG 项目面试表达版

> 这份不是技术百科，而是面试现场的“说话稿”。每题按「遇到什么需求／问题 → 业界通常怎么解决 → 我的方案怎么取舍和落地 → 最后带来什么效果」来讲。不要逐字背，记住自己的判断、做法和例子即可。
>
> 事实边界：当前仓库已经有可演示、可测试、可追踪的本地闭环；真实生产 SLA、企业 IAM／DLP、长期压测和业务收益仍需在目标环境验证。

## 先记住一条表达原则

面试时不要一上来报组件名。先说：

```text
当时遇到什么业务问题？
我为什么这样判断？
我在代码里怎么落地？
遇到失败时怎么处理？
现在还差什么生产验证？
```

比如不要说“我们使用了 Milvus、Elasticsearch、Neo4j 和 RRF”。可以说：

> 活动资料里有活动 ID、接口字段这种必须精确匹配的内容，也有“类似什么玩法”这种语义问题。只用一种检索总会漏，所以我让关键词和向量并行召回，再融合排序；图谱只在需要追关系时补，不让所有问题都付出图谱成本。

## 每道题都用这四步展开

面试官问一个技术点时，先别急着报组件名，可以按下面的顺序说：

1. **遇到什么需求／问题：** 先讲业务现场，以及不解决会造成什么影响。
2. **业界解决方案：** 说明常见做法，以及它适合什么场景、有什么不足。
3. **我的解决方案：** 结合当前项目说明你做了哪些取舍，具体落在哪些模块和状态上。
4. **落地效果：** 说已经验证的工程结果；没有真实线上数据时，明确说评测、本地联调或后台可观测结果，不虚构业务收益。

例如被问“为什么要做 Agent”，可以这样开口：

> 需求不是所有问题都能一次检索解决，有些活动方案还要补资料、拆任务、等审批。业界一般会用工作流或 Agent 编排，但如果所有问题都走 Agent，延迟和成本都会上去。我的做法是把简单问题留在固定检索链路，只有需要判断下一步的复杂任务才进入 LangGraph 状态机，并限制步数、工具次数和预算。这样简单问题速度稳定，复杂任务又能留下状态、产物和审计记录。

## 一、项目总述

### 30 秒版本

> 这是一个给游戏官网和活动团队用的知识协同平台。最开始的问题不是“模型不会回答”，而是资料散在 PRD、设计规范、接口、埋点和测试文档里，大家搜到内容后还要自己判断版本和适用范围。
>
> 我把资料先做版本、权限和来源治理，再用关键词加语义检索找证据。简单问题走快速链路，复杂问题才拆子问题、补联网资料或调用工具。产研运任务还能按产品、设计、研发、测试、运营分阶段生成结构化交付物，并且支持审批、回灌、恢复和审计。

### 2 分钟版本

> 我把系统看成三部分：第一部分是知识供给，负责文档解析、父子切块、版本和权限；第二部分是问答和 Agent，负责 Simple、Auto、Chat Agentic 以及产研运 Task Agentic；第三部分是质量运营，负责 Bad Case、评测、运行审计和监控。
>
> 我比较看重的一点是，不把模型输出直接当答案。检索结果要经过权限、版本和生效时间过滤，回答还要做引用校验。答错以后，用户可以提交 Bad Case，运营审核后进入纠正层或正式知识，再用回归集验证。这样系统不是“问一次答一次”，而是有持续纠错的闭环。

## 二、项目复盘中的 9 个问题

### N1．你们的问答是怎么审计的？

> 我当时发现只记一条“用户问了什么、模型答了什么”不够排障，所以把一次请求拆成 Run、Event 和 Action。Run 看一次完整运行，Event 按顺序记录路由、节点、检索和审批，Action 专门记录工具调用。
>
> 这些记录用 `runId` 关联一次运行，用 `threadId` 关联会话和 Checkpoint。后台可以从运行详情一路看到哪里开始偏离。LangFuse 看模型链路，Prometheus 看服务指标，二者解决的问题不一样。

### N2．这套审计具体解决了什么？

> 它解决的是“模型答错了，但不知道为什么”。比如是文档没入库、版本被过滤了、关键词没命中、上下文太长，还是模型引用不够，都能顺着事件时间线定位。
>
> 对我来说，价值不是多存几张表，而是把排查从“重新问一遍看看”变成“找到第一次出错的位置”。

### N3．为什么 Run、Event、Action、Artifact 要分开？

> 因为它们的查询方式和生命周期不一样。Run 适合看总览，Event 适合按时间回放，Action 需要展开工具输入输出，Artifact 可能很大，不能全塞进事件表。
>
> 所以小的审计摘要留事件，大结果外置成 Artifact，只在事件里留预览和 ID。这样运行中心看得快，真正排查时又能下钻。

### N4．数据分别存在哪里？

> PostgreSQL 是业务事实和审计的主存储，放会话、Run、Event、Action、反馈、任务和 Artifact 元数据。Redis 放短期记忆、Checkpoint、租约和幂等状态。
>
> Milvus 负责语义召回，BM25／Elasticsearch 负责关键词召回，Neo4j 负责关系和多跳补证。不是“所有数据都放向量库”，而是按查询特点分开存。

### N5．异常怎么处理？

> 我没有做一个“所有错误都重试”的总开关，而是先区分错误类型。检索超时就快速失败并使用可用分支，联网或重排失败不阻断主链路，结构化输出失败才在有限次数内重试。
>
> 如果证据不够，宁愿返回待确认或安全降级，也不让模型根据空上下文编一个看起来完整的答案。每种降级都会留下事件，避免把降级结果误认为正常成功。

### N6．任务中断后如何恢复？

> LangGraph 每个关键节点都会把状态写进 Redis Checkpoint，Run 里保留当前节点和事件。恢复时先读最新 Checkpoint，再判断上一个动作能不能安全重放。
>
> 只读检索和已确认结果可以继续；如果是外部写入且结果未知，就先标记 `unknown`，要求人工核验，不能直接再写一次。这是我认为恢复流程里最重要的安全边界。

### N7．项目背景是什么？

> 游戏活动的周期短、版本变化快，产品、设计、前端、后端、测试和运营又各自维护资料。真正麻烦的是同一个问题可能搜到多个版本，大家不知道哪个能用。
>
> 所以项目目标不是做一个聊天框，而是让团队围绕同一份带版本、权限和来源的证据协作，并把需求逐步变成可以评审、开发和验收的交付物。

### N8．方案怎么设计？

> 我先把知识入库和在线问答分开，避免模型链路承担数据治理。入库阶段做解析、质量门禁、父子切块、版本和权限；在线阶段做混合召回、过滤、重排、引用校验和按需 Agent。
>
> 复杂产研任务再使用岗位 DAG，把每个岗位的输出结构化，并在岗位之间做审批和交接。这样普通问答不会被多 Agent 拖慢，复杂任务也不会变成一段不可审查的长文本。

### N9．遇到过什么问题？

> 最大的问题是“功能看起来都有，但链路之间对不上”。比如 Bad Case 提交了却没进入检索，工作流产物生成了却无法审计，Auto 每次又重复检索。
>
> 我的处理方式是先把状态落点和 ID 关系补齐，再补页面和监控。现在可以从反馈、知识状态、查询日志、Run、Artifact 一路追到最终答案；剩下的生产规模和真实业务效果，必须用真实数据继续验收。

## 三、Agent、MCP、RAG 共性题

### A1．为什么用 Agent，不直接写业务流程？

> 能确定步骤的流程我不会用 Agent，比如查一个接口字段，普通检索更快也更稳定。只有当目标比较开放，需要根据证据决定下一步、补资料、调用工具或等待审批时，Agent 才有价值。
>
> 这个项目里，简单问答走固定链路；复杂活动方案才让 Agent 拆问题和组织交付物。

### A2．Agent 的完整运行流程是什么？

> 先装配会话上下文和权限，再判断链路。Agentic 会拆子问题，分别检索，再看证据够不够；不够时才联网或调用只读工具。证据够了以后生成答案，做引用校验和反思，最后写 Query Log 和运行审计。
>
> 每一步都有状态和预算，超过最大步数、工具次数或超时就停止，不把“继续想”当成无限权限。

### A3．是单 Agent 还是多 Agent？

> 两种都有。普通复杂问答是 Chat Agentic 状态机；产研运交付是 Task Agentic，多岗位按依赖协作。
>
> 我没有为了体现“多 Agent”而把所有问题拆给多个角色。只有职责、输入输出和审批边界真正不同，才拆成岗位 Agent；否则协调成本会超过收益。

### A4．Agent 怎么判断意图和选链路？

> 用户可以显式选择 Simple、Auto 或 Agentic。Auto 不只看问题长短，而是先跑一次快速检索，再结合证据充分性和任务复杂度决定是否升级。
>
> 例如“某接口字段是什么”通常停在快速链路；“设计一个活动并输出接口、埋点和测试清单”就会进入 Agentic。路由结果会写入运行事件，便于解释为什么走这条路。

### A5．工具失败怎么重试和兜底？

> 先判断是工具不可用、权限拒绝、超时，还是结果不确定。只读检索可以在剩余预算内切换备用链路；联网和重排失败就用已有本地证据；写入动作如果结果未知，直接停下来人工核验。
>
> 具体的重试不是整条链路无脑重跑，而是节点级处理，并受最大次数、超时和幂等键约束。

### A6．中断时状态怎么保存？

> Checkpoint 保存的是 Agent 的执行状态，比如当前节点、子问题、检索结果、审批状态和工具结果；会话历史和用户长期记忆另有存储。
>
> 恢复时使用同一个 `threadId` 读取最新状态，审批通过就从安全节点继续，而不是重新从头生成。

### A7．怎么避免死循环和重复调用？

> 状态图先限制允许的边，Loop 再限制最大步数和工具次数。Chat Agentic 当前外层有反思重试上限，岗位检索工具每个岗位默认最多调用 1 次。
>
> 对副作用工具再加幂等指纹：已完成就恢复结果，执行中或结果未知就阻断。这样“重试”不会变成重复发奖、重复写文件这类副作用。

### A8．MCP 在项目中做什么？

> MCP 是给 Codex、Claude Code、Trae 这类 AI 编程工具提供项目上下文的入口。编码前，它们可以查询活动模板、组件规范、接口、埋点和测试要求。
>
> MCP 不直接连数据库，也不替代后端权限；它只是标准化发现和调用已有能力，真正的权限、版本和审计仍在 RAG 服务端。

### A9．为什么不用 API 或 SDK？

> 内部前端和服务之间当然继续用 API。MCP 解决的是“多个 AI 客户端都要用这套能力”的问题，统一工具发现和输入输出。
>
> 所以这是边界选择，不是说 MCP 比 API 更高级：单一调用方、强事务或极低延迟场景，直接 API 更合适。

### A10．MCP 工具怎么拆粒度？

> 我按单一意图拆，而且尽量让输入输出可验证。比如 `rag_search` 只返回证据，`rag_ask` 才负责生成回答；工作流上下文和活动列表也分开，避免一个工具承担太多职责。
>
> 工具越大越难审计，工具越碎又会增加调用次数，所以我会根据权限边界和是否需要独立重试来决定粒度。

### A11．MCP 怎么做权限和安全？

> MCP 只把身份上下文带到后端，后端按用户、租户、角色和数据范围做权限判断。知识检索先过滤可访问文档，工具执行前再检查模式、岗位和白名单。
>
> 当前项目有用户级隔离和基础 RBAC，企业 IAM、ABAC、DLP 和凭证中心属于生产接入项，不能把本地能力说成已经完成。

### A12．RAG 完整链路是什么？

> 入库是“解析 → 质量门禁 → 父子切块 → PostgreSQL 保存 → 向量、关键词、Karpathy／Obsidian 和可选图谱索引”。查询是“精确直答门禁 → 关键词和向量并行召回 → RRF 融合 → 权限、版本、生效时间过滤 → Rerank 和上下文组装 → 生成和引用校验”。
>
> 证据不足时才补联网或进入 Agentic；最终还要写 Query Log、LangFuse 和运行事件。核心不是用了多少数据库，而是答案能不能回到有效证据。

### A13．为什么不只用全文检索？

> 活动 ID、接口名和埋点字段要求精确匹配，BM25 很擅长；但“有没有类似抽奖活动”这种问题需要语义理解，向量更合适。
>
> 所以我用混合检索互补，而不是用向量检索替代全文检索。原始全文全部塞给模型还会带来 Token、权限和版本污染。

### A14．文档少还需要 RAG 吗？

> 如果只有几份短文档，直接放上下文可能更简单。这个项目上 RAG 的价值主要来自权限、版本、生效时间、引用和持续更新，不是单纯因为文档数量大。

### A15．召回不准怎么定位？

> 我会按顺序排查：文档是否成功入库、切块是否破坏结构、版本和权限是否误过滤、关键词和向量各自召回了什么、融合和重排有没有丢掉强证据，最后再看上下文预算。
>
> 不会第一反应就是把 TopK 调大，因为那可能只是把更多噪声塞给模型。

### A16．怎么判断答案可信？

> 不看模型自己说“我很有信心”，而看证据。检索先过充分性门禁，事实性回答要能引用片段，生成后再做引用支撑校验；校验不过就抽取式回退或安全降级。
>
> 评测时还要看引用覆盖、拒答正确性、版本和权限是否正确，而不是只看回答像不像人话。

### A17．记忆、Checkpoint、审计分别是什么？

> 记忆解决“用户之前说过什么”，Checkpoint 解决“Agent 执行到哪了”，审计解决“谁在什么时候用什么证据做了什么”。
>
> 当前项目分别用 Redis／Mem0、LangGraph Checkpoint、PostgreSQL Run／Event／Action 来承载，三者不能混成一个大上下文。

### A18．模型超时或输出格式错了怎么办？

> 结构化输出用 Schema 校验，失败时有限重试；模型超时按节点预算处理，不把整个任务无限延长。检索判断器失败时可以依据已有证据和规则降级。
>
> 最终失败要保留证据和失败原因，并明确告诉使用者没有完整成功，不能只返回一段看起来正常的文本。

## 四、可观测、审计与安全

### O1．AI 应用怎么做全链路可观测？

> 我分三层看：HTTP 和服务层看请求、错误和延迟；Agent 层看路由、节点、检索、工具和重试；模型层用 LangFuse 看 Trace、Generation、Token 和成本。
>
> Prometheus 更适合聚合 p50／p95、空召回、工具失败和熔断等指标。LangFuse 不是 Prometheus 的替代品。

### O2．怎么知道一次请求经过了哪些步骤？

> 请求开始就创建 `runId`，所有事件带 `runId`、`threadId` 和顺序号。路由有 `route.selected`，节点有开始／完成事件，工具有调用／结果／失败事件，最终有 Run 终态。
>
> 运行中心按 Run 聚合，LangFuse 按 Trace 观察模型调用，两个视角可以互相定位。

### O3．模型失败从哪里查？

> 先看 Failure Onset，也就是第一条关键失败事件，而不是先猜“模型不稳定”。再看是 Provider 超时、上下文过长、检索为空、Schema 不匹配，还是工具参数不对。
>
> 有了第一失败点，后面的错误很多只是连锁反应，定位会快很多。

### O4．记录哪些日志、指标和状态？

> 日志记录请求 ID、路由、节点、错误和耗时；指标记录调用量、延迟、Token、召回、工具成功率、拒答、重试和成本；状态记录当前节点、Checkpoint、审批和 Artifact。
>
> 密钥、密码和完整敏感 Prompt 不进日志。审计的目标是可定位，不是把所有原文无限复制。

### O5．审计哪些信息？

> 重点是发起人、模式、Prompt 版本、检索配置、证据 ID、工具摘要、权限和审批、幂等结果、终态和耗时。
>
> 大结果放 Artifact，事件只放摘要和定位信息；查询快照优先保存 hash 和长度，减少敏感数据暴露。

### O6．敏感信息怎么处理？

> 当前主要做数据最小化：API Key 只存 hash，工具参数只留预览和 hash，大结果外置，Prompt Injection 在入库和生成前都检测。
>
> 这还不等于完整 DLP。字段级识别、自动脱敏、保留周期和删除请求要接企业安全系统后才能算生产闭环。

### O7．如何控制幻觉？

> 先治理知识来源，再做权限和版本过滤；召回后判断证据是否充分，生成时要求引用，生成后校验引用。支撑不了的内容就标待确认或降级。
>
> Bad Case 不是简单把错误答案塞回 Prompt，而是审核后进入纠正层或正式知识，并通过回归集验证。

### O8．Bad Case 怎么持续优化？

> 用户提交时先保存到 PostgreSQL，运营审核原问题、答案、引用和检索快照。审核通过后，可以留在可撤销的纠正层，也可以核验来源后晋升正式知识。
>
> 勾选回归只代表加入评测集，不直接代表答案立刻生效。这样“知识生效”和“评测用例”不会互相污染。

### O9．知识、Prompt 或模型变了怎么回归？

> 固定一批问题、期望证据和答案约束，同时记录模型、Prompt、知识版本和工具策略。改动后比较召回、排序、引用、拒答、注入防护和 Agent 合法步骤。
>
> 评测报告只能支持发布决策，不能代替真实流量验收；本地测试通过也不能直接说生产质量达标。

## 五、AI 编程方法论

### C1．你如何用 AI 完成需求？

> 我先让 AI 读项目规则、Roadmap 和相关代码，再把需求拆成能验收的小目标。实现过程中限制修改范围，完成后跑类型检查、测试、构建和 Smoke Test。
>
> AI 负责提高实现速度，但需求边界、风险判断和最终验收还是我负责。

### C2．AI 编程和传统编程差别是什么？

> 主要差别是代码生成更快，但错误也更容易被快速放大。它可能引用不存在的 API、沿用旧接口，或者把假设当成事实。
>
> 所以我会把上下文、规则、测试和 Diff Review 做得更严格，而不是把 AI 当自动驾驶。

### C3．怎么保证 AI 代码可维护？

> 先限制技术栈和修改范围，再用类型、Schema、测试和构建验证行为，最后看 Diff 是否越界。对于跨模块改动，还要检查运行状态、权限和失败路径。

### C4．不熟悉的方案怎么验证？

> 我会先查官方文档、SDK 源码和官方示例，逐字段对比参数、请求体、错误语义和生命周期，再做最小 PoC。
>
> 如果连续两轮还在猜，就停止试错，找参考实现或对照工作版本，而不是继续堆 Prompt。

### C5．有没有沉淀项目规则和上下文？

> 有。`CLAUDE.md` 放工程边界和红线，`ROADMAP.md` 放真实进度，架构和功能文档放稳定知识，运行后用 Evidence 记录验证结果。MCP 则把需要给编码 Agent 的上下文提供出来。

### C6．怎么区分 Prompt、上下文和代码问题？

> 先用同一个输入复现。输出结构错，优先查 Prompt 和 Schema；出现不存在的模块或旧接口，查上下文；理解没问题但运行失败，再按普通代码查类型、状态、并发和边界。
>
> 一次只改一个变量，才能知道到底是哪一层修好了。

### C7．个人 AI 项目和商业产品差在哪里？

> 商业产品要面对真实数据、权限、安全、容量、SLA、成本、备份恢复和运营责任。个人项目可以先证明架构和主链路，但不能把模拟数据和本地构建结果包装成线上收益。

### C8．AI 时代开发者最重要的能力是什么？

> 我认为是把开放目标变成可验证任务的能力：知道哪里该自动化，哪里必须设门禁；知道怎么评测，也知道失败发生在数据、检索、模型、工具还是工程层。

## 七、简历关键词的七层追问

### P1．这个概念是什么？

> 先用业务语言解释，再补技术名词。例如 Agent 就是围绕目标维护状态、选择工具并执行多步动作的程序；在这个项目里，LangGraph 用来把这些动作约束成可检查的状态图。

### P2．为什么要用？

> 先说不用它会遇到什么问题。复杂活动需求需要多轮取证、跨岗位交接和失败恢复，一次性 RAG 不够；但简单事实题用 Agent 反而增加延迟，所以我们把两类场景分开。

### P3．具体怎么做？

> 按“输入、核心步骤、状态、输出”讲。比如 Chat Agentic 是问题和记忆进入状态图，拆子问题并检索，证据不足再补工具，最后生成带引用答案；Task Agentic 则产出岗位 Artifact 并经过审批。

### P4．你本人做了什么？

> 只讲我能打开代码、解释取舍和现场复现的部分。比如我可以讲清楚检索链路、Agent 状态、工具执行外壳、运行审计和管理后台；团队协作和个人边界按真实经历说明。

### P5．出错怎么办？

> 不只说“重试”。我会先分类错误，再决定节点级重试、模型降级、备用检索、人工审批或安全停止，同时用事件和幂等控制副作用。

### P6．效果怎么证明？

> 用数据集、基线、指标和运行报告证明。当前可以证明的是本地测试、构建、评测和审计链路；真实线上收益要等真实业务流量和长期数据，不能提前编数字。

### P7．重新做会怎么改？

> 我会优先补真实业务数据、专家评测集、跨实例故障演练和 IAM／DLP，再决定哪些复杂能力值得长期保留。不是 Agent 越多越好，而是每个复杂度都要有业务收益。

## 八、面试现场的三个万能例子

### 例子一：为什么要混合检索？

> 接口字段和活动 ID 要精确，关键词检索更可靠；玩法相似性和自然语言描述又需要语义召回，所以两路并行，最后融合。这样是针对数据特点做取舍，不是为了把组件数量做多。

### 例子二：为什么要做 Bad Case？

> 用户说“答案不对”只是反馈，不能直接拿来当知识。我们先保存问题、答案、引用和检索快照，人工确认正确答案和来源，再进入纠正层或正式知识，最后加入回归集验证。

### 例子三：为什么要做 Checkpoint？

> 多步任务运行几十秒甚至更久，页面刷新或进程中断时不能从第一步重来。Checkpoint 记录当前节点和中间状态，恢复时还要判断副作用是否已发生，未知结果不能盲目重放。

## 九、使用方式

1. 第一次回答只讲业务问题、核心判断和方案，控制在 30～45 秒。
2. 面试官追问时，再补具体模块、状态流、异常处理和代码入口。
3. 重点背 N3、N8、N9、A2、A5、A12、A16、O3、O9，以及上面的三个真实例子。
4. 每道题至少准备一个“当时为什么这样做”的理由，不要只记组件名。
5. 所有个人经历、团队规模、薪资和线上指标都以真实情况为准；没有生产数据时，就讲设计目标、评测方法和本地验证边界。
