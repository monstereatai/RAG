# Agent／RAG 七个难点面试速查卡

更新时间：2026-08-10

## 一句话总纲

我做的不是一个接上大模型的聊天框，而是一套面向游戏官网和活动产研运的协作 Agent 平台：让任务能拆、岗位能协作、知识能检索、结论有证据、过程可恢复、结果可评测、错误能反哺。

## 回答任何技术题的五句话

1. **背景**：业务为什么需要它，原方案出了什么问题。
2. **对比**：我比较了哪几种方案，各自优缺点是什么。
3. **选择**：我最后选什么，为什么适合当前业务，不说“因为流行”。
4. **落地**：讲清数据流、状态、失败处理和关键代码边界。
5. **效果**：用指标、测试和真实边界收尾，不编造收益。

## 七个难点

| 难点             | 核心问题                                                | 我的选择                                                   | 结果怎么说                                                 |
| ---------------- | ------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------- |
| 六岗位协作       | 多角色不是多写六段 Prompt，依赖、并行、审批和恢复才难   | LangGraph 状态图＋固定业务 DAG＋风险审批＋局部重跑         | 单岗位可独立，完整链路为产品→设计／后端并行→前端→测试→运营 |

## 当前闭环口径

除真实业务数据、真实生产流量和线上 SLA 外，七个难点的本地工程闭环均已具备可执行验证：

- 六岗位协作：稳定性回放脚本支持 30 次完整 DAG、串行或并发执行、429 退避和成功／降级分离统计。
- 快慢路径：Simple／Auto／Agentic 的路由、充分性升级和本地 30 样本性能门禁已可执行；性能报告区分 `local` 与 `strict` Profile。
- 检索与切片：结构保护切片、混合召回、RRF、Rerank、降级和本地质量评测已覆盖。
- 分层记忆：短期窗口、结构化摘要、Mem0 和 Redis Checkpointer 双进程共享 Redis 恢复 smoke 已覆盖。
- Agent Evals：任务、工具、步骤、证据、失败降级和稳定性报告均有脚本和门禁。
- Bad Case 飞轮：提交、审核、回灌、撤销索引、自然化回答和三链路回归已通过。
- 可观测与防死循环：Prometheus、Trace、节点耗时、首 Token、工具调用、超时、步数限制、LangFuse 真实 trace／flush／health 已覆盖。
- 运营闭环：Bad Case 长期回归追加历史趋势；查询、回答、反馈、活跃用户、复访用户和反馈覆盖率已有采集接口。真实用户采纳率仍需持续线上流量。

本轮本地门禁结果：六岗位完整 DAG 30／30 次完成，180／180 个岗位模型调用成功，模型降级 0，产物创建 30／30；`local` profile 通过。自动审批场景的审批就绪率为 0 是预期行为，本地非真实业务数据的证据覆盖率只记录观察值（约 50.17％），不冒充真实质量结论。RAG 性能基准为 Simple 30／30、Agentic 30／30，`local` profile 通过；Redis 跨进程恢复、Milvus Bad Case、LangFuse 配置状态和真实 trace smoke 均通过。

## 面试加分工程能力

七个难点之外，面试中高频追问的企业化能力也已有代码落点：

- 权限与安全：文档 ACL、userId 隔离、检索前权限过滤、Prompt Injection 检测、Tool Registry 风险／权限／超时／审计字段。
- 模型网关：`LlmGatewayPolicy` 统一任务路由、主备模型、超时、输出上限和成本预算；业务层通过 `LlmProvider` 访问，不直接绑定厂商 SDK。
- 数据治理：文档版本、生效／失效时间、来源权威、冲突检测、索引回滚和 Bad Case 撤销。
- 运营指标：查询窗口内活跃用户、复访用户、回答率、反馈覆盖率和正向反馈率。

这些是本地代码级能力；真实 IAM、DLP、租户账单、线上灰度、生产告警和用户长期采纳仍按后续条件处理。

## 性能与可观测监控分工

项目采用 LangFuse 与 Prometheus 双层监控：

| 监控层 | 负责内容 |
| --- | --- |
| LangFuse | Trace／Generation、模型和节点耗时、首 Token 延迟、总耗时、Token、成本、Prompt／模型版本、工具调用、重试、降级、Bad Case 和评测关联 |
| Prometheus | QPS、成功率、错误率、P50／P95／P99、并发数、超时、熔断、重试、CPU、内存、Redis、数据库、队列和服务健康 |

LangFuse 负责回答「这一条问答为什么慢、错在哪个节点、用了多少模型资源」；Prometheus 负责回答「服务整体是否稳定、是否达到 SLA、基础设施是否异常」。当前已经验证 LangFuse 真实云端 `trace／generation／flush／health` 上报，以及本地性能基准；生产环境仍需补 Dashboard、告警规则、采样脱敏、长期留存和真实流量 SLA。

## 高频题核心答案

### RAG 召回怎样评测

先把检索和生成分开。检索看 Recall@K、Precision@K、MRR、nDCG、首个正确证据排名、来源覆盖、权限过滤正确率和延迟；生成看事实正确率、证据覆盖率、引用忠实度、拒答正确率。再按中文别名、数字时间、跨文档、多跳、无答案和权限场景分桶，否则平均分会掩盖问题。

### Agent 死循环怎样处理

先限制，再识别，再恢复：限制最大步数、总耗时、工具次数和 token；对连续相同节点、相同工具参数、状态无变化做重复检测；工具超时使用熔断和降级；状态通过 Checkpointer 保存，失败后从节点恢复；最后把轨迹纳入回归集，避免同类循环再次上线。

### Agent、Chatbot、Skill、Tool 的关系

Chatbot 主要是输入到回复；Agent 有目标、状态、决策、工具和停止条件。Tool 是可调用的原子能力，有明确 schema；Skill 是可复用的任务方法，负责何时选什么工具、怎样组合和验收；Agent 根据状态选择 Skill 或 Tool，并对执行结果继续决策。

### 为什么加 Reranker

第一阶段召回追求“不漏”，会混入语义相近但不能回答的问题；Reranker 联合阅读 query 和候选块，做更精细的相关性判断，把真正能支撑答案的证据排到前面。代价是延迟和费用，所以只重排较小候选集，并准备超时降级。

## 不能说错

- 模拟评测 100% 不等于真实业务 100%，只能证明工程路径和门禁成立。
- GraphRAG 不会天然提高所有问题，只适合实体关系、多跳和跨文档场景。
- Reranker 改善排序，不负责弥补第一阶段完全没召回的证据。
- 长期记忆不是保存全部聊天，而是带来源、时间和作用域的可检索事实。
- 多 Agent 不是越多越好；职责、上下文和失败边界清楚时才拆。
- 审批不是每个节点必经，只有指定岗位或达到风险阈值才暂停。
