# 林芮瑭简历大模型面试问题

> 适用方向：Agent 开发工程师、LLM 应用工程师、Agent Infra、LLM 评测与数据工程、多模态应用工程。
>
> 使用方式：先准备 1 分钟项目概述，再按项目逐层回答“做了什么、为什么这样做、如何验证、遇到什么问题”。简历里的指标、仓库贡献和项目职责必须能够提供代码、日志、评测结果或协作者证明。

## 一、面试官对简历的总体判断

这份简历的核心优势不是训练单个多模态模型，而是把大模型能力做成可运行、可恢复、可评测、可扩展的 Agent 系统：

```text
用户任务
  → 意图识别与规划
  → 多 Agent／Sub-agent 协作
  → Tool／MCP 调用
  → Sandbox 执行
  → 上下文选择、压缩和记忆
  → Checkpoint 恢复
  → 轨迹评测与结果交付
```

因此最适合的面试定位是：高级 Agent 开发工程师、LLM 应用架构／平台工程师、Agent Runtime 或 AI Coding 基础设施工程师、LLM 评测与数据工程师、多模态应用工程师。

如果岗位是纯多模态算法训练，需要额外准备视觉编码器、数据集、Loss、训练资源和离线指标，不能只讲 Agent 编排。

## 二、必问的自我介绍和项目总览

### 1. 你主要做的是模型算法，还是 Agent 应用工程？

回答要点：主线是 LLM／Agent 系统工程，负责 Agent Runtime、工具调用、上下文工程、记忆、恢复和评测闭环；同时做了视觉理解、图片检索、图像生成和 UI 生成等多模态应用。如果涉及 SFT／RL，准确表述为训练数据、轨迹生成、筛选、评测和训练基础设施，不要把平台工程夸成底层模型训练。

### 2. 选一个最能代表你的项目，讲清楚完整链路。

按“业务目标和输入输出 → 为什么需要 Agent → Planner／Lead Agent／Sub-agent／Tool／Sandbox 职责 → 上下文选择和压缩 → 失败恢复和交付 → 效果指标”的顺序回答。

### 3. 你在项目中真正负责的边界是什么？

明确架构设计、核心代码、模型／工具接入、评测脚本、部署或运营中的具体责任。准备提交记录、代码目录、设计文档、日志和协作分工。

### 4. 简历里的指标是怎么统计的？

准备统计时间范围、样本量、基线、指标定义、数据来源、去重规则和异常样本处理方式。调用量、通过率、耗时、转化率和成本下降都不能只报结论。

## 三、DeerFlow／Long-Horizon Agent Harness 高频问题

### 5. 为什么采用 Coordinator／Planner／Researcher／Coder／Reporter 多 Agent？

按职责拆分上下文和工具权限，使研究、编码、执行、汇总可以独立失败和恢复；代价是通信和模型调用增加，所以简单任务应走单 Agent 或 Fast Path。只有独立角色状态、工具权限、输入输出契约和可观测事件同时存在，才算多 Agent，而不是多次调用模型。

### 6. Lead Agent 和 Planner 的区别是什么？

Planner 生成任务计划和依赖关系；Lead Agent 在运行时根据观察结果做下一步决策、分派子任务、处理失败和汇总结果。计划不是固定脚本，但必须受最大步数和权限约束。

### 7. 多 Agent 如何避免无限循环？

准备说明最大步数、最大工具调用次数、单任务超时、总预算、重复动作检测、状态机终态、失败降级和人工接管，并说出项目实际配置。

### 8. Sub-agent 如何隔离上下文？

每个 Sub-agent 使用独立 Thread 或 Sandbox 上下文；Lead Agent 只接收任务结果摘要、证据引用和失败原因；大结果通过文件、Artifact 或结构化 handoff 传递，不把所有原始对话全文拼给主 Agent。

### 9. 什么时候应该拆 Sub-agent，什么时候不应该拆？

任务边界清晰、工具或权限不同、可以并行、结果可结构化验证时拆分。任务短、上下文强耦合、通信成本高或没有独立验收标准时不拆分。

### 10. Agent Teams Harness 解决了什么问题？

重点讲单 Lead Agent 统一决策、Sub-agent 并发规则、任务超时、结果汇总、动态 system prompt 和交接消息，而不是只复述“Agent Teams”。

## 四、Context Engineering、记忆和 Checkpoint

### 11. 为什么强调 Context Engineering？

长流程 Agent 的瓶颈通常不是模型不会回答，而是上下文过长、证据混杂、历史污染、工具输出过大和任务状态丢失。Context Engineering 决定什么信息、何时、以什么结构进入模型。

### 12. Write、Select、Compress、Isolate 分别是什么？

- Write：把中间结果写入文件、Artifact 或结构化状态；
- Select：按任务、Token 预算和相关性选择上下文；
- Compress：摘要历史和工具结果，保留目标、结论、证据和未完成事项；
- Isolate：按 Thread、Agent、任务和权限隔离上下文。

### 13. 长期记忆和短期记忆如何配合？

短期记忆保存当前 Thread 的最近对话、任务状态和临时摘要；长期记忆保存稳定偏好和可复用经验。长期记忆不能覆盖当前任务事实，注入前要做相关性、权限和时效判断；过长时先压缩短期上下文，再按需检索长期记忆。

### 14. Checkpoint 和 Memory 有什么区别？

Checkpoint 关注“从哪里继续执行”，保存当前节点、工具结果、任务列表和待执行步骤；Memory 关注“模型需要知道什么”，为后续任务提供上下文信息。

### 15. Agent 中断后如何恢复？

保存节点状态和输入输出，生成幂等键，恢复后检查已完成动作，避免重复写入；写入结果未知时进入补偿或人工确认，不能简单整条链路重跑。

### 16. 如何控制上下文压缩造成的信息损失？

压缩模板至少保留用户目标、已完成任务、关键证据 ID、工具结论、失败原因、待办事项、约束和交付格式；通过压缩前后 Token、关键信息召回率和任务成功率做回归。

## 五、工具、MCP、Sandbox 和安全

### 17. Tool Registry 为什么必要？

统一登记工具名称、来源、风险、权限、超时、适用模式、审批要求和降级策略。工具调用必须经过注册、参数校验、权限判断、审计和结果回写，不能由 Agent 任意拼接函数。

### 18. MCP 解决什么问题？

MCP 把知识检索、代码上下文和外部能力以标准工具协议提供给 Codex、Claude Code、Trae 等客户端，减少重复集成；服务端仍需要权限、工具白名单、超时和敏感数据过滤。

### 19. 模型生成的代码为什么不能直接执行？

代码可能包含破坏性命令、网络外传、密钥读取或资源消耗，应在 Sandbox／容器中限制目录、网络、CPU、内存和时间；生产环境还需要镜像隔离、审计和人工审批。

### 20. 工具失败如何处理？

参数错误返回模型修正，临时网络错误有限重试，模型超时降级，权限错误立即阻断，写入结果未知时进入补偿或人工确认。每类错误都要有次数上限、日志和最终状态。

### 21. Prompt Injection 如何防护？

把外部文档、网页和工具结果当作不可信数据；系统指令、用户任务和检索内容分层；工具侧再次做权限和参数校验；禁止模型仅凭文档内容提升权限或执行写操作。

## 六、SFT／RL 轨迹和评测问题

### 22. SFT／RL 数据从哪里来？

说明轨迹来源、任务类型、成功标准、人工或模型筛选、去重和脱敏方式，以及如何避免错误轨迹进入训练集。

### 23. Scaffold 是什么？为什么需要多个 Scaffold？

Scaffold 是 Agent 的执行脚手架或策略框架，规定任务分解、工具使用、错误处理和交付方式。多个 Scaffold 可以产生不同策略的轨迹，降低单一行为模式过拟合，但必须用统一评测标准筛选。

### 24. Multi-Model Relay 如何工作？

不同模型按规划、代码生成、审查和总结等能力接力；交接只传结构化任务、证据和结果，处理好模型输出格式不兼容和失败回退。

### 25. LLM-as-Judge 有什么问题？

可能存在评审偏差、位置偏差、长度偏差、模型自偏好和评分不稳定。可用细化 Rubric、多模型投票、规则检查、人工抽检、隐藏候选顺序和真实任务指标对照缓解。

### 26. Rubric 怎么设计？

把质量拆成任务完成度、工具调用正确率、证据使用、代码可运行性、Patch 质量、事实准确性、成本和耗时等可观察维度，每个维度定义等级、反例和阈值。

### 27. Failure Onset 是什么？

定位第一次出现错误决策的步骤，例如证据误读、工具选择错误、参数错误或错误恢复，而不是只看最终失败。保留 onset 之前的高质量轨迹，减少失败片段污染训练数据。

### 28. 为什么不能只看最终成功率？

还要看有效工具调用率、重复调用率、平均步数、恢复成功率、成本、延迟、引用准确率和人工接管率；长流程 Agent 还要评估中间产物和失败定位准确率。

### 29. Benchmark 结果如何证明没有数据泄漏？

准备数据隔离、版本固定、测试集不可见、运行环境一致、Patch 来源、失败样本复核和重复实验，不能只报通过率提升。

## 七、多模态内容重点问题

### 30. 你的多模态能力属于模型训练还是模型应用？

如果主要是 GPT-4o Vision、图像检索、Prompt、扩散模型 API、UI 生成和结果评估，应定位为多模态应用工程。只有实际参与视觉编码器、数据、Loss、训练和模型指标，才适合表述为多模态算法训练。

### 31. 参考图到角色卡片的完整链路是什么？

```text
用户意图
  → 检索关键词生成
  → 图片搜索与筛选
  → Vision 提取构图、风格、角色和颜色特征
  → 结构化 Prompt
  → 图像生成
  → 设计维度评估
  → 失败重试或返回角色卡片
```

### 32. 图像检索和图像生成如何协作？

检索提供风格、构图和参考证据，生成基于结构化条件产出新图；同时要防止直接复制受版权保护的素材，记录参考来源和授权范围。

### 33. 如果面试官追问模型细节怎么办？

如实区分调用了什么模型、自己实现了什么编排、是否改过模型参数、是否训练过 LoRA、是否有离线评测。不能把“接入 Vision API”回答成“训练了视觉语言模型”。

### 34. UI 生成中的 JSON／XML／UIDL 为什么必要？

结构化中间表示可以把自然语言意图、页面组件、事件绑定和流程节点分开，便于 Schema 校验、增量更新、回滚和局部 Patch，比直接生成 HTML 更容易验证。

## 八、工程指标和线上稳定性

### 35. 如何降低 Agent 延迟和成本？

简单问题走 Fast Path；无依赖子任务并行；缓存稳定检索和工具结果；按任务选择模型；限制上下文、步数、工具次数和输出长度；失败时局部重试；记录 Token、模型、耗时和工具成本。

### 36. 如何设计重试？

按错误类型做节点级重试，结合超时、指数退避、幂等键和预算控制。权限错误和参数错误直接返回；写入操作出现未知结果时不能盲目再次执行。

### 37. 如何监控 Agent？

LangFuse 记录 Trace、Generation、Span、Prompt、模型、Token 和耗时；Prometheus 记录请求量、错误率、P95 延迟、首 Token 延迟、空召回、工具失败、重试和预算超限；通过 runId／traceId 关联。

### 38. 如何定位一次 Agent 失败？

从 Run 和 Trace 进入，依次检查路由、上下文快照、检索证据、工具输入输出、模型响应、重试原因、Checkpoint 和最终状态，重点定位第一次错误决策。

## 九、简历可信度和反向追问

### 39. 你写“项目 Owner”，具体哪部分代码是你写的？

准备仓库目录、关键类、提交记录、架构决策和一次线上问题案例，明确自己亲自落地的模块。

### 40. 调用量、使用率和转化率如何证明？

说明日志来源、统计周期、分母、去重规则和基线。若是内部试点或估算，应明确标注，不能包装成大规模线上数据。

### 41. 为什么同时写前端、Agent、模型和 Infra？

前端是交互入口，Agent 是任务编排，模型是能力提供方，Infra 负责执行、恢复和评测；跨层经验能帮助完整交付，但要说明最深的技术主线。

### 42. 如果重新设计，你会改什么？

统一 Run／Trace／Artifact 标识；更早建立离线评测集；将工具权限和成本预算前置；增加真实用户采纳率和人工接管率；把多模态算法指标与 Agent 产品指标分开统计。

## 十一、最终面试定位

推荐表达：

> 我主要做 LLM Agent 系统和 AI 应用基础设施，重点解决长流程任务中的多 Agent 协作、工具调用、上下文控制、记忆与 Checkpoint 恢复、轨迹评测和成本治理；同时有视觉理解、图像检索、图像生成和 UI 生成等多模态应用落地经验。

不建议直接表达为“我主要负责多模态大模型训练”，除非能够完整回答数据集、训练代码、Loss、GPU 资源、模型结构和离线指标。
