## 项目二：诗悦网络｜游戏官网活动营销 Agentic RAG 知识协同平台

### 项目简介

面向游戏活动、营销 H5／小程序活动页及 PC／H5 官网业务的 AI 知识协同平台。沉淀活动类型、营销玩法、页面模块、前端工程规范、接口与埋点规范、地区适配及上线验收清单等知识，帮助产品、UI、前端和测试将模糊需求快速整理为可评审、可开发、可验收的方案初稿。

### 技术栈

NestJS、React、LangGraph.js、Milvus、Elasticsearch／BM25、Redis、Neo4j、MCP、LangFuse、Prometheus。

### 团队规模

研发 4 人，其中前端 2 人。

### 负责内容

1. 建立活动营销知识模型与资料治理规范，统一活动类型、玩法、页面模块、接口、埋点、地区版本、风险项和验收清单等元数据，支持活动模板、官网规范、前端经验、Obsidian 笔记、URL 文章及官方文档持续入库。

2. 建设知识协同工作台，提供文档管理、智能问答、活动方案初稿生成、引用查看、知识版本管理、权限过滤和运营后台能力，输出页面结构、接口清单、埋点清单、风险项及测试验收 Checklist。

3. 建设质量运营闭环，覆盖 Bad Case 提交、审核、回灌、回归验证、评测集管理及调用链路审计，使错误回答能够沉淀为可检索、可撤销、可验证的修正知识。

4. 建设 MCP 上下文服务，为 Codex、Claude Code、Trae 等编码工具提供活动模板、组件规范、埋点规则和地区适配经验的检索能力，减少研发前人工整理上下文的成本。

5. 建设运行观测与验证能力，接入 LangFuse Trace／Generation、Prometheus 指标、链路追踪、稳定性与成本评估脚本，为检索质量、模型调用和工作流执行提供可观测依据。

### 技术难点

1. **多角色协作如何避免 Agent 自由发挥失控**：活动方案涉及产品、设计、前端、后端、测试和运营，多 Agent 并行时容易出现职责重叠、跳步骤、上下文串扰。基于 LangGraph 将协作过程建模为固定状态机：产品澄清后，设计与后端并行，再依次进入前端、测试和运营；每个节点只读取所属输入并输出结构化 Artifact（阶段产物），通过证据门禁、人工审批节点和最大步数限制保证流程可控、可局部重跑。

2. **简单问答与复杂活动方案不能共用一条昂贵链路**：固定走 Agentic 会导致简单问题延迟和成本过高，固定走检索问答又无法完成复杂方案拆解。设计 Simple／Auto／Agentic 分层路由：Simple 走快速检索与生成；Auto 先走快速路径，再由 Sufficiency Gate（回答充分性门禁）根据检索命中、引用完整度、置信度和任务复杂度决定是否升级；Agentic 专门处理跨角色、多步骤的活动方案任务，并设置查询、工具调用、重试和反思预算。

3. **活动知识既要精确命中，又要补齐上下游业务关系**：单纯向量检索容易漏掉活动 ID、埋点事件、接口字段、版本号等精确术语，也难以补齐「玩法—页面—接口—埋点—风险—地区」之间的关联。采用结构化切块保留标题层级、表格、代码块和来源位置；结合 Milvus 语义召回、Elasticsearch／BM25 精确召回、Neo4j 图谱扩展、RRF 融合、Rerank 重排和相邻片段补全，在上下文预算内输出带引用的证据链。

4. **AI 输出如何做到可验证，而不是“看起来合理”**：活动规则、奖励比例和地区口径不能由模型自行补全。将 RAG 质量与 Agent 执行质量拆开评估：前者关注召回率、引用正确性、忠实度、拒答和版本／权限过滤；后者关注任务完成度、方案覆盖率、工具成功率、步骤正确率及人工接管情况。评测采用规则断言优先、LLM Judge（模型裁判）辅助的方式，并通过回归集阻止质量退化。

5. **Bad Case 如何从反馈记录变成真正生效的知识闭环**：普通反馈只会停留在后台，无法影响后续回答。将 Bad Case 设计为受治理的独立知识源：用户提交错误类型、修正答案和回归开关；运营审核通过后写入独立向量集合并保留原始检索快照；后续 Simple、Auto、Agentic 查询都会先检索已审核修正知识，再由 Correction Gate（修正答案门禁）结合当前官方证据生成自然回答。撤销审核时同步取消索引，避免错误修正长期污染知识库。

6. **长流程状态、断线与多实例下如何恢复执行**：Agentic 工作流包含多个节点和工具调用，仅依赖前端会话无法支撑中断恢复。采用 Redis Checkpointer 保存线程级状态，区分短期上下文、结构化摘要和长期记忆，并按用户／会话隔离、设置 TTL；SSE 断线后可恢复事件状态，节点失败可从最近检查点继续，避免整条活动方案链路重新执行。

7. **如何定位慢、空召回、工具失败和循环调用问题**：多 Agent 的问题通常发生在具体节点，而不是单一接口。为模型调用、检索、工具调用和工作流节点建立 LangFuse Trace／Span，并通过 Prometheus 采集请求量、耗时、首 Token 延迟、空召回率、工具成功率、重试次数、循环上限命中率等指标；同时对最大步骤、最大工具调用数和超时进行保护，使异常链路可定位、可告警、可降级。

### 本地验证说明

已完成 Simple／Auto／Agentic 三条链路、Bad Case 回灌与回归、Redis Checkpointer、LangFuse／Prometheus 埋点及多角色工作流的本地验证。真实线上活动数据、生产 SLA、多副本容灾和企业级 IAM／DLP 属于后续生产接入范围。
