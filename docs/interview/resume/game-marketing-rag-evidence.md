## 结论

这个项目不再只按“企业通用知识库”讲，而是可以收敛成：

```text
面向游戏活动、营销 H5、小程序活动页和 PC/H5 官网业务线的 Agentic RAG 知识协同平台。
```

它适合支撑主人过往的业务经历：节假日活动、周年庆、版本活动、新角色宣发、改版活动、充值营销、抽奖营销、小程序/H5 活动页、PC/H5 游戏官网，以及台湾服、东南亚服、国内和海外多地区交付。

需要注意：简历正文不要主动写项目周期或“半年/6 个月”，避免面试官先关注时间长度。更稳但有力度的说法是：结合当前业务链路完成 RAG/Agent/MCP 框架、知识结构和评测方法建设，后续随着活动上线、问题复盘、组件规范和埋点反馈持续扩充。只有面试官追问时间线时，再解释这是诗悦网络任职期间从 0 到 1 推进的试点建设。

## 评测维度

专项评测不是看“回答像不像”，而是检查游戏营销业务线真正关心的点：

| 维度 | 检查内容 |
|---|---|
| 玩法识别准确率 | 能否识别抽奖、充值返利、微信分享、兑换码、回流、周年庆等玩法 |
| 必要模块覆盖率 | 是否覆盖页面结构、接口、素材、状态机、FAQ、客服入口 |
| 风险项召回率 | 是否召回概率公示、库存、到账时间、防刷、隐私、投诉风险 |
| 地区适配覆盖率 | 是否识别台湾服、东南亚服、海外的语言、支付、时区、CDN、客服差异 |
| 埋点覆盖率 | 是否覆盖曝光、点击、分享、抽奖、充值、领奖、支付跳转等事件 |
| 引用命中率 | 关键建议是否有来源文档支撑 |
| 拒答正确率 | 对具体概率、返利比例、预算、活动时间等无依据问题是否标记待确认 |

## 面试主线

### 30 秒版本

```text
我把 RAG 项目收敛到了自己更熟悉的游戏活动和官网营销业务线。重点不是包装成多年数据验证的成熟平台，而是从 0 到 1 搭建活动类型、营销玩法、页面模块、接口模式、埋点规范、地区适配和风险检查的知识框架。系统通过 Hybrid Search、GraphRAG、Agentic Workflow 和 MCP，把业务需求转成可评审、可编码、可验收的技术方案初稿。
```

### 2 分钟版本

```text
这个项目最早是企业级 RAG 知识库，后面我把它和自己的游戏业务经历结合起来，定位成游戏活动 / 营销 / 官网业务线的知识协同平台。

原因是游戏活动每次具体规则都不一样，比如奖励数值、概率、时间、预算都要由产品运营确认，不能让 RAG 瞎编。但底层模式是稳定的，比如周年庆会场、新角色抽奖、充值返利、微信分享裂变、兑换码、回流活动、PC/H5 官网、活动专题页，它们都会涉及页面模块、素材需求、接口、状态机、埋点、地区适配、风险检查和测试验收。

数据量还没到能证明长期线上效果的程度，所以我没有强调线上准确率，而是强调从 0 到 1 的框架和方法：RAG 负责从活动模板、官网工程规范、埋点规范、地区适配经验里找证据；GraphRAG 负责把活动类型、玩法、页面模块、接口、埋点和风险关系补全；Agentic Workflow 负责把这些证据组织成技术方案、checklist 和编码上下文；MCP 让 Codex 这类 AI Coding 工具在写代码前自动调用 RAG。后续每次活动上线、测试遗漏、线上问题和复盘都会回流到知识库和评测集。
```

## MCP 在这个方向里的价值

AI Coding 工具不知道公司内部组件、活动模板、埋点命名、接口约定和地区适配经验。MCP 的作用是让 Agent 写代码前先查知识库：

```text
Codex / Claude Code / Trae
  -> rag_context / rag_search / rag_game_plan
  -> 活动模板、页面模块、组件规范、埋点规范、接口约定、地区风险
  -> 生成代码计划或直接编码
```

典型例子：

```text
帮我实现东南亚服新角色抽奖 H5。
先调用 rag_context 获取内部组件、抽奖玩法、埋点、接口和地区适配上下文；
必要时调用 rag_graph_query 补齐玩法/页面/埋点/风险关系；
再按当前仓库风格实现页面并运行验证。
```

## 多 Agent 在这个方向里的职责

| Agent | 在游戏营销场景中的职责 |
|---|---|
| researcher | 查活动模板、官网规范、埋点规范、地区适配、历史复盘 |
| analyst | 把模糊需求拆成玩法、页面、接口、状态机、风险和验收项 |
| writer | 生成技术方案、checklist、FAQ、编码上下文 |
| critic | 检查是否缺概率公示、库存、客服入口、埋点、地区适配、拒答边界 |
| editor | 合并输出，去重，统一成业务负责人和前端都能看懂的版本 |

面试时不要说它已经完全替代人做决策。更稳的说法是：多 Agent 用来做复杂方案整理和遗漏项检查，最终规则、预算、概率、法务口径仍由业务负责人确认。

## 不能硬说的边界

| 不能硬说 | 正确说法 |
|---|---|
| 已接入大量真实游戏私有数据 | 当前处于早期建设阶段，已有脱敏/仿真业务模板和部分业务链路口径；真实落地需要继续接历史活动复盘、官网项目文档、埋点规范 |
| RAG 自动生成最终活动规则 | RAG 只生成方案初稿和检查清单，具体奖励、概率、预算由产品运营法务确认 |
| 已有线上长期准确率 | 当前有本地专项评测集和脚手架，线上准确率需要更多真实活动数据、用户反馈和时间验证 |
| 多 Agent 已完全自治 | 当前是工程化编排和质量检查，后续还可补 step-level trace 和人审反馈 |

## 推荐下一步

1. 用真实脱敏活动复盘替换当前模板文档。
2. 把真实组件文档、埋点规范、接口规范导入知识库。
3. 扩展 50-100 条真实“毒题”：具体奖励、概率、预算、地区差异、接口异常、埋点遗漏、上线事故。
4. 把专项评测接到 `eval-rag-project` 的 live 模式，统计 simple/auto/agentic 的准确率、引用率和拒答率。
