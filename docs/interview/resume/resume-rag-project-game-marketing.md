# 游戏官网营销 RAG 项目简历写法

更新时间：2026-08-12

## 项目定位

面向游戏活动、营销投放、小程序/H5 和游戏官网的 Agentic RAG 知识库与方案生成平台。

当前公开资料验收已覆盖 PC 端候选 Top50 和页游候选 Top50：实际抓取 127 个官网／活动／运营／营销／社区公开页面，形成 108 份唯一目标文档并完成 RAG、Karpathy、Obsidian 索引；真实活动数据和长期线上效果仍需业务环境继续验证。

这个版本比“企业级知识库”更贴合我的业务经历：我之前做游戏节假日活动、周年庆、版本活动、角色活动、改版活动、充值营销、抽奖营销、新角色宣发、小程序/H5 活动页，以及 PC/H5 游戏官网，业务覆盖台湾服、东南亚服、国内和海外。真实痛点不是记住某一次活动的具体规则，而是快速理解活动类型、营销玩法、地区差异、官网落地模式和前端交付约束，并把需求转成可执行的技术方案。

## 业务边界

不把系统定位成“某个游戏活动规则库”，因为每个游戏、每个版本、每次活动规则都会变。系统沉淀的是更稳定、更通用的知识：

- 活动类型模式：节假日、周年庆、版本更新、新角色上线、角色返场、资料片、改版、预约、回流、拉新、留存。
- 营销玩法模式：充值返利、累充、首充、礼包、抽奖、签到、微信分享裂变、兑换码、排行榜、邀请助力、问卷、UGC 投稿。
- 官网落地模式：PC 官网、H5 官网、小程序活动页、活动专题页、首页 Hero、角色展示、新闻公告、活动规则、预约下载、礼包领取、视频 PV、FAQ、客服入口、适龄提示。
- 多地区交付模式：台湾服、东南亚服、国内和海外版本的语言、渠道、支付、客服、合规提示、素材尺寸、CDN 和访问链路差异。
- 前端工程规范：SSR/SEO、首屏性能、图片压缩、CDN 缓存、响应式适配、微信内置浏览器兼容、小程序限制、分享 SDK、埋点规范。
- 活动工程模板：页面结构、接口清单、状态机、埋点清单、测试验收、灰度发布、异常补偿和客服 FAQ。
- 风险检查模板：抽奖概率公示、奖励库存、奖励到账时间、渠道限制、隐私授权、未成年人提示、投诉风险。

## 业务线用户与用途

这个知识库主要不是给玩家直接用的，也不是面向全公司的通用协作平台，而是面向游戏活动 / 营销 / 官网这条业务线。它不是按岗位散开做工具，而是围绕一条业务流打通知识：

```text
活动想法 -> 玩法方案 -> 页面方案 -> 素材需求 -> 技术拆解 -> 埋点验收 -> 上线检查 -> 复盘沉淀
```

核心价值是让业务负责人能统一掌握活动 / 营销 / 官网这条业务线的知识上下文，并让需求策划侧、体验设计侧、交付验证侧围绕同一套知识协同，把模糊活动想法整理成可评审、可落地、可验收、可复盘的方案。

### 三类核心角色

| 类型 | 包含角色 | 用途 |
|------|----------|------|
| 业务负责人 | 活动/营销/官网业务 owner、项目负责人、前端负责人 | 统筹活动目标、玩法方案、资源协同、技术风险、上线节奏和复盘沉淀；快速判断需求是否完整、方案是否可落地、上线风险是否可控。 |
| 需求策划侧 | 产品、运营、市场、发行、本地化、需求方 | 提出活动目标、玩法、地区、渠道、奖励和宣发节奏；查询同类玩法模板，拆活动流程，发现规则缺口，生成需求说明、FAQ、地区差异和风险检查初稿。 |
| 体验设计侧 | UI、视觉、交互、内容 | 把活动玩法转成页面、视觉、文案和素材需求；理解页面结构、模块优先级、素材尺寸、PC/H5/小程序适配、多语言文案长度和地区素材差异。 |
| 交付验证侧 | 前端、后端、测试、数据 | 负责技术落地、接口、埋点、验收和效果追踪；生成页面结构、状态机、接口清单、埋点清单、测试 checklist、上线风险检查和复盘问题。 |

### 系统串联的业务链路

| 阶段 | 系统串联的内容 |
|------|----------------|
| 活动想法 | 活动目标、目标地区、目标用户、玩法类型、宣发节奏 |
| 玩法方案 | 预约、抽奖、充值、分享裂变、签到、兑换码、排行榜、回流等玩法模板 |
| 页面方案 | PC 官网、H5、小程序、活动专题页、角色页、会场页、FAQ 页 |
| 素材需求 | KV、角色图、PV、缩略图、分享图、多语言素材、地区素材尺寸 |
| 技术拆解 | 页面模块、状态机、接口清单、性能预算、兼容适配 |
| 埋点验收 | 曝光、点击、预约、下载、分享、抽奖、充值、领取、支付跳转等事件 |
| 上线检查 | 地区适配、渠道参数、CDN、客服入口、合规提示、灰度和回滚 |
| 复盘沉淀 | 活动效果、问题记录、遗漏项、复用模板、下次优化建议 |

### 一句话总结

```text
这是一个面向游戏活动 / 营销 / 官网业务线的 Agentic RAG 知识与方案协同系统，用来打通活动玩法、官网页面、素材需求、技术拆解、埋点验收、地区适配和复盘沉淀，帮助业务负责人统筹业务链路，并让需求策划侧、体验设计侧和交付验证侧在同一套知识上下文里协同。
```

## 典型使用场景

### 接到活动需求

```text
东南亚服新角色抽奖活动 H5，需要怎么拆技术方案？
```

系统输出活动玩法理解、页面模块、接口清单、埋点清单、地区适配项、风险点和测试验收 checklist。

### 产品 / 运营需求还比较粗

```text
周年庆活动通常需要哪些页面模块和风险检查？
```

系统输出会场页结构、登录礼/累计任务/抽奖/礼包模块、奖励发放链路、概率/库存/到账时间说明、FAQ 和客服准备项。

### 前端准备技术评审

```text
微信分享裂变活动前端要注意什么？
```

系统输出微信 JS-SDK 配置、分享标题/缩略图、渠道参数、邀请关系、防重复领取、埋点事件、微信内置浏览器兼容和测试清单。

### 多地区上线前

```text
台湾服和东南亚服活动页上线前要检查哪些差异？
```

系统输出繁体/多语言字段、支付方式、CDN 和访问链路、客服入口、社媒分享、合规提示、素材尺寸、时区和活动时间展示检查项。

### 测试和上线验收

```text
充值返利活动上线前怎么验收？
```

系统输出支付链路、订单状态、奖励发放、异常补偿、重复提交、埋点校验、多端兼容和回滚预案。

## 项目描述

基于 NestJS + React + LangGraph.js + Milvus + Elasticsearch + Redis + Neo4j 构建游戏活动与官网营销 RAG 知识库，聚合节假日/周年庆/版本/角色/改版活动方法论、充值/抽奖/新角色营销玩法、小程序/H5/PC 官网落地模式、前端工程规范、埋点规范、地区差异和风险检查清单。系统通过 Hybrid Search、GraphRAG 和 Agentic Workflow，帮助游戏活动 / 营销 / 官网业务线打通活动玩法、页面方案、素材需求、技术拆解、埋点验收、地区适配和复盘沉淀。

```text
项目一：【诗悦网络】游戏活动与官网营销 Agentic RAG 知识协同平台

项目简介：
面向公司游戏活动、营销 H5、小程序活动页和 PC/H5 官网业务线的 AI 知识协同平台。项目从 0 到 1 完成试点建设，围绕活动类型、营销玩法、官网页面模块、前端工程规范、埋点规范、地区适配和上线验收清单搭建知识框架、检索问答链路、方案生成流程和评测方法，帮助业务负责人、产品/UI/测试/前端把模糊活动需求整理成可评审、可编码、可验收的技术方案初稿。考虑到真实活动数据和长期效果仍在积累，系统设计为可随活动上线、问题复盘和埋点反馈持续扩充。

技术栈：
NestJS + React + LangGraph.js + Milvus + Elasticsearch/BM25 + Redis + Neo4j + MCP

团队规模：
研发4人，前端2人；本人担任前端组长，负责方案设计、技术选型、架构拆分和核心链路落地

负责内容：
1. 负责整体方案设计、技术选型、架构拆分和任务推进，完成 RAG 后端、Admin 管理后台、MCP 工具服务和评测脚本等核心链路的从 0 到 1 建设。
2. 设计知识入库链路，支持活动模板、官网规范、前端经验、Obsidian 笔记、URL 文章和官方文档统一进入 RAG/Karpathy/Obsidian 索引层，先以业务模板、试点样本和官网/活动交付经验建立可持续扩充的知识结构。
3. 设计 Hybrid Search 检索链路，结合 Milvus 向量召回、Elasticsearch/BM25 关键词召回、RRF 融合、Rerank 和引用校验，提升活动模板、页面模块、埋点规范和地区适配经验的检索可靠性。
4. 基于 LangGraph 设计 simple / auto / agentic 分层问答流程，简单问题走快速检索，复杂活动需求升级为 Agentic Workflow，输出页面结构、接口清单、埋点清单、风险检查和测试验收 checklist。
5. 引入 GraphRAG 建模活动类型、营销玩法、页面模块、接口、埋点、地区版本和风险项之间的关系，用于补齐技术方案中的遗漏项。
6. 通过 MCP 暴露 rag_context、rag_search、rag_game_plan 等工具，让 Codex/Claude Code/Trae 在编码前自动获取内部组件、活动模板、埋点规范和地区适配上下文。
7. 建设 Admin 管理后台和评测体系，覆盖文档治理、问答运营、GraphOps 节点编辑、权限/审计、Prompt Injection 检测和业务回归。

难点：
1. 活动规则变化快，不能把 RAG 做成某一次活动的规则库：将知识沉淀对象从“具体奖励数值/概率/预算”收敛为更稳定的活动类型、营销玩法、页面模块、接口模式、埋点规范、地区适配和验收清单；对缺少依据的具体规则引导系统拒答或标记待确认。
2. 单纯向量检索容易漏掉业务链路关系：引入 Hybrid Search + GraphRAG，向量检索负责找相似模板，BM25/ES 负责精确词召回，图谱负责补齐活动玩法、页面模块、接口、埋点、风险项和地区差异之间的关系。
3. AI 输出需要可信可追溯：通过 Rerank、引用校验、低相关拒答、Prompt Injection 检测和评测集回归，避免模型把没有来源的活动规则、奖励比例、地区口径编成确定结论。
4. 复杂活动需求很难直接转成前端任务：基于 LangGraph 将需求拆成活动理解、页面结构、素材需求、接口清单、埋点方案、风险检查、地区适配和验收 checklist，降低产品/UI/测试/前端之间的理解成本。
5. AI Coding 工具不了解内部业务和组件规范：通过 MCP 将 RAG 能力暴露给 Codex/Claude Code/Trae，让 Agent 写代码前先检索活动模板、组件规范、埋点规则和地区适配经验，减少人工复制上下文和模型凭空猜测。
6. 质量不能只靠主观体验：在真实数据积累不足的阶段，先补充项目级仿真实业务评测、游戏活动/官网营销专项评测样本、Prompt Injection 检测和企业 readiness 检查，建立可持续评测方法；真实效果后续通过活动数据、上线复盘和用户反馈继续验证。
```

## CLI 在这条业务线里的作用

CLI 不是给业务方日常点页面用的主入口，而是给业务负责人、前端负责人和自动化脚本使用的工程入口。它适合把知识库结果变成结构化上下文，方便后续继续编码、生成计划、跑评测和做图谱查询。

但如果目标是让 Codex 自动查内部资料并直接编码，**优先使用已落地的 `tools/rag-mcp-server`，而不是让人手动跑 CLI 再复制粘贴**。CLI 保留价值：本地调试、人工查询、脚本调用、CI、评测和批量导入。

## MCP / CLI / 插件路线

### 结论

```text
Codex 自动编码主入口：MCP（已实现 tools/rag-mcp-server）
人工查询和脚本入口：CLI
后续按平台封装：Codex 插件 / 其他客户端适配
```

MCP 是通用能力接口，插件是某个平台的分发/封装方式。当前已新增通用 `tools/rag-mcp-server`，让 Codex、Trae、Claude Code、Cursor 等 AI 编程工具都能稳定调用 RAG 能力；等工具设计稳定后，再按平台需要封装 Codex 插件或其他客户端适配。

### 推荐集成架构

```text
Codex / Trae / Claude Code / Cursor
  -> tools/rag-mcp-server
  -> RAG API
  -> Milvus + ES/BM25 + GraphRAG + Obsidian
  -> 内部组件、活动模板、埋点规范、接口约定、地区适配、复盘知识
```

命名上不使用 `rag-codex-mcp`，而使用更通用的 `rag-mcp-server`，避免把能力绑定到 Codex 单一平台。

### 和 CLI 的关系

CLI 仍然保留，不是废弃：

```text
CLI 给人和脚本用。
MCP 给 Agent / AI 编程工具用。
```

更准确地说，CLI 是命令行网关，面向人、脚本、CI、批量导入和批量评测；MCP 是 Agent 工具接口，面向 Codex、Claude Code、Trae、Cursor 等 AI 编程工具，让它们在任务执行过程中自动查内部知识、组件 API、埋点规范、接口约定和图谱关系。

| 场景 | 推荐入口 |
|------|----------|
| Codex / Trae / Claude Code / Cursor 自动查资料并编码 | MCP |
| 人工临时查内部组件/规范 | CLI |
| 批量导入文件、活动模板、组件文档 | CLI |
| CI 或脚本里跑评测/导出上下文 | CLI |
| 调试 MCP 工具返回是否正确 | CLI |
| 后续按平台增强安装体验 | 插件或客户端适配 |

### AI 编程工具使用方式

后续接入 MCP 后，可以直接对 Codex、Trae、Claude Code 或 Cursor 说：

```text
帮我实现东南亚服新角色抽奖 H5 页面。
先调用 rag_context 获取内部组件、活动玩法、埋点、接口和地区适配上下文；
必要时调用 rag_search 查询内部组件用法，调用 rag_graph_query 补齐玩法/页面/埋点/风险关系；
然后基于当前仓库实现代码并运行验证。
```

AI 编程工具不需要人工粘贴 CLI 输出，而是自己调用 MCP 工具拿上下文。

### MCP 什么时候会被调用

MCP 的定位不是给普通用户点页面用，而是在 AI 编程工具执行任务时自动调用项目能力。可以这样理解：

```text
人直接用系统：Admin / Web / CLI
Agent 自动用系统：MCP
```

| 场景 | 调用 MCP 工具 |
|------|---------------|
| 写代码前需要查内部组件、业务规则、项目规范 | `rag_search` / `rag_context` |
| Codex 要根据知识库生成开发计划 | `rag_context` |
| 需要先理解活动/营销/官网业务需求 | `rag_game_plan` |
| 生成上线检查清单 | `rag_game_checklist` |
| 生成埋点方案 | `rag_game_tracking` |
| 检查台湾服/东南亚服/海外差异 | `rag_game_region_check` |
| 查询活动、页面、接口、埋点之间的关系 | `rag_graph_query` |
| 直接问知识库一个问题 | `rag_ask` |
| 跑复杂方案生成或多 Agent 分析 | `rag_agent_pipeline` |
| 确认 RAG 后端是否正常 | `rag_health` |

按开发流程看，MCP 通常这样被触发：

```text
1. 接到需求
   -> rag_context / rag_game_plan
   先拿业务背景、历史模板、技术约束。

2. 准备写代码
   -> rag_search
   查内部组件怎么用、接口规范、埋点规范。

3. 方案不清楚
   -> rag_agent_pipeline
   让 researcher / analyst / writer / critic / editor 做一轮复杂方案整理。

4. 涉及图谱关系
   -> rag_graph_query
   查玩法、页面模块、接口、埋点、风险之间的关系。

5. 准备上线
   -> rag_game_checklist / rag_game_region_check
   生成验收和多地区检查清单。

6. 编码过程中遇到不确定问题
   -> rag_ask
   直接问知识库。
```

面试时可以这样说：

```text
MCP 主要在 AI Coding 或 Agent 执行任务时被调用。比如 Codex 写一个活动 H5 页面前，会先通过 MCP 调用 RAG 检索内部组件、活动模板、埋点规范和地区适配经验，再基于这些上下文生成代码或技术方案。这样避免人工复制粘贴 CLI 输出，也避免模型凭空猜内部系统怎么用。
```

边界也要说清楚：

```text
MCP 不是替代 RAG 后端，也不是替代 Admin 后台。它只是 Agent 调用项目能力的协议入口。
```

### MCP 本地接入方式

```json
{
  "mcpServers": {
    "rag": {
      "command": "node",
      "args": [
        "/Users/monster/Documents/GitHub/code/RAG/tools/rag-mcp-server/dist/src/server.js"
      ],
      "env": {
        "RAG_BASE_URL": "http://localhost:3000/api/v1"
      }
    }
  }
}
```

长期使用时，MCP 不应该依赖 Admin 登录 JWT，因为登录 token 默认 7 天有效期。当前更推荐使用 Admin 后台生成的长期 API Key：

```text
系统管理 -> 系统配置 -> 长期 MCP / API Key
```

生成后的 key 只展示一次，服务端只保存 hash，可以吊销；Codex MCP 使用 `RAG_MCP_API_KEY` 访问 RAG 后端。配置优先级是 `RAG_MCP_BASE_URL/RAG_MCP_API_KEY`、`RAG_MCP_TOKEN`、`RAG_MCP_USERNAME/RAG_MCP_PASSWORD` 自动登录、`RAG_BASE_URL/RAG_API_KEY/RAG_TOKEN`、`~/.config/rag-cli/config.json`、默认 `http://localhost:3000/api/v1`。本地开发可以用自动登录兜底，面试时要强调生产化入口是长期 API Key，而不是长期复用登录 JWT。

## GraphRAG 建模

GraphRAG 不用建成复杂业务中台，核心是把“活动玩法”和“前端落地”之间的关系说清楚。

### 实体类型

| 实体 | 示例 |
|------|------|
| `ActivityType` | 周年庆、节假日、新角色、版本更新、回流活动 |
| `Playbook` | 抽奖、充值返利、微信分享、签到、兑换码 |
| `PageModule` | Hero、角色展示、活动规则、礼包领取、FAQ |
| `Platform` | 小程序、H5、PC 官网、移动官网 |
| `Region` | 国内、台湾服、东南亚服、海外 |
| `TrackingEvent` | page_view、click_reserve、share_success、draw_result、pay_success |
| `ApiContract` | 活动状态、用户资格、抽奖、领奖、订单、渠道参数 |
| `RiskItem` | 概率公示、库存不足、防刷、隐私授权、未成年人提示 |
| `Checklist` | 联调、埋点验收、兼容性、性能、灰度、回滚 |

### 关系类型

```text
ActivityType -> uses -> Playbook
Playbook -> requires -> PageModule
PageModule -> emits -> TrackingEvent
PageModule -> calls -> ApiContract
Playbook -> has_risk -> RiskItem
Region -> adapts -> PageModule / ApiContract / RiskItem
Platform -> constrains -> PageModule / ApiContract
Checklist -> verifies -> PageModule / TrackingEvent / ApiContract / RiskItem
```

### 面试展开例子

用户问“东南亚服新角色抽奖活动 H5 怎么做技术方案”，GraphRAG 可以从 `ActivityType=新角色` 找到 `Playbook=抽奖/充值/分享`，再关联到角色展示、奖池、概率公示、支付渠道、社媒分享、地区语言、CDN、埋点事件和验收 checklist。向量检索负责找相似模板，图谱负责补齐关系链和遗漏项。

## 业务评测口径

不要只用通用 RAG 指标，还要加游戏营销场景自己的评测口径。

| 指标 | 说明 |
|------|------|
| 玩法识别准确率 | 能否从需求中识别出预约、抽奖、充值、分享、回流等玩法 |
| 必要模块覆盖率 | 方案是否覆盖页面模块、接口、埋点、风险、验收 |
| 风险项召回率 | 是否召回概率公示、库存、到账时间、防刷、隐私等风险 |
| 地区适配覆盖率 | 是否识别台湾服/东南亚服/海外的语言、支付、渠道、CDN、客服差异 |
| 引用命中率 | 输出的每个关键建议是否能回链到玩法模板、规范或 checklist |
| 拒答正确率 | 对具体奖励数值、概率、预算、法务口径等无依据问题是否拒答 |
| 方案可用率 | 人工评审方案是否能作为技术评审初稿 |

可以在面试里说：

```text
通用指标我看 Recall、MRR、Faithfulness、AnswerRelevancy；业务指标我更关注玩法识别、必要模块覆盖、风险项召回、地区适配覆盖和拒答正确率。因为这个项目的价值不是替运营拍板，而是让研发快速形成靠谱的技术方案初稿。
```

## 需求到前端落地点

这个项目最能体现价值的地方，不是“问答”，而是帮助需求侧把活动想法转成前端可执行、测试可验收的方案：

- **页面结构**：PC 官网、H5 官网、小程序活动页、专题页、会场页、角色页、预约页。
- **状态机**：未开始、预约中、活动中、已结束、领奖中、库存不足、资格不符、发奖失败。
- **接口清单**：活动状态、用户资格、奖池、抽奖、领奖、订单、分享关系、渠道参数。
- **埋点方案**：页面曝光、按钮点击、预约、下载、分享、抽奖、充值、领取、跳转支付。
- **性能预算**：首屏资源、图片压缩、懒加载、CDN、PV 视频加载、LCP/CLS、弱网兜底。
- **兼容适配**：微信内置浏览器、小程序限制、iOS/Android 差异、PC/H5 响应式、多语言文案长度。
- **上线验收**：接口联调、埋点校验、跨地区访问、灰度发布、回滚方案、客服 FAQ。

面试时可以强调：RAG 负责找经验，Agent 负责把经验整理成方案，前端负责人负责判断方案是否能落地。

## 简历四条负责内容怎么说

面试不要逐条念简历，按“我负责四块”来说。先给 30 秒版本，面试官追哪块再展开。

### 30 秒版本

```text
这个项目我主要负责四块：第一是整体架构，包括 RAG 后端、Admin（管理端）后台、MCP（模型上下文协议）工具服务和评测脚本；第二是知识入库和检索链路，包括 Direct Answer Gate（精确直答门禁）、统一 Hybrid Search（混合检索）和 GraphRAG（图检索增强生成）；第三是 Agentic Workflow（智能体工作流），把复杂活动需求拆成方案、接口、埋点、风险和验收 checklist（检查清单）；第四是质量和工具化，包括引用校验、低相关拒答、评测回归、MCP 接入 Codex／Claude Code 这类 AI Coding（人工智能辅助编码）工具。
```

### 1 分钟版本

```text
我在这个项目里不是只做一个页面或者一个接口，主要负责从架构到核心链路落地。

第一块是整体架构，包括 NestJS RAG 后端、React Admin 管理后台、MCP 工具服务和评测脚本，保证系统能被管理、被评测，也能给 AI 编程工具调用。

第二块是知识和检索链路。资料进来后会并发构建关键词、向量、图谱和 Obsidian 编译知识；Simple 与 Auto 先精确直答，未命中后执行统一 Hybrid Search，复杂问题再按需补充 GraphRAG。Karpathy 本地知识只负责受治理直答和降级，不是独立在线链路。

第三块是问答编排。简单查询走 simple，系统判断证据不足时进入 auto，复杂活动需求走 agentic，通过 LangGraph 拆成页面方案、接口清单、埋点方案、风险检查和验收 checklist。

第四块是质量和工具化。因为活动规则不能瞎编，所以加了引用校验、低相关拒答、Prompt Injection 检测和评测集回归；同时通过 MCP 把 RAG 能力接给 Codex / Claude Code，让编码前能自动拿到内部上下文。
```

### 被问“你具体负责什么”

```text
我负责的是方案设计、技术选型、架构拆分和核心链路落地。具体包括后端 RAG 管线、Admin 运营能力、MCP 工具服务、知识入库、检索路由、Agentic Workflow，以及评测和可信输出机制。
```

### 被问“为什么要有 Admin”

```text
因为 RAG 不是只做一个聊天接口，后续需要运营知识库、看文档状态、看问答效果、管理图谱节点、检查评测结果和问题记录。Admin 的作用是把 RAG 做成可运营系统，而不是只能开发人员调接口。
```

### 被问“MCP 有什么用”

```text
MCP 是给 AI Coding 工具用的。比如 Codex / Claude Code 写代码前，可以通过 MCP 调用 rag_search、rag_context、rag_game_plan 这些工具，先拿到内部组件规范、活动模板、埋点规则和地区适配经验，再基于这些上下文写代码，避免人工复制资料，也减少模型凭空猜。
```

### 被问“simple / auto / agentic 怎么分”

```text
simple 适合明确知识查询，先精确直答，未命中后执行统一 Hybrid RAG，不进入多步 Agentic。
auto 共用精确直答和 Hybrid Fast Path，再按证据充分性与复杂度决定轻量回答或升级。
agentic 适合复杂活动方案，会通过 LangGraph 拆任务、查资料、补接口埋点和风险项，最后生成结构化方案。
```

### 一句话记忆

```text
我负责的是 RAG 从资料入库、检索召回、Agent 编排、可信输出，到 Admin 运营和 MCP 赋能 AI Coding 的完整闭环。
```

### ProcessOn AI 应用图怎么用

ProcessOn「AI 应用」思维导图适合当作 Agent / RAG 面试补课地图，不适合逐条背到简历里。面试时只取和本项目强相关的 6 条主线：

```text
1. RAG 主链路：入库、切片、Embedding、召回、Rerank、生成、引用校验。
2. 分层路由：Direct Answer Gate（精确直答门禁）、统一 Hybrid Fast Path（混合快速路径）与按需 Agentic。
3. Hybrid Search：Milvus 向量召回 + BM25/ES 精确召回 + RRF + Rerank。
4. GraphRAG：用图谱补齐活动玩法、页面、接口、埋点、风险项之间的关系。
5. Agentic Workflow：复杂需求拆成方案、接口、埋点、风险和验收 checklist。
6. MCP：让 Codex / Claude Code / Trae 写代码前自动拿业务和工程上下文。
```

## 重难点与结果短回答

面试时每个点控制在 3 句话：问题是什么，为什么这么做，结果是什么。不要按简历原文长段背。

### 1. 业务知识变化快

```text
这个项目最大的问题是活动规则变化很快，比如奖励、概率、预算每次都不一样，不能把 RAG 做成某一次活动的规则库。
所以我把沉淀对象从具体数值收敛到更稳定的业务结构，比如活动类型、玩法模式、页面模块、接口模式、埋点规范、地区适配和验收清单。
这样新活动进来时，系统不是直接套旧规则，而是帮助产品、UI、测试、前端快速生成一份可评审的方案框架。
```

### 2. 单一检索链路不适合所有问题

```text
这个项目不是所有问题都走复杂链路，我做了分层路由。
简单知识查询先过 Direct Answer Gate，未命中后统一执行关键词、向量与 Obsidian 混合召回，在低延迟和低成本之外保证证据完整性。
复杂方案类问题再进入 Hybrid Search + GraphRAG，用向量找相似模板，BM25/ES 做精确召回，图谱补齐玩法、页面、接口、埋点和风险项之间的关系。
```

### 3. AI 输出必须可追溯

```text
活动规则、地区口径、奖励比例这些不能让模型凭空猜，所以我在生成前后都加了控制。
检索后会做 Rerank 和低相关判断，生成时要求带引用，生成后再做 citation gate 和 Prompt Injection 检测。
如果证据不足，系统会拒答或提示需要人工确认，而不是强行给一个确定答案。
```

### 4. 复杂需求难直接转代码

```text
活动需求通常不是一句话能开发的，里面会包含玩法、页面、素材、接口、埋点、适配和测试验收。
所以复杂需求我没有直接丢给模型回答，而是通过 Agentic Workflow 拆成几个阶段：需求理解、页面结构、接口清单、埋点方案、风险检查和验收 checklist。
最后输出的是一份产品、UI、测试、前端都能看的结构化方案，前端再基于这份方案拆任务和编码。
```

### 总回答

```text
这个 RAG 项目不是单纯做知识问答，而是围绕游戏活动和官网业务，把不稳定的活动规则沉淀成稳定的玩法、页面、接口、埋点和验收知识；检索上先过 Direct Answer Gate，未命中后统一执行 Hybrid Search（混合检索），Auto 根据证据和复杂度按需用 GraphRAG（图检索增强生成）补关系；生成上用引用校验、低相关拒答和 Prompt Injection（提示注入）检测控制幻觉，复杂需求再通过 Agentic Workflow（智能体工作流）拆成可评审、可开发、可验收的方案。
```

## 面试追问回答

### 活动规则每次都变，为什么还适合 RAG？

```text
我不把具体规则当作长期知识沉淀，因为奖励数值、概率、预算、活动时间每次都会变。RAG 沉淀的是更稳定的活动类型、营销玩法、页面模块、接口模式、埋点规范、风险检查和地区适配经验。具体规则由产品和运营确认，系统只辅助研发理解业务和生成技术方案初稿。
```

### 入职时间短，数据量不多怎么办？

```text
我不会把这个项目说成已经被大量线上数据长期验证。更合适的说法是从 0 到 1 做试点建设：把活动类型、营销玩法、页面模块、埋点规范、地区适配和风险 checklist 结构化起来，先用业务模板、脱敏样本和试点数据验证检索、引用、拒答和方案生成链路。后续每次活动上线、问题复盘、埋点反馈和测试遗漏都会回流到知识库和评测集里。如果面试官追问时间线，再说明项目发生在诗悦网络任职期间。
```

### GraphRAG 在这里有什么必要？

```text
向量检索能找到相似玩法，但不一定能补齐关系。比如抽奖活动会关联奖池、概率公示、抽奖接口、中奖记录、发奖链路、防刷、客服 FAQ、埋点事件和地区支付差异。GraphRAG 可以把这些关系补出来，避免方案漏掉关键模块。
```

### 这个项目和普通知识库有什么区别？

```text
普通知识库偏问答，这个项目更偏方案生成。它会把营销玩法、官网模块、接口、埋点、风险和验收清单组合起来，输出研发能拿去评审的技术方案初稿。核心价值是减少业务理解成本和方案遗漏，而不是替业务最终决策。
```

## 面试边界

```text
这个项目不是替运营生成最终活动规则，也不会宣称已经有大量真实数据长期验证。它解决的是业务负责人统筹活动 / 营销 / 官网业务线时的知识框架建设、业务理解、玩法复用、地区适配和技术方案生成问题。最终奖励规则、概率、预算、渠道策略、地区发行策略和法务口径仍由产品、运营、发行、法务确认；系统效果需要随着后续活动上线和复盘数据持续验证。
```

## 不建议写法

不要写：

```text
基于 RAG 自动生成游戏活动规则。
```

原因：

```text
这个说法风险太高，也不符合真实业务。活动规则强依赖游戏、版本、预算、渠道和法务，RAG 更适合沉淀通用玩法模板、官网工程规范和方案检查清单。
```
