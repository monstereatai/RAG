# BOSS 20K＋AI Agent 岗位要求与面试指南

更新时间：2026-09-10

## 先说结论

20K＋的 AI Agent／AI 应用开发岗位，招聘方要的不是“会调大模型的人”，而是能把模型做成稳定业务系统的人。核心考察分为四层：

1. 能做出可信 RAG：资料能入库、能检索、能引用、能治理。
2. 能编排 Agent：能让模型规划、调用工具、恢复失败任务，并控制成本和风险。
3. 能做全栈工程：有后端服务、前端交互、数据库、权限、异步任务、接口集成与部署排障能力。
4. 能证明效果：有评测、观测、Bad Case 回流、成本／延迟控制，而不是只演示一次能回答。

对主人当前项目而言，主干要求已经能覆盖。面试时的正确定位是：**高级 AI 应用全栈／Agent 全栈工程师，优势在企业 RAG、可控工作流和运营治理；不包装成模型训练、GPU 推理基础设施或真实生产合规负责人。**

### 掌握程度不要混淆

| 等级 | 面试表现 | 例子 |
|---|---|---|
| 了解 | 能解释概念和适用场景 | 知道 RRF 是多个召回列表的融合方式 |

## 四、面试指南：高频问题的可讲答案

以下每题均按“背景／问题 → 主流方案 → 我的选择 → 效果与边界”组织。回答时先说结论，再用项目细节证明，不要从定义开始背。

### 1．你这个 RAG 为什么不只做向量检索？

**背景／问题：** 游戏活动、接口字段、活动 ID、埋点事件名这类信息要求精确命中；只用向量检索容易把语义相近但字段不同的内容找回来。另一方面，业务人员的自然语言问法又不能只靠关键词。

**主流方案：**

- 只用向量检索：搭建快，但精确名词和版本规则容易错。
- 只用 BM25：字段准确，但不理解同义表达和业务语义。
- 混合检索：向量负责语义，关键词负责精确词，再融合和重排。

**我的选择：** 并行执行 Milvus 语义召回、ES／BM25 关键词召回；涉及“玩法—页面—接口—埋点—地区”关系的问题，再由 Neo4j 补关系证据。随后 RRF 融合、去重、父子块补全、Rerank 重排，最后做权限、版本、有效期与引用门禁。

**效果与边界：** 这让活动名称、接口字段等能精确找到，同时保留自然语言问题的召回能力。它不是“召回越多越好”，而是用 Rerank 和引用门禁控制噪声。真实线上命中率仍要用业务题库持续量化。

### 2．Simple、Auto、Agentic 为什么要分层？

**背景／问题：** 如果所有问题都走 Agent，简单问题也会经历规划、工具调用和多轮判断，慢且贵；如果所有问题都直答，复杂问题又缺证据和步骤控制。

**主流方案：**

- 统一 Chatbot：实现简单，复杂任务能力弱。
- 全量 Agent：展示很炫，但成本、延迟和不确定性高。
- 分层路由：简单问题走快路径，只有复杂问题升级。

**我的选择：** Simple 先检查经过治理的 Karpathy／Obsidian 编译知识，命中且满足权限、版本、来源和覆盖度时直接组织回答；否则进行混合 RAG，并在证据不足时联网补证。Auto 先走低成本判断，再根据任务复杂度、证据充分性、引用覆盖度决定是否升级。Agentic 再分为 Chat Agentic 和 Task Agentic：前者解决复杂问答，后者解决 PRD 到多岗位交付物的长任务。

**效果与边界：** 低风险常见问题不被重链路拖慢；复杂问题才获得规划和工具能力。路由阈值不能写死，需要结合问答日志和评测集调整。

### 3．你如何设计一个可控 Agent，而不是让模型无限循环？

**背景／问题：** 模型会重复搜索、重复调用工具，甚至把失败结果继续放大。企业任务还涉及审批和副作用，不能让模型自由决定所有动作。

**主流方案：**

- ReAct：边思考边调用工具，灵活但容易漂移。
- Plan-and-Execute：先拆计划再执行，长任务更可控。
- 状态机／DAG：节点和转移条件明确，最适合业务流程与审计。

**我的选择：** 对问答采用受预算控制的 Agent Loop；对产研运任务采用 LangGraph 状态图，把产品、设计、前端、后端、测试、运营定义为有明确输入／输出的节点。每一步写入状态和 Artifact，限制最大步骤、工具预算、重试次数和超时；质量不足时只局部重跑，涉及发布或高风险动作必须人工审批。

**效果与边界：** 复杂任务可恢复、可审计，也能定位是哪一阶段失败。它不是多个 Agent 自由聊天，而是可控的多角色工作流；这比“自治程度”更符合企业交付场景。

### 4．Agent 工具调用怎样保证安全和可靠？

**背景／问题：** Function Calling 的风险不在“能不能调”，而在模型可能选错工具、参数不合法、外部服务超时，或执行具有副作用的动作。

**主流方案：** 将工具当成后端能力，而不是让模型直接访问系统；在工具层加入 Schema 校验、权限、超时、重试、幂等、审计和人工确认。

**我的选择：** 使用 Tool Registry 管理工具的用途、风险等级、所需权限、超时、降级策略和审计要求；通过 MCP 接入外部能力，但只暴露经过注册的工具。读操作可自动执行；写操作、外部发布、代码落盘等需要审批。工具失败先节点级重试，达到上限则切备用路径或返回明确的不可执行原因。

**效果与边界：** 模型只是提出调用意图，实际执行仍由服务端控制。当前是本地工具治理和审计基础，真实企业系统还要对接 IAM、审批流和业务 API 的幂等约束。

### 5．RAG 如何避免过期知识和错误纠正内容污染正式知识？

**背景／问题：** 业务规则会变；用户反馈也不一定正确。把新文档或 Bad Case 直接覆盖旧向量，会造成不可追溯和误召回。

**主流方案：** 文档版本化、有效期、权限过滤、旧版本保留；纠正信息先审后用；用独立纠正层或双层知识做受控晋升。

**我的选择：** 正式知识与审核后的纠正知识分层管理。文档有来源、版本、权限、状态、有效期与索引状态；新版本生效后旧版本标记为 deprecated 而不是直接删除。Bad Case 先进入 PostgreSQL 审核，审核通过才转为可检索纠正知识；检索统一执行版本、权限、时间和来源过滤。

**效果与边界：** 回答可以追溯到哪个版本和来源，发现纠错不正确也能撤销，不会直接毁掉正式知识。真实业务还需要结合制度发布流程和长期数据保留策略。

### 6．上下文太长时，你怎样保证模型不忘记早期关键事实？

**背景／问题：** 把完整聊天历史直接塞给模型会超 Token、变慢且引入噪声；只保留最近几轮又会遗忘早期约束。

**主流方案：** 最近窗口＋滚动摘要＋长期记忆；必要时对会话历史做语义检索补充。

**我的选择：** PostgreSQL 保存完整会话作为事实底座；Redis 维护近期消息窗口用于低延迟追问；超过窗口或 Token 预算后，将可复用事实压缩为摘要并保存；Mem0 保存跨会话偏好和稳定事实。当前问题进入模型前，组合“近期窗口＋摘要＋必要的相关旧问答”，并给检索证据预留 Token 预算。

**效果与边界：** 既保留连续对话体验，又避免上下文无限膨胀。摘要本身可能丢细节，所以不能替代原始会话；有争议时仍以 PostgreSQL 原文和正式知识为准。

### 7．Bad Case 是什么？为什么它不是一个反馈表？

**背景／问题：** 单纯收集“回答不好”没有改进价值。要知道错在检索、引用、提示词、模型、工具还是业务资料缺失，并且修完后要防止复发。

**主流方案：** 反馈分类、保留请求与检索快照、人工审核、修正答案或资料补充、回归测试。

**我的选择：** 用户提交 Bad Case 时保存问题、错误类型、期望答案、检索快照、引用和 Query Log 关联；运营后台审核后可选择补资料、写修正答案或调整用例。通过的纠正知识受治理后进入可检索层，同时自动加入回归评测集；撤销后让对应纠正知识失效。

**效果与边界：** 把一次投诉变成可定位、可修复、可回归的质量资产。它不能代替真实人工标注体系，但对中小团队是可落地的质量闭环。

### 8．你如何评估 Agent 或 RAG 的效果？

**背景／问题：** “回答看起来不错”无法作为上线标准；Agent 还会出现工具失败、循环、耗时高但最终答案勉强正确等问题。

**主流方案：** 离线题集评测＋线上观测＋Bad Case 回归。RAG 看正确性、引用、拒答和召回；Agent 额外看任务成功率、步骤成功率、工具成功率、重试和成本。

**我的选择：** 建立固定评测集和游戏营销专项回归；在回答侧记录引用覆盖、空召回和拒答；在 Agent 侧记录节点耗时、工具成功、重试、最大循环命中和任务产物状态。LangFuse 用于查看单次 Trace／Generation，Prometheus 观察整体延迟、错误率和服务指标。

**效果与边界：** 新知识、Prompt、模型或检索参数变动后都能回归，避免“修一个问题坏一批问题”。当前评测以本地／模拟业务数据为主，真实业务效果仍需持续积累真实问答与标准答案。

### 9．为什么还要做管理后台，直接给业务一个聊天框不行吗？

**背景／问题：** 企业 AI 的问题不是“有没有回答”，而是资料谁能看、答案为什么这样、哪条链路失败、反馈如何修、工作流交付物如何审批。

**主流方案：** 将知识、问答、反馈、评测、运行、工具与权限运营化，而不是把它们藏在日志里。

**我的选择：** 后台分为文档／版本治理、智能问答、Bad Case 审核、Agent 运行中心、Artifact 审计、插件与工具治理、定时任务、图谱搜索与调用链路等入口。业务人员可以提问或提交反馈；运营人员审核、补料、回归；研发人员定位 Trace、工具和节点问题。

**效果与边界：** AI 系统从 Demo 变成可协作维护的产品。后台已经覆盖本地项目闭环；真实组织的权限体系、告警值班和跨系统工单需接企业环境。

### 10．如果让你接入一个新的企业业务系统，你会怎么做？

**背景／问题：** 新系统通常有不稳定接口、字段口径、权限、审计和写操作风险。直接把 API 暴露给模型不可控。

**我的选择：**

1. 与业务确认可被 Agent 增强的 SOP、成功标准、人工兜底和禁止动作。
2. 将业务 API 封装为小而明确的工具，定义输入输出 Schema、权限、限流、超时、幂等键和审计字段。
3. 先以只读查询工具和沙箱数据接入，写操作必须审批。
4. 为每个工具建立成功／失败样本与回归测试，再接入 Tool Registry／MCP。
5. 用灰度流量观察工具成功率、人工接管率、耗时和业务结果后再扩大范围。

**效果与边界：** 这是从“模型会回答”升级到“模型能参与业务流程”的安全路径。项目已具备工具、MCP、审批和审计基础，但真实 API 契约必须跟具体公司共同设计。

## 五、面试时的项目开场版本

> 我做的是一个面向游戏活动和官网营销业务的 AI 应用与多 Agent 全栈平台。核心不是做聊天框，而是把业务知识、复杂需求和交付流程做成可治理闭环：资料通过版本、权限、生命周期进入 RAG；简单问题优先走低延迟知识直答，复杂问题才升级为 Agent；产研运工作流会输出页面 Schema、接口、埋点和验收清单，并支持审批、驳回补料和局部重跑。上线质量方面，我做了 Bad Case 回灌、回归评测、LangFuse Trace 和 Prometheus 指标。我的定位是 AI 应用工程和 Agent 工程，重点是把模型能力变成稳定、可追踪、可运营的业务系统。

## 六、回答时避免的五个坑

1. 不说“多 Agent 就是多个模型互相聊天”，要说职责、状态、输入输出与审批怎么定义。
2. 不说“RAG 就是向量数据库”，要说检索、治理、引用和评测如何配合。
3. 不说“接了 LangFuse 就可观测”，要说看哪些指标、如何定位问题、如何回归。
4. 不说“已经生产可用”，要区分本地工程闭环与真实生产 SLA／IAM／DLP／业务 API。
5. 不背概念。每个技术点都要落到一个具体问题、一个方案取舍和一个可验证结果。

## 七、与当前项目的复习顺序

1. 先讲项目开场版本，再练习 Simple／Auto／Agentic 路由。
2. 练混合检索、版本权限、Bad Case、记忆四题，它们最能体现 RAG 深度。
3. 再练 Agent 工具、工作流、恢复与审批，体现 Agent 工程能力。
4. 最后练评测、LangFuse／Prometheus、后台运营与生产边界，体现高级工程化能力。
