## 一、LLM、Prompt 与模型路由

### 1．模型输出不稳定，你怎么让它产出可被程序消费的结果？

**来源：** S1、S3、S8（多轮决策、业务系统集成、复杂应用架构）。

**怎么答：** 不把自然语言直接当接口返回值。优先让模型按 JSON Schema 输出，服务端再做 Zod 校验；字段缺失或类型错误时做一次修复重试，仍失败就走保底结构。我的工作流 Artifact、页面 Schema、接口和埋点清单都是这样落地的。结果是下游节点接收结构化字段而不是解析一段 Markdown；边界是模型不能替代业务规则校验。

### 2．Prompt 写得越长越好吗？

**来源：** S1、S2、S5（上下文工程、复杂 Agent、业务落地）。

**怎么答：** 不好。Prompt 的目标是让模型在有限上下文里拿到正确约束和证据，而不是塞全部资料。我会固定系统规则、动态注入已过滤的检索证据和必要记忆，并给证据、工具结果、历史消息分别留 Token 预算。长历史先摘要，原始会话仍保留在 PostgreSQL 用于追溯。

### 3．什么时候选择大模型，什么时候选择小模型或规则？

**来源：** S3、S5、S7（AI 应用工程化、成本和效率）。

**怎么答：** 确定性校验用规则，例如权限、版本、Schema、参数格式；意图分类、简单改写可用低成本模型；复杂方案生成和跨资料推理才用能力更强的模型。项目中 Simple／Auto／Agentic 就是把这个选择固化为路由，而不是每次请求都用最贵模型。

### 4．模型超时或限流时，用户体验怎么保证？

**来源：** S3、S6、S8（稳定运行、高可用、执行引擎）。

**怎么答：** 先设置单节点超时和有限次数重试；失败后按错误类型降级，例如向量检索降级到 BM25，Rerank 失败使用融合排序，复杂 Agent 无法执行则回退为已有证据的回答。SSE 会实时告诉用户当前处于检索、生成还是降级，不让前端一直空等。

### 5．如何防止 Prompt Injection？

**来源：** S4、S8（智能体安全、高权限工具场景）。

**怎么答：** 把检索文本、网页内容和用户上传资料都视为不可信输入。检索片段先做注入模式检测和高风险内容剔除；系统提示明确规定资料只能作为证据，不能改变系统规则或触发工具；高风险工具还需要服务端权限判断和人工审批。效果是降低“文档里写一句忽略规则”带偏 Agent 的风险，但不能宣称能防住所有攻击。

### 6．怎样做模型选型？

**来源：** S3、S5（主流模型集成、AI 应用从 0 到 1）。

**怎么答：** 先按业务任务拆维度：事实问答看引用准确率，方案生成看结构完整性，工具调用看参数成功率，再比较延迟、价格、上下文长度与私有化要求。项目通过 LLM Gateway 配置主备模型、超时和输出预算；不能只看某次 Demo 的主观效果。

## 二、RAG 与知识治理

### 7．文档为什么要切块？块多大合适？

**来源：** S1、S3、S5、S7（RAG、企业知识库、复杂信息处理）。

**怎么答：** 模型和向量检索不适合直接处理整篇文档；切块能把问题对应到局部证据。块太大噪声多，太小上下文断裂。我的做法是父子切块：子块用于精准召回，父块补足上下文；具体大小按文档类型和评测结果调，不说一个固定数字适合所有资料。

### 8．为什么要做父子块，不只存普通 Chunk？

**来源：** S3、S5（企业 RAG、复杂生成需求）。

**怎么答：** 用户的问题往往命中一段接口字段，但回答还需要同一章节的前置条件。子块可以提高命中精度，父块保留规则边界和上下文。检索后先用子块找位置，再回填父块，避免“只找到了半句话就下结论”。

### 9．向量检索和 BM25 分别解决什么问题？

**来源：** S3、S5、S7（RAG、知识库、检索增强）。

**怎么答：** 向量检索擅长同义表达和语义相近；BM25 擅长活动 ID、接口路径、字段名、专有名词等精确匹配。项目里二者并行召回，不能因为接了向量库就删掉关键词检索。

### 10．RRF 和 Rerank 的区别是什么？

**来源：** S3、S5（RAG 系统优化）。

**怎么答：** RRF 是把多个召回列表按名次融合，不依赖不同检索分数能否直接比较；Rerank 是拿问题和候选证据做更细的相关性排序。我的链路先并行召回和 RRF，再只对较小候选集 Rerank，控制时延和费用。

### 11．GraphRAG 什么时候值得用？

**来源：** S1、S3、S5（知识图谱、业务语义层、Data Agent）。

**怎么答：** 不是所有问答都需要图谱。涉及实体关系、依赖链和跨资料关联时才值得，例如活动玩法对应哪些页面、接口、埋点和地区差异。简单“某字段是什么意思”仍走普通检索更快。项目用 Neo4j 作为关系补证，而不是让图谱替代全文知识库。

### 12．如何防止旧规范被新规范覆盖后查不到历史？

**来源：** S3、S8（企业系统、可扩展应用）。

**怎么答：** 新版本入库后标记为 effective，旧版本标记 deprecated，不直接覆盖或物理删除。检索默认只看当前有效版本，同时可按需要追溯历史。权限、有效期、来源和版本在召回后、生成前都要再过滤一次。

### 13．知识库里既有用户反馈又有正式文档，怎么避免错误反馈污染？

**来源：** S1、S3、S5（企业知识库、效果评测、业务落地）。

**怎么答：** 反馈不能直接写进正式文档。项目使用双层知识：正式知识和审核后的纠正知识分开管理。Bad Case 先保存问题、检索快照和修正建议，审核通过后才晋升为可检索纠正知识；撤销则失效对应内容。

### 14．RAG 没有检索到足够证据时应该拒答还是联网？

**来源：** S2、S3、S5（场景化应用、RAG、业务系统接入）。

**怎么答：** 取决于问题类型和信息边界。实时公开信息可以联网补证，但内部制度、活动规则或敏感数据不能拿网络结果替代内部真相。项目中会先判断是否允许联网；联网结果同样视为不可信外部证据，需要来源标识，不能伪装成内部规范。

### 15．如何证明 RAG 回答可信？

**来源：** S3、S5、S7（企业 RAG、研发效能、质量平台）。

**怎么答：** 不只看模型说得通不通。每个结论尽量关联来源片段；证据不足时降低置信度、继续检索或明确说明缺资料。离线用标准问答检查回答正确性、引用覆盖和拒答合理性，线上再看 Bad Case、空召回和人工接管。

## 三、Agent、规划与工作流

### 16．Agent 和工作流有什么区别？

**来源：** S1、S2、S5、S8（多 Agent、任务规划、工具调用）。

**怎么答：** 工作流的路径主要由系统预先定义，适合稳定 SOP；Agent 会根据当前状态选择下一步工具或计划，适合开放问题。企业场景我不二选一：确定环节用工作流保证稳定，开放检索和复杂分析用 Agent，但都要有状态、预算和终止条件。

### 17．ReAct、Plan-and-Execute、LangGraph 状态机怎么选？

**来源：** S1、S4、S5（ReAct／Plan-and-Execute、平台研发、长程规划）。

**怎么答：** ReAct 适合短链路探索；Plan-and-Execute 适合先拆计划再执行的较长任务；有岗位依赖、审批和交付物的企业流程更适合 LangGraph 状态机。我的问答 Agent 使用受控循环，产研运任务使用状态图和 DAG，不把所有需求都塞进一种范式。

### 18．多 Agent 是不是越多越好？

**来源：** S1、S2、S5、S7（多 Agent 自动化、业务工作流）。

**怎么答：** 不是。多 Agent 会增加上下文传递、协调、失败定位和成本。只有职责清晰、输入输出不同且可以独立验收的角色才拆开，例如产品澄清、前端页面、后端接口、测试验收。项目里所谓多 Agent 本质是多岗位状态节点，不是多个模型自由聊天。

### 19．怎样判断任务该结束，避免 Agent 无限循环？

**来源：** S1、S4、S6（执行引擎、长程规划、上下文利用率）。

**怎么答：** 同时设业务终止条件和工程预算：计划是否完成、证据是否足够、Artifact 是否通过校验；以及最大步骤、最大工具次数、最大重试、超时和 Token／成本上限。任意硬限制命中就结束并返回当前已完成部分与缺失项，而不是继续“思考”。

### 20．Agent 计划错了怎么办？

**来源：** S1、S4、S5（任务规划、反思与自我修复）。

**怎么答：** 先把计划与执行状态保存下来，失败时判断是参数错、工具错、证据不足还是前置资料缺失。可修复的问题节点级重试或重新规划；依赖资料的问题进入补料和人工审批；已完成节点不重复执行。这样避免整条工作流从头跑。

### 21．什么是 Human-in-the-loop，放在哪一步最合理？

**来源：** S3、S5、S8（业务集成、高风险应用、复杂系统）。

**怎么答：** 人工不应该审每个模型 token，而应卡在高风险、有副作用或低置信度的关口。项目中 Schema、接口／埋点方案等 Artifact 可以审核；驳回时要求填写缺失资料或修改意见，然后只重跑受影响节点。写库、发布、外部调用等动作也应如此处理。

### 22．Chat Agentic 和 Task Agentic 为什么要分开？

**来源：** S1、S5、S7（多轮对话、任务规划、自动化）。

**怎么答：** Chat Agentic 的结果是一次高质量回答，重点是检索、补证和引用；Task Agentic 的结果是持续推进的结构化交付物，重点是状态、审批、恢复和依赖管理。混在一起会让聊天请求背上长任务的状态复杂度，也会让任务缺少可审计交付物。

### 23．如何设计 Agent 的共享状态？

**来源：** S1、S4、S6（Agent 框架、记忆、执行引擎）。

**怎么答：** 状态只存任务必需字段：原始需求、已确认约束、检索证据、当前计划、节点结果、Artifact、错误和预算。每个节点只写自己负责的字段，结构化 Schema 校验后再提交。不要把完整聊天原文和所有工具日志都复制给每个节点。

## 四、工具、MCP、记忆与上下文

### 24．Function Calling 的参数由模型生成，怎么防止传错？

**来源：** S1、S2、S3、S8（工具调用、业务集成、MCP）。

**怎么答：** 给工具定义严格输入 Schema，服务端做类型、枚举、范围、权限和业务前置条件校验。模型产出不合法就返回结构化错误，让它修正一次；不能因为模型说“执行成功”就认为业务成功。

### 25．MCP 和普通 HTTP API 有什么区别？

**来源：** S2、S5、S8（MCP、Agent 框架、工具生态）。

**怎么答：** HTTP API 是服务间协议；MCP 是给模型／Agent 发现和调用工具的一套上下文协议。MCP 解决工具描述、统一接入和客户端兼容，但不替代鉴权、审计、限流和业务幂等。项目里 MCP 是受 Tool Registry 管理的接入方式，不是绕过后端安全层。

### 26．插件／Skill 系统有什么价值？

**来源：** S2、S5、S8（Harness、Skill、MCP、可扩展应用）。

**怎么答：** 把可复用能力按契约注册，避免把所有工具硬编码到 Agent。一个插件应明确输入输出、权限、超时、风险等级、版本和降级策略。项目后台可查看启用状态和工具清单，运行记录里可以追溯实际使用了哪些插件。

### 27．短期记忆、长期记忆和知识库有什么区别？

**来源：** S1、S4、S6（记忆管理、上下文窗口）。

**怎么答：** 短期记忆是当前会话近期上下文，服务连续追问；长期记忆是用户偏好、稳定事实等跨会话信息；知识库是可治理的业务事实和制度。它们不能混存：聊天摘要可以帮助对话，但不能取代正式规则；正式知识必须经过版本和权限治理。

### 28．什么时候写入 Mem0 或长期记忆？

**来源：** S1、S4、S6（长期记忆、上下文优化）。

**怎么答：** 只写稳定、可复用且允许保留的信息，例如语言偏好、常用业务范围、已确认的长期约束。一次性需求、未经确认的推测和敏感内容不写。项目会在回答完成后分类写入，并保留清理和审计入口。

### 29．为什么需要 Redis Checkpointer，PostgreSQL 不够吗？

**来源：** S4、S6、S8（执行引擎、长任务、平台能力）。

**怎么答：** PostgreSQL 适合持久记录、审计和查询；Redis Checkpointer 适合高频保存工作流执行状态并在中断后快速恢复。长任务运行到一半断线或实例重启时，可以从最近 checkpoint 恢复，而不是重跑所有节点。最终状态和关键 Artifact 仍要落 PostgreSQL。

### 30．上下文压缩会丢信息，为什么还要做？

**来源：** S1、S4、S6（上下文工程、窗口利用率）。

**怎么答：** 不压缩会让延迟、成本和噪声持续增长。正确做法不是删除原文，而是保留原始会话作为事实源，在模型上下文中使用最近窗口＋滚动摘要＋少量语义相关旧问答。出现争议时可回查原始记录。

## 五、全栈工程、可靠性与平台化

### 31．为什么 AI Agent 岗位还要看后端和数据库？

**来源：** S3、S5、S8（全流程 AI 应用、后端架构、系统集成）。

**怎么答：** 真实 Agent 的大部分复杂度在模型之外：会话、权限、知识版本、任务状态、工具调用、异步任务、审计和指标都需要后端与数据库。我的项目用 NestJS 组织服务，PostgreSQL 存业务事实，Redis 管状态和缓存，Milvus／ES／Neo4j 各自承担检索职责。

### 32．SSE 和 WebSocket 怎么选？

**来源：** S3、S5、S6（多轮交互、稳定服务、执行状态）。

**怎么答：** 单向流式生成和状态事件，SSE 更简单、浏览器兼容和断线处理成本低；需要双向实时协作、客户端频繁主动发送事件时再选 WebSocket。项目问答使用 SSE／AG-UI 把生成、检索、工具和运行事件按时间流回前端。

### 33．一次 Agent 运行如何做到可追踪？

**来源：** S3、S5、S7（线上运维、工程化提效、质量平台）。

**怎么答：** 为一次请求建立 trace／run ID，关联用户问题、路由、检索摘要、工具调用、模型生成、节点耗时、重试、Artifact 与最终结果。LangFuse 用于查看单次模型与 Agent 轨迹，Prometheus 看总体延迟、错误、空召回与工具成功率；二者解决的问题不同。

### 34．如何做幂等，避免重试导致重复写数据？

**来源：** S3、S6、S8（业务系统接入、高稳定服务、Agent 平台）。

**怎么答：** 读操作可安全重试；写操作需要请求幂等键、状态机和唯一约束。工作流节点重试前先检查该节点是否已经成功产出 Artifact；外部工具调用记录请求 ID 和结果，超时不能盲目再发。模型输出重试与业务写操作重试必须分开。

### 35．异步任务、消息队列什么时候需要？

**来源：** S3、S5、S6（后台服务、长任务、稳定运行）。

**怎么答：** 文件解析、批量索引、长工作流、定时报告和代码包生成不应该阻塞 HTTP 请求，这些适合异步任务。队列的价值是削峰、重试和失败隔离；但简单同步问答不必为了“架构完整”强行上队列。当前项目把重任务设计为可追踪运行，再根据部署环境接入 Worker／死信队列。

### 36．如何做多租户和权限过滤？

**来源：** S3、S4、S8（企业级 Agent、安全、高权限场景）。

**怎么答：** 权限不是回答后遮一下，而是检索前就限制候选范围。文档、Chunk、图谱关系和工具调用都要携带用户、角色或部门上下文；向量库和关键词库返回后再做一次权限校验。审计需要记录谁在什么时间通过什么工具访问了什么资源。

## 六、评测、运营与业务价值

### 37．RAG 和 Agent 的评测指标分别是什么？

**来源：** S3、S5、S7（AI 应用运维、工程化、质量平台）。

**怎么答：** RAG 看召回相关性、回答正确性、引用覆盖、拒答合理性和延迟；Agent 还要看任务完成率、步骤成功率、工具成功率、重试率、循环限制命中、成本与人工接管率。不要把“模型评分高”当成唯一指标。

### 38．如何建设评测集？

**来源：** S1、S3、S5（业务 Agent、RAG、从 0 到 1）。

**怎么答：** 从真实高频问题、线上失败案例、规则边界和高风险操作收集用例；每题明确期望结论、必要引用、允许拒答条件和错误等级。项目中的 Bad Case 审核通过后会进入回归集，形成“问题—修复—验证”的闭环。

### 39．什么叫 Bad Case 闭环？

**来源：** S3、S5、S7（AI 应用迭代、质量和工程化）。

**怎么答：** 不是收集差评。每个 Bad Case 关联原问题、路由、检索证据、回答、错误类型和期望修复；审核后决定补知识、修正答案、调参数或改 Prompt；最后加入回归集验证修复没有伤害其他场景。这样才能把线上问题变成长期质量资产。

### 40．如何向业务证明 Agent 有价值？

**来源：** S3、S5、S8（业务自动化、企业流程、AI 产品落地）。

**怎么答：** 先定义业务前后的对照，不只统计调用次数。常见指标是任务完成率、人工接管率、返工率、处理时长、资料查找时间、投诉率和用户复访。项目已提供采纳指标和运行数据入口；真实节省工时与 SLA 必须在真实用户和真实流程中持续测量。

### 41．上线后发现某类问题一直答错，你先查哪里？

**来源：** S3、S5、S7（线上运维、AI 质量平台）。

**怎么答：** 先看 trace 判断是路由错、检索空、召回偏、Rerank 排错、引用不足、模型生成偏还是工具失败；再用该请求快照复现。不要直接改 Prompt。确定根因后用 Bad Case 补知识或调整链路，并跑回归集确认没有引入副作用。

### 42．高级岗位如何谈“生产化”，又不夸大？

**来源：** S3、S4、S6、S8（高可用、平台、安全、执行引擎）。

**怎么答：** 我会区分本地工程闭环与真实生产验证。已具备的包括版本权限、状态恢复、降级、审计、评测和观测；仍需真实环境验证的是多副本故障切换、业务 API 幂等、IAM／DLP、告警值班、真实成本和 SLA。能清楚说边界，比把 Demo 说成生产系统更符合高级工程师预期。
