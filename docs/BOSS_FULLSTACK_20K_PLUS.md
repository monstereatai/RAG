### 明确排除项

- `15–30K`、`18–25K` 等职位：虽然上限超过 20K，但不满足「20K 以上」的下限口径。
- 纯前端、纯后端、纯移动端职位：除非 JD 明确承担服务端和用户端的完整交付，否则不算全栈样本。
- AI Agent 专岗：不纳入本次主样本；相关能力只作为通用全栈职位中的附加趋势观察。

## 三、岗位考察知识点清单

### P0：必须能讲出项目证据

1. **需求到上线的完整闭环**：能拿一个功能讲清楚范围、接口、数据、异常、测试、上线与回滚。
2. **一主一辅技术栈**：主栈做到能排障和做取舍，例如 React＋NestJS，或 Vue＋Spring Boot；辅栈能读代码、完成协作。
3. **接口、权限与数据模型**：能自己设计资源、状态流转、错误码、分页、RBAC、表结构、索引和事务。
4. **性能与稳定性**：不是背 QPS，而是能说明慢在哪里、如何量到、怎么优化、优化后指标如何变化。
5. **工程化**：Git 协作、代码评审、单测／集成测、环境配置、Docker、日志、监控、发布回滚。

### P1：20K＋岗位常用的拉开差距项

6. **Redis 与消息队列**：缓存、分布式锁、热点保护、异步任务、重复消费、失败重试、死信和人工补偿。
7. **系统设计**：从单体开始，按真实瓶颈拆模块；限流、熔断、降级、幂等、可观测性要能落到接口。
8. **前端复杂交互与质量**：状态边界、表单校验、长列表、上传、SSE／WebSocket、可访问性、首屏性能。
9. **安全与治理**：越权、注入、XSS、CSRF、敏感信息、审计日志、数据删除／导出控制。
10. **业务协作**：需求含糊时如何澄清；线上问题如何止血；和产品、测试、运维如何形成可执行的验收标准。

### P2：有项目就讲，没有不要硬装

11. **支付／订单／库存**：状态机、回调验签、幂等、对账与补偿。
12. **多租户和 SaaS**：租户识别、数据隔离、配置隔离、配额、审计。
13. **AI 辅助研发或 AI 应用**：把 AI 放在有测试、有 Review、无密钥泄漏的流程里，不把生成代码直接当生产代码。

## 四、面试用的回答结构

每题不要背概念，固定用下面五句话组织即可：

1. **背景**：这是哪个用户／业务流程，为什么要做。
2. **问题**：真实阻塞是什么，影响了谁，如何发现。
3. **方案比较**：列两三个可行选择，说明不选的原因。
4. **我的选择**：自己负责哪一段，关键设计和兜底是什么。
5. **效果与边界**：用指标、故障次数、交付周期或用户反馈收尾；承认还未解决的边界。

## 五、问题式面试指南（60 题）

> 用你真实项目替换文中的「我」。没有做过的效果不要编数字，可以说「上线后用 XX 指标观察，目前还没有足够样本下结论」。

### A．需求、架构与协作

**1．主题：端到端交付｜你如何把模糊需求做成可上线功能？**

- 背景／问题：产品常只给目标，例如「加一个审批流」，边界、角色、异常路径都不完整。
- 主流方案：直接开工；先写长 PRD；先用短流程图、接口契约和验收例子对齐。
- 我的选择：我先列角色、状态和异常例子，确认最小可用范围；再按「数据模型—接口—页面—测试—发布」拆任务，依赖不清的内容显式标风险。
- 效果／边界：联调返工会明显减少；但规则经常变的业务，仍要保留配置化或二次迭代空间，不能假设第一次就定稿。

**2．主题：架构｜单体什么时候该拆服务？**

- 背景／问题：业务增长后，所有模块都在同一服务里改，发布和故障互相影响。
- 主流方案：一开始微服务；始终单体；按领域和独立伸缩／发布需求逐步拆。
- 我的选择：早期保留模块化单体，把接口、领域和数据库访问边界写清；当任务处理或高流量模块确实需要独立扩缩容时，先抽成独立服务并保留兼容接口。
- 效果／边界：避免过早引入调用链、分布式事务和运维成本；拆分后仍需监控跨服务失败，不能把拆服务当成性能万能药。

**3．主题：协作｜前后端如何避免「接口到联调才发现不对」？**

- 背景／问题：字段名称、空值、分页和错误语义不一致，会把简单功能拖成反复返工。
- 主流方案：口头同步；接口写完再给；先维护 OpenAPI／接口示例和 Mock。
- 我的选择：接口开发前确认请求、响应、状态码、权限和空数据例子；前端先按 Mock 开发，后端以契约做集成测试，变更必须版本化或提前通知。
- 效果／边界：联调问题从「猜」变成可定位的契约差异；契约本身也要评审，否则只是在固化错误设计。

**4．主题：技术选型｜你怎么在 React 和 Vue、Java 和 Node 之间做选择？**

- 背景／问题：选型常被个人偏好带偏，后续招聘、维护和生态成本被忽略。
- 主流方案：追新框架；统一公司栈；按团队、领域、性能与交付时间选择。
- 我的选择：先看现有团队和组件资产；管理后台优先选团队最熟的 React／Vue，服务端优先选现成的 Java／Node 主栈。只有性能模型或生态能力明确不匹配时才换栈。
- 效果／边界：新成员能更快接手、工具链更一致；极端计算密集型任务仍可能需要独立的 Go／Java 服务，而不是强行全用 Node。

**5．主题：方案评审｜方案里你一定会写哪些内容？**

- 背景／问题：只写「用 Redis／MQ」无法让人判断风险和验收标准。
- 主流方案：口头评审；大而全设计文档；一页式决策记录加关键时序图。
- 我的选择：写目标与非目标、流程、数据变化、接口契约、失败路径、容量假设、监控指标、发布回滚；争议项标明备选和取舍。
- 效果／边界：评审能提前暴露遗漏；文档必须随关键变更更新，否则会误导排障。

**6．主题：线上事故｜线上出错时先做什么？**

- 背景／问题：事故中同时改代码、找人、猜原因，往往扩大影响。
- 主流方案：先追根因；先重启；先止血再恢复、再复盘。
- 我的选择：先确认影响范围和最近变更，限流、降级、回滚或关闭有风险开关；稳定后通过日志、指标、调用链定位根因，最后补监控和回归测试。
- 效果／边界：用户影响时间更短；若没有开关和观测，止血手段会很有限，所以它们应在事故前建设。

### B．前端与用户体验

**7．主题：前端状态｜复杂页面的状态怎么管理？**

- 背景／问题：筛选、编辑、分页、弹窗同时存在时，状态散在组件里会互相覆盖。
- 主流方案：所有状态放全局；全写本地；按共享范围分层。
- 我的选择：输入框等临时状态留组件内；跨页面或多个组件共享的数据放 query／store；服务端数据交给查询缓存，避免手写重复 loading 和刷新逻辑。
- 效果／边界：状态来源清晰、重复请求少；全局 store 仍要控制粒度，不能把每个 UI 开关塞进去。

**8．主题：前端性能｜你如何定位首屏慢？**

- 背景／问题：用户感到「页面慢」不等于一定是 React 渲染慢。
- 主流方案：先 memo；先换 CDN；先用网络、性能面板和真实指标拆分瓶颈。
- 我的选择：先分 TTFB、接口耗时、资源体积、JS 执行和渲染；按结果做接口并发／缓存、路由懒加载、图片压缩、虚拟列表或减少无效渲染。
- 效果／边界：每次优化都有前后对比；不为小页面过度拆包，避免请求数反而变多。

**9．主题：表单｜长表单怎样保证可用和数据正确？**

- 背景／问题：复杂配置表单容易出现前端能填、后端不能存，或错误提示太晚。
- 主流方案：只后端校验；只前端校验；前端即时反馈＋后端最终校验。
- 我的选择：前端做必填、格式和关联字段提示，提交时后端用同一业务规则再校验；失败返回明确字段错误，草稿与正式提交分开。
- 效果／边界：用户少走回头路，服务端数据仍可信；复杂规则不能只靠前端表达，要有接口测试覆盖。

**10．主题：实时交互｜什么时候选轮询、SSE、WebSocket？**

- 背景／问题：进度、通知、聊天等场景需要及时更新，但连接也有成本。
- 主流方案：固定轮询；单向流用 SSE；双向实时协作用 WebSocket。
- 我的选择：状态变化不频繁的任务用退避轮询；服务端持续推送生成进度用 SSE；聊天室或协同编辑才用 WebSocket，并处理断线重连和最后状态补拉。
- 效果／边界：实现与需求匹配；SSE 不是双向协议，WebSocket 也不应替代普通 CRUD。

**11．主题：组件设计｜如何避免组件越写越难维护？**

- 背景／问题：一个「万能组件」同时处理业务、请求和样式，很快无法复用也不敢改。
- 主流方案：所有内容都抽组件；全部写在页面；按稳定复用边界抽象。
- 我的选择：先拆展示组件、业务容器和数据请求；只有结构和行为稳定重复两次以上才抽公共组件，业务规则留在业务层。
- 效果／边界：页面阅读成本下降；过早抽象会让简单需求变复杂，所以组件 API 必须克制。

**12．主题：前端错误｜如何处理接口失败和重复提交？**

- 背景／问题：网络抖动或用户连点会造成重复订单、页面空白或错误被吞。
- 主流方案：只 toast；按钮禁用；前端体验控制＋后端幂等兜底。
- 我的选择：提交期间禁用按钮并显示可理解状态；请求超时可重试但不盲目重复；后端用幂等键保证同一业务动作只生效一次。
- 效果／边界：体验稳定，数据不靠前端「防连点」来保证；幂等键的有效期和冲突响应要定义清楚。

### C．接口、服务端与数据库

**13．主题：API｜一个好 REST 接口你怎么设计？**

- 背景／问题：接口若混用动作、资源和错误语义，前后端都会难维护。
- 主流方案：随手设计；完全 REST 教条；资源为主、必要时保留明确业务动作。
- 我的选择：资源读写使用统一路径、分页和筛选；审批、发布等状态机动作采用明确 action；所有接口定义鉴权、幂等、错误码和空数据行为。
- 效果／边界：客户端能预测接口行为；不为形式统一而把复杂业务动作硬塞进 CRUD。

**14．主题：数据库｜表结构与索引如何设计？**

- 背景／问题：先把字段堆出来，上线后查询慢、状态混乱、数据无法追溯。
- 主流方案：只按页面字段建表；全范式化；按核心查询和一致性要求建模。
- 我的选择：先画实体关系和状态变化，明确唯一约束；给高频筛选、关联和排序建立组合索引，再用真实 SQL 的执行计划验证。
- 效果／边界：查询稳定且数据约束更可靠；索引会增加写成本，低频字段不滥加。

**15．主题：事务｜什么时候必须使用事务？**

- 背景／问题：创建订单同时扣库存、写流水，任一步失败都不能留下半成品。
- 主流方案：所有操作都包事务；完全靠补偿；单库强一致用短事务，跨服务用状态与补偿。
- 我的选择：同库、必须同时成功的数据写入放短事务；外部调用和耗时任务移到事务外，靠事件、状态机和补偿处理。
- 效果／边界：避免长事务锁表；跨服务无法天然强一致，必须接受最终一致并设计可观测的补偿。

**16．主题：慢查询｜怎么定位并修复？**

- 背景／问题：接口慢可能是 SQL、缓存击穿、网络或序列化，不能凭直觉加索引。
- 主流方案：直接加索引；先查日志和慢 SQL；用执行计划验证假设。
- 我的选择：按 trace 定到 SQL，查看执行计划的扫描行数、索引命中和排序；再改查询条件／分页方式／索引，最后压测并观察写入影响。
- 效果／边界：优化能复现且有证据；数据量增长后需持续监控，不能把一次优化视为永久解决。

**17．主题：分页｜深分页为什么慢，怎么处理？**

- 背景／问题：`offset` 越大，数据库丢弃的行越多，运营后台导出也可能拖垮库。
- 主流方案：全部 offset；游标分页；异步导出。
- 我的选择：用户跳页需求强的后台用受限 offset；按时间或 ID 连续浏览用游标分页；大导出走异步任务并下载结果。
- 效果／边界：大数据列表更稳定；游标分页不适合任意跳到第 N 页，要在产品层说明。

**18．主题：文件上传｜上传大文件怎么设计？**

- 背景／问题：同步上传、解析、转码会占满请求线程，用户也不知道进度。
- 主流方案：接口同步处理；对象存储直传；上传与处理解耦。
- 我的选择：服务端签名或受控直传到对象存储，数据库只记录元数据；解析、转码、索引进异步队列，前端轮询或订阅处理状态。
- 效果／边界：上传接口更快、失败可重试；要校验文件类型、大小、权限和病毒扫描，不能相信扩展名。

### D．缓存、并发与异步

**19．主题：Redis｜缓存和数据库不一致怎么办？**

- 背景／问题：数据更新后旧缓存还在，用户看到错误结果。
- 主流方案：先删缓存再写库；先写库再删缓存；双删／消息订阅。
- 我的选择：多数读多写少场景采用「先写数据库，事务提交后删除缓存」；热点数据设置合理 TTL，并在关键读路径允许短暂回源。
- 效果／边界：实现简单且最终收敛；极端并发下仍可能短暂读旧值，强一致业务不应只靠缓存。

**20．主题：缓存风险｜缓存穿透、击穿、雪崩分别怎么处理？**

- 背景／问题：恶意不存在 ID、热点过期、同批 key 过期都会把流量压到数据库。
- 主流方案：只加大 Redis；空值缓存、互斥重建、过期时间打散和限流组合。
- 我的选择：不存在数据做短 TTL 空值缓存；热点采用逻辑过期或单飞重建；TTL 加随机抖动，入口做参数校验和限流。
- 效果／边界：数据库峰值被保护；锁本身也会失败，需设置超时与降级，不能无限等待。

**21．主题：幂等｜如何保证消息或支付回调不重复生效？**

- 背景／问题：网络重试和 MQ 至少一次投递意味着同一事件可能来多次。
- 主流方案：相信上游只发一次；内存去重；业务唯一键＋持久化状态。
- 我的选择：用订单号／事件 ID 建唯一约束或幂等记录，处理前判断状态；成功与失败都记录可追溯结果，重复请求返回已处理语义。
- 效果／边界：重复事件不会重复扣款或发券；幂等不等于顺序正确，乱序事件还要靠版本号或状态机处理。

**22．主题：消息队列｜什么任务适合异步化？**

- 背景／问题：发短信、导出、转码等慢任务放在接口里会拖慢用户请求。
- 主流方案：全部异步；全部同步；以用户是否需要即时结果、失败重试需求来划分。
- 我的选择：用户必须立即知道成败的核心写操作同步完成；耗时、可重试、可延后的副作用放队列，并返回任务状态。
- 效果／边界：请求更快且能削峰；队列不是免费午餐，需要消费幂等、积压监控和失败补偿。

**23．主题：任务重试｜失败重试如何不制造灾难？**

- 背景／问题：下游暂时故障时立即无限重试会雪崩，永久错误重试没有意义。
- 主流方案：无限重试；不重试；有限次数＋指数退避＋死信处理。
- 我的选择：只重试超时和短暂不可用等可恢复错误；指数退避并加抖动，超过阈值进入死信或人工处理；业务错误直接失败并给原因。
- 效果／边界：短暂故障可自愈；必须有积压、失败率和死信告警，否则失败只是被藏起来。

**24．主题：限流｜怎么保护核心接口？**

- 背景／问题：突发流量或脚本攻击会让所有用户一起受影响。
- 主流方案：单机计数；网关统一限流；按用户／租户／接口分级。
- 我的选择：网关做基础 IP／接口限流，业务层再按用户、租户或资源配额限制；超限返回可理解提示，并为内部任务保留隔离配额。
- 效果／边界：核心服务不会被少数请求拖死；阈值要按容量和真实流量调，不能拍脑袋设一个数。

### E．权限、安全与质量

**25．主题：认证｜JWT 和 Session 怎么选？**

- 背景／问题：既要登录态，又要处理多端、注销和权限变化。
- 主流方案：全 JWT；全 Session；按部署和风险选择。
- 我的选择：需要无状态横向扩展的 API 使用短期 access token＋可撤销 refresh token；强后台控制场景可用服务端 Session。无论哪种，接口都实时校验用户状态和权限。
- 效果／边界：扩展性和安全性平衡；JWT 不能一签就永不失效，密钥轮换和吊销策略必须具备。

**26．主题：授权｜RBAC 做到什么才算真的可用？**

- 背景／问题：只有「管理员／普通用户」很快覆盖不了部门、数据范围和临时授权。
- 主流方案：前端隐藏按钮；只做角色；角色＋权限点＋数据范围。
- 我的选择：后端以权限点校验操作，再叠加数据归属／部门／租户过滤；前端权限只用于体验，不作为安全边界；关键操作写审计日志。
- 效果／边界：越权风险下降；权限模型不要一开始过细，先覆盖真实角色再迭代。

**27．主题：安全｜怎样防 SQL 注入、XSS、CSRF？**

- 背景／问题：用户输入、富文本和 Cookie 登录态都是攻击入口。
- 主流方案：只靠 WAF；参数化查询、输出编码、CSRF 防护分层处理。
- 我的选择：SQL 一律参数化；富文本白名单清洗并按上下文转义输出；Cookie 登录启用 SameSite／HttpOnly，危险写操作加 CSRF token 或同源策略校验。
- 效果／边界：常见输入攻击被前置挡住；依赖升级、权限审计和安全测试仍要持续做。

**28．主题：测试｜你如何决定哪些代码必须测？**

- 背景／问题：全量测试成本高，但只靠人工回归会漏核心规则。
- 主流方案：追求覆盖率；只测 UI；按风险分层测试。
- 我的选择：金额、权限、状态机、幂等和数据转换写单测；接口契约与数据库交互写集成测试；关键用户链路做少量端到端测试。
- 效果／边界：把预算集中在最怕出错的地方；覆盖率只是信号，不能替代有价值的断言。

**29．主题：代码评审｜你看 PR 时重点看什么？**

- 背景／问题：只看格式会错过数据安全和线上风险，过度挑语法又会拖慢交付。
- 主流方案：只看能否运行；逐行挑风格；先看行为、边界和可维护性。
- 我的选择：先确认需求覆盖、数据变化、鉴权、异常、并发和测试；再看命名和重复。评论说明风险和替代写法，非关键风格问题交给 lint。
- 效果／边界：评审更聚焦线上质量；评审者也会漏，核心改动仍需自动化测试和灰度保障。

**30．主题：可观测性｜日志、指标、链路追踪分别解决什么？**

- 背景／问题：线上只看到「报错了」时，无法知道影响多少用户、慢在哪一跳。
- 主流方案：只打日志；日志＋指标；日志、指标、Trace 联合。
- 我的选择：日志记录请求 ID、用户／租户（脱敏）、错误上下文；指标看成功率、延迟、队列积压；跨服务调用透传 trace ID 定位链路。
- 效果／边界：故障从人工猜测变为可查询证据；日志不能记录密码、token 或完整敏感内容。

### F．部署、稳定性与业务能力

**31．主题：Docker｜如何把开发环境带到生产？**

- 背景／问题：「我本机能跑」常因环境变量、依赖版本和启动顺序在服务器失败。
- 主流方案：手工部署；单 Docker；镜像化服务＋外置配置。
- 我的选择：镜像只包含运行所需依赖，配置通过环境或密钥系统注入；健康检查区分进程活着和依赖就绪；数据库、Redis 等依赖在部署清单中明确。
- 效果／边界：环境更一致、回滚更可控；镜像不是安全边界，仍需最小权限和漏洞扫描。

**32．主题：发布｜如何降低上线风险？**

- 背景／问题：一次全量发布失败会影响所有用户，数据库变更尤其难回滚。
- 主流方案：直接覆盖；蓝绿；灰度＋功能开关。
- 我的选择：普通变更先自动化测试，发布后观察错误率和延迟；高风险功能按用户／租户灰度并保留开关；数据变更按兼容顺序先扩展、后切流、最后清理。
- 效果／边界：发现问题可快速止损；灰度需要监控和回滚预案，否则只是把风险延后。

**33．主题：高可用｜服务怎样避免单点？**

- 背景／问题：单实例宕机、单 Redis、单数据库都会让整个业务不可用。
- 主流方案：简单多副本；所有组件都多活；按故障影响做分层冗余。
- 我的选择：无状态服务先做多副本和负载均衡；关键依赖设主从／托管高可用，应用设置超时、熔断与降级；备份恢复定期演练。
- 效果／边界：单机故障不再等于全站故障；多活会显著增加一致性成本，只在业务值得时使用。

**34．主题：容量｜没有历史大流量数据，怎样做容量预估？**

- 背景／问题：新功能上线前只能估算，但完全不估会在活动时失控。
- 主流方案：拍脑袋 QPS；照搬别的系统；按用户行为和资源测量建保守模型。
- 我的选择：从预计用户数、峰值时段、每人操作频率推请求量；压测核心接口，预留余量；把缓存命中率、数据库连接、队列积压作为上线观察指标。
- 效果／边界：估算假设透明可修正；真实流量偏差仍可能很大，所以必须能扩容、限流和降级。

**35．主题：支付｜支付回调最容易漏什么？**

- 背景／问题：用户跳回页面不等于支付成功，回调可能重复或延迟。
- 主流方案：以前端结果为准；只收回调；回调验签＋订单状态机＋对账。
- 我的选择：以后端验签回调更新订单为准，按交易号幂等处理；前端只展示查询到的订单状态；定时对账发现漏单并补偿。
- 效果／边界：避免伪造成功和重复记账；支付渠道异常时仍要有人工核对路径。

**36．主题：业务指标｜全栈工程师怎么证明技术有价值？**

- 背景／问题：只说「做完了」无法说明质量和业务结果。
- 主流方案：只报代码量；只报技术指标；把用户、效率、质量和成本关联起来。
- 我的选择：上线前定义一个业务指标和几个护栏指标，例如审批完成时长、转化、错误率、接口 P95；上线后对比趋势并结合反馈解释变化。
- 效果／边界：技术决策更容易获得支持；相关性不等于因果，样本不足时必须诚实说明。

### G．快速追问清单（37–60）

**37．主题：Git 协作｜遇到冲突你怎么处理？**

- 背景／问题：同一业务文件多人改动时，机械选择「我的／他的」会悄悄丢逻辑。
- 主流方案：直接覆盖一方；逐段理解后合并；推倒重来。
- 我的选择：先看双方提交想解决什么和测试覆盖什么，再逐块合并；关键流程请原作者复核并运行相关测试。
- 效果／边界：保住两边业务意图；冲突频繁说明模块边界或任务切分本身需要调整。

**38．主题：接口演进｜如何做 API 版本兼容？**

- 背景／问题：客户端未同步升级时，删字段或改语义会直接导致线上故障。
- 主流方案：直接改；字段兼容；新增版本并设迁移期。
- 我的选择：非破坏性变更优先新增字段；破坏性变更使用 `/v2` 或版本字段，记录旧版本调用量并公告下线时间。
- 效果／边界：客户端可平滑迁移；版本不能无限保留，要有可执行的淘汰计划。

**39．主题：服务端分层｜为什么 DTO 不直接当数据库实体？**

- 背景／问题：接口输入输出、权限字段和存储结构的变化节奏不同，直接复用易泄漏内部字段。
- 主流方案：全复用实体；完全重复定义；显式 DTO 与实体映射。
- 我的选择：对外 DTO 只放允许读写的字段，服务层完成映射和业务校验，持久化结构只由仓储层处理。
- 效果／边界：接口更安全也更易演进；简单内部工具不必为了形式堆很多层。

**40．主题：错误处理｜怎样设计错误码？**

- 背景／问题：只返回「失败」无法让前端处理，也不利于线上定位。
- 主流方案：直接抛堆栈；只返回 HTTP 状态；HTTP 状态加稳定业务码。
- 我的选择：区分参数、鉴权、冲突、限流和内部错误；返回机器码、可读提示和请求 ID，详细堆栈只进日志。
- 效果／边界：用户知道怎么处理，排障有线索；不能把数据库或密钥细节返回客户端。

**41．主题：数据库｜N+1 查询如何解决？**

- 背景／问题：列表循环查询关联数据，数据一多接口就随条数变慢。
- 主流方案：加缓存；循环查库；批量查询、预加载或聚合。
- 我的选择：从 Trace 或 SQL 日志确认重复查询后，改成一次批量查映射或合理 join，并比较查询次数和响应时间。
- 效果／边界：延迟随列表长度增长的速度下降；大 join 也会膨胀，复杂场景仍需按数据量验证。

**42．主题：事务｜为什么避免长事务？**

- 背景／问题：事务里调用远程服务或做慢计算，会长期占锁和连接。
- 主流方案：所有流程包事务；完全不用事务；只包必须原子的短写入。
- 我的选择：同库一致性写入使用短事务，网络调用和慢任务移到事务外，通过状态和补偿收敛。
- 效果／边界：锁等待和死锁风险下降；跨服务只能做到最终一致，补偿必须可观测。

**43．主题：并发｜分布式锁有哪些坑？**

- 背景／问题：多实例抢同一资源时，内存锁失效；锁错误释放又会互相覆盖。
- 主流方案：本地锁；Redis 锁；数据库唯一约束或条件更新。
- 我的选择：能用唯一约束／原子更新的业务优先不用锁；必须锁时使用 token、安全释放、TTL 和超时，关键结果仍由数据库约束兜底。
- 效果／边界：避免重复执行；锁不能替代正确的数据模型，网络分区等极端场景要保守处理。

**44．主题：库存｜如何避免超卖？**

- 背景／问题：多请求同时读到同一库存后再扣减，会卖出不存在的商品。
- 主流方案：先读后写；悲观锁；条件更新／乐观锁加排队削峰。
- 我的选择：以数据库条件更新保证 `stock > 0` 才扣减，失败立即返回；高峰期用队列削峰，缓存只做展示和加速。
- 效果／边界：最终库存不会为负；用户体验与公平性还要由排队规则和订单超时释放处理。

**45．主题：消息队列｜队列积压怎么排查？**

- 背景／问题：任务迟迟不完成，直接清队列会造成业务数据丢失。
- 主流方案：盲目扩容；清空重来；比较生产、消费、失败与下游延迟。
- 我的选择：先看积压增长速度和消费者报错，短期扩消费或限生产止血，再定位慢处理和下游瓶颈，失败消息保留重放路径。
- 效果／边界：恢复过程可控且可追溯；扩容前要确认下游数据库或第三方能承受更多并发。

**46．主题：实时通信｜WebSocket 断线如何恢复？**

- 背景／问题：移动网络切换会丢消息，用户重连后不知道当前状态。
- 主流方案：只重连；定时全量刷新；重连＋事件位置补拉。
- 我的选择：客户端退避重连并带最后事件位置，服务端支持补拉；订单、任务等最终状态始终落库并可主动查询。
- 效果／边界：临时断线不会丢关键结果；连接消息只负责体验增量，不能作为唯一事实来源。

**47．主题：前端性能｜大列表怎么优化？**

- 背景／问题：一次渲染几千行、每行又请求数据，会卡顿并压垮接口。
- 主流方案：全量加载；纯前端虚拟滚动；服务端分页＋前端按需渲染。
- 我的选择：服务端完成筛选、排序和分页，前端长列表虚拟化，关联数据批量返回，图片懒加载；先量化是接口还是渲染慢。
- 效果／边界：滚动和首屏更稳定；虚拟列表会影响部分 DOM 测量和可访问性，需要专项验证。

**48．主题：兼容性｜怎样处理浏览器兼容？**

- 背景／问题：无限兼容所有旧浏览器代价很高，却不一定服务真实用户。
- 主流方案：不管兼容；全部 polyfill；以用户数据定义支持矩阵。
- 我的选择：按用户浏览器占比确定最低版本，构建阶段转译和按需 polyfill，登录、支付等关键流程在真实浏览器回归。
- 效果／边界：投入和用户价值匹配；超出支持范围要给明确提示，不能默默白屏。

**49．主题：渲染模式｜SSR 和 CSR 怎么取舍？**

- 背景／问题：内容站要首屏和 SEO，后台更看重复杂交互与鉴权。
- 主流方案：全 SSR；全 CSR；按页面目标混用。
- 我的选择：公开、搜索流量高的内容页考虑 SSR／预渲染；登录后的运营后台偏 CSR；同时设计 SSR 缓存、鉴权和 hydration 成本。
- 效果／边界：关键页面更快被看见；SSR 会增加服务端复杂度，不应为普通内部页面强上。

**50．主题：密钥安全｜如何防止敏感配置泄漏？**

- 背景／问题：把 key 放前端、仓库或日志，删除后也可能已被复制。
- 主流方案：`.env` 入库；运行时环境变量；密钥系统加轮换。
- 我的选择：密钥只在服务端运行时注入，按环境隔离，日志和异常脱敏；发现泄漏先吊销轮换，再追踪影响和补救。
- 效果／边界：泄漏面更小；权限最小化和定期审计不能省。

**51．主题：SaaS｜多租户数据隔离怎么做？**

- 背景／问题：漏掉一个租户过滤条件就会造成严重越权。
- 主流方案：共享表不隔离；共享表强制 `tenant_id`；独库／独 schema。
- 我的选择：从可信登录上下文获取租户，仓储层统一注入过滤并建组合索引；高隔离客户再选独库／schema，补越权自动化测试。
- 效果／边界：默认查询不易漏隔离；共享表还需防管理员跨租户操作和缓存串数据。

**52．主题：审计｜怎样设计审计日志？**

- 背景／问题：出了误操作或越权事件，只有业务表无法回答「谁做的」。
- 主流方案：不记录；记录全文；记录结构化动作摘要。
- 我的选择：记录操作者、时间、对象、动作、前后摘要、请求 ID 和结果；敏感字段脱敏，审计数据独立保留并支持检索。
- 效果／边界：排查和合规更有证据；审计日志也受隐私和留存期限约束。

**53．主题：运维｜为什么要区分 liveness 和 readiness？**

- 背景／问题：进程未死但数据库不可用时，继续接流量会放大错误。
- 主流方案：只一个 `/health`；分存活与就绪检查。
- 我的选择：liveness 只判断进程是否卡死，readiness 判断关键依赖和初始化是否可服务；负载均衡只把就绪实例接入流量。
- 效果／边界：故障实例更快隔离；不要把所有非关键依赖都设为不就绪条件，否则会不必要地下线服务。

**54．主题：稳定性｜怎样做降级？**

- 背景／问题：下游慢或不可用时，如果所有链路一起等待，核心功能也会倒。
- 主流方案：统一报错；缓存兜底；按核心级别降级。
- 我的选择：先定义必须成功的交易／写入路径；推荐、报表、搜索等非核心能力返回缓存、稍后处理或明确提示，并监控降级触发率。
- 效果／边界：核心服务有生存空间；降级结果必须可见，不能把旧数据伪装成最新结论。

**55．主题：发布治理｜为什么需要特性开关？**

- 背景／问题：代码已发布不代表功能应该对所有人立即生效。
- 主流方案：全量开；独立分支；按人群开关与灰度。
- 我的选择：高风险功能按租户／用户分批放开，问题时可秒级关闭；开关写明责任人和过期日，稳定后清理死分支。
- 效果／边界：发布和曝光解耦；开关过多会让测试组合爆炸，必须治理。

**56．主题：数据可靠性｜备份如何验证真的可恢复？**

- 背景／问题：备份任务显示成功，不代表恢复速度、权限和数据完整性符合目标。
- 主流方案：只看备份日志；定期在隔离环境恢复演练。
- 我的选择：按 RPO／RTO 定目标，定期恢复到隔离环境并抽查关键表、权限和应用启动，记录恢复耗时。
- 效果／边界：灾难时不是第一次执行恢复；备份本身也要加密、访问控制和异地冗余。

**57．主题：外部依赖｜第三方 API 不稳定怎么办？**

- 背景／问题：支付、短信、地图等供应商慢或报错，不能无限拖住用户请求。
- 主流方案：无限重试；立即失败；超时、有限重试、熔断和可对账落库。
- 我的选择：设明确连接与总超时，只重试短暂错误；触发熔断时返回可理解降级，关键请求落状态便于后续补偿和对账。
- 效果／边界：供应商故障不会拖垮自身服务；重试量要受限，避免成为对方故障的放大器。

**58．主题：AI 辅助研发｜如何提效又不失控？**

- 背景／问题：AI 可加速样板代码和排障，但幻觉、泄密和未测试代码会进入生产。
- 主流方案：完全禁止；直接接受生成结果；受控地用于辅助。
- 我的选择：用它产出脚手架、测试思路和排错假设；敏感数据不发送，生成代码必须 Review、测试、依赖检查和安全扫描。
- 效果／边界：重复工作减少但责任仍在人；AI 不能替代需求澄清、架构取舍和线上验收。

**59．主题：项目管理｜你如何估算需求工期？**

- 背景／问题：只报一个日期会掩盖接口、数据、测试和上线的不确定性。
- 主流方案：拍脑袋；只估编码；拆解并给区间和风险。
- 我的选择：拆成调研、接口、页面、数据、测试、发布和依赖项；对未知项先做小验证，给区间、假设和风险触发条件。
- 效果／边界：预期更可管理；估算不是承诺书，范围变化时必须及时更新。

**60．主题：自我认知｜你如何回答「你的短板是什么」？**

- 背景／问题：面试官想判断你是否知道自己的风险，以及是否会改进。
- 主流方案：说假缺点；承认核心能力缺失；讲真实但可控的具体改进项。
- 我的选择：选一个不影响岗位底线的真实场景，例如过去方案文档过于技术化；说明影响、我如何用验收例子和评审模板改进、如何验证。
- 效果／边界：回答可信且有成长证据；不能把「不擅长主栈／扛不住压力」包装成无害短板。

## 七、复习优先级

1. 先准备两个完整项目：一个后台／业务 CRUD＋权限，一个高并发或异步任务场景。每个都能按五段式讲完。
2. 再准备三段「排障证据」：一次慢查询、一次接口故障、一次发布或回滚。没有真实数字就准备观察方法。
3. 最后补技术深度：在主栈里至少把数据库索引、缓存一致性、幂等、队列重试、鉴权和发布说透。
