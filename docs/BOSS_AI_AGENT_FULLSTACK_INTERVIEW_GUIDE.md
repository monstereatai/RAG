## 先记住这一条回答公式

面试官真正想听的不是「你用了 LangChain、Redis、React」，而是你有没有解决一个真实工程问题。每题都按下面五句说：

```text
1. 背景：业务原来要做什么，为什么普通做法不够。
2. 问题：具体卡在哪里，会造成什么风险。
3. 方案：行业里常见的几种做法，各自适用什么情况。
4. 选择：我为什么选这一种，怎么落到代码和流程。
5. 效果：解决了什么；还有什么边界没有假装解决。
```

下面的「项目口述」以当前 RAG／Agent 全栈项目为例。数字只说已经验证过的；没有线上业务指标时，说「本地链路验证」「回归测试」即可，不要编造转化率或节省人力。

## 1．你做的到底是什么项目？

**面试官常问：用两分钟介绍你的 AI Agent 全栈项目。**

### 可以直接回答

我做的不是一个单纯的聊天框，而是一个面向企业知识和产研协作的 AI 应用。

背景是，企业资料散在文档里，普通搜索只能给一堆链接；业务人员还会问跨文档问题，研发流程中的需求、设计、测试和运营交接也常靠人工复制粘贴。

这个项目分成三层。第一层是知识层：文档解析后做结构化切片，用关键词检索和向量检索一起召回，再做重排；同时按用户、版本、地区和权限过滤。第二层是问答和 Agent：简单问题直接回答，复杂问题进入 Agent 流程，按需检索、调用工具、补证和反思。第三层是运营治理：有 Bad Case 回归、评测、运行轨迹、文档审核和管理后台。

全栈部分是用户端、管理后台、两个 NestJS 服务和 SSE 流式链路；Agent 部分重点不是让模型自由发挥，而是工具 Schema、超时、预算、审批、检查点和恢复。最终目的，是让答案有证据、任务能恢复、管理员能看到过程，而不是只让模型「看起来很聪明」。

### 面试官追问：为什么不直接接一个大模型 API？

直接接 API 的优点是快，适合公开知识或 Demo。但企业场景有三个问题：模型不知道内部资料；它回答错时无法追溯；不同用户不应该看到同一批文档。所以我把模型放在受控链路中：先按权限找证据，再决定是否回答；回答必须带引用，资料不足就明确拒答或让用户补充条件。

## 2．前后端和服务为什么这样拆？

**面试官常问：你的架构是什么？为什么有两个 NestJS 服务？**

### 可以直接回答

背景是系统既有普通用户端，也有高权限运营后台。如果所有页面都直接访问同一个后端，后台权限、服务间调用和前端接口会混在一起，后期很难控制。

常见做法有两个：一个后端服务到底，开发快；或者把面向用户的 RAG 服务和面向管理后台的 BFF 分开。前者适合小项目，后者更适合有后台、权限和多个前端的系统。

我选择第二种：RAG Backend 负责文档、检索、问答、Agent 和任务状态；Admin Backend 只处理管理端登录态、权限校验和对 RAG 服务的受控转发。管理前端不直接拿 RAG 的内部服务凭证，也不直接信任浏览器传来的用户 ID。

这样做的效果是，用户端、管理后台和 MCP 都能复用核心能力，但边界清楚。代价是多了一跳网络和接口包装，所以我会把服务间认证、超时和错误码作为正式契约，而不是临时 `fetch` 一下。

### 面试官追问：什么时候不需要拆？

如果只有一个前端、没有高权限运营操作、团队也很小，先做模块化单体更合适。拆服务不是为了显得复杂，而是当登录体系、权限模型、发布节奏或负载特征真的不同，才拆。

## 3．流式回答和长任务怎么做？

**面试官常问：SSE 怎么实现？为什么不用普通 HTTP 等模型返回？**

### 可以直接回答

背景是模型生成往往要几秒到几十秒。如果前端一直等完整 HTTP 响应，用户会以为系统卡死，也看不到引用、检索状态和错误原因。

常见方案有轮询、WebSocket 和 SSE。轮询实现简单但延迟高；WebSocket 更适合双向实时协作；模型输出本质上是服务端持续往浏览器推内容，所以 SSE 更直接，浏览器也原生支持。

我在问答链路用 SSE：后端按 `meta → partial → final → done` 推送，前端先显示生成过程，最终再用完整答案覆盖临时文本。真正的业务结果，例如引用、检索充分性、模型路由和错误码，放在 final 事件里，不让前端从零散 token 猜状态。

效果是用户能即时看到输出，前端也能稳定展示引用。边界是 SSE 不是任务持久化：网络断了只能重新订阅或重新发请求；文档解析、生成项目、多人审批这类分钟级任务要单独进入任务队列或状态机，并保存任务 ID。

### 面试官追问：流式中断会不会重复内容？

会，所以前端不能把每次连接都当成全新消息。做法是给一轮请求一个 `threadId` 或 `runId`，事件带序号或消息 ID；重连时只补缺失部分，最终以服务端 final 结果为准。对写操作还要有幂等键，避免重试导致重复入库。

## 4．权限和多租户怎么保证？

**面试官常问：RAG 系统怎样避免 A 用户查到 B 用户的文档？**

### 可以直接回答

背景是知识库最危险的问题不是「答错」，而是「答对了不该给他看的内容」。只在前端隐藏按钮没有用，用户可以直接改请求参数。

常见做法是只在生成前做一次过滤，或者在整个链路里都带归属信息。我选择后者：文档、切片、会话、任务、Artifact 都有 owner 或租户信息；检索时先做权限、版本、地区过滤，再把候选交给排序和模型；服务间调用通过内部服务 Token，浏览器传来的 ownerId 不作为可信身份来源。

效果是权限不只是页面层功能，而是数据检索和导出层的硬约束。对于管理员，我会单独设计角色权限和审计记录，不能因为是管理员就默认绕过所有数据边界。

### 面试官追问：向量库也能做权限吗？

可以。最少要把租户／用户、文档状态、版本、地区等作为 metadata，并在向量检索过滤表达式中带上。更严格的方案是按租户拆 collection 或物理隔离。小中型系统通常先用 metadata 过滤；隔离级别和数据量上来后，再评估独立索引或独立实例。

## 5．为什么要做多模型 Provider？

**面试官常问：模型接入怎么设计？换模型是不是改个环境变量？**

### 可以直接回答

背景是不同模型擅长的事不同：有的便宜快，有的推理强，有的支持更长上下文。模型也会超时、限流或临时不可用。如果业务代码到处写某一家 SDK，后面切换成本很高。

常见做法是直接在业务里调用 SDK，或者抽象一个 Provider 接口。前者做 Demo 最快，后者更适合生产。我把模型能力收在统一 Provider 内：业务层只请求「聊天」「流式」「结构化输出」这类能力，Provider 再选择 Qwen、DeepSeek、智谱等兼容实现。

我没有把「切模型」说成只改环境变量。生成模型可以切，但 embedding 模型一换，向量维度和历史索引可能不兼容；这需要新建索引、双写或重建，而不是热切。

效果是业务代码不和单一厂商绑定，并可做超时、重试和降级。边界是降级不能悄悄改变事实质量：例如引用问答的主模型失败时，要么用同一证据重新生成，要么明确返回资料不足，不能丢掉证据门禁后随便回答。

## 6．结构化输出和 Tool Calling 为什么不能相信模型？

**面试官常问：模型生成 JSON 或调用工具后，你怎么保证安全？**

### 可以直接回答

背景是模型输出本质上是文本。就算它看起来像 JSON，也可能缺字段、类型错，甚至被用户提示词诱导去调用不该调用的工具。

常见方案是靠 Prompt 约束、正则解析，或者用 JSON Schema／Zod 这类严格校验。Prompt 和正则只适合轻量场景；涉及工具、审批和结构化交付时，我选 Schema 校验。

具体做法是：模型先提出工具名和参数，服务端用工具白名单找到定义，再校验输入 Schema、用户权限、预算和超时。只有全部通过才真的执行。工具返回值也按 Schema 收口，避免把原始系统错误或敏感字段直接塞回模型上下文。

效果是模型负责「提出意图」，系统负责「执行决定」。例如模型说要导出文件，不等于它获得任意文件系统写权限；危险写操作仍要审批和审计。

### 面试官追问：Schema 校验失败怎么办？

先把失败类型区分开。缺字段、枚举错、JSON 不完整可以带错误信息让模型有限次数修复；权限不足、预算耗尽、危险操作未审批则不能重试执行，应返回可解释的 blocked 状态。无限重试只会烧钱和制造循环。

## 7．RAG 不是「向量库＋Chat」：你怎么做检索？

**面试官常问：你的 RAG 链路是什么？为什么要混合检索？**

### 可以直接回答

背景是企业问题里既有精确名词，例如接口名、活动 ID、版本号，也有语义问题，例如「这个流程的风险是什么」。只做关键词会漏掉同义表达；只做向量又容易把精确 ID 和版本号找错。

主流方案是 BM25、向量检索或两者混合。我选择混合：关键词检索负责精确字词，向量检索负责语义相近，再用 RRF 合并候选，必要时再做 Rerank。进入生成前还会按权限、版本、地区、文档状态过滤。

文档不是按固定字数硬切。我优先保留 Markdown 标题层级、表格和代码块的完整性，因为把一张规则表切断后，模型即使检索到其中一半，也很容易误读。

效果是既能回答技术术语，也能总结业务资料。边界是检索结果再高也不等于结论成立，所以最终仍要走引用和充分性判断。

### 面试官追问：Rerank 挂了怎么办？

Rerank 是质量增强，不该成为单点故障。它失败时保留混检结果，记录降级指标，再继续走证据充分性门禁。如果候选不足，就拒答；不能因为 Rerank 失败就让系统随便用低质量片段生成答案。

## 8．怎样保证回答有引用，资料不足时不胡说？

**面试官常问：引用怎么做？模型乱编引用怎么办？**

### 可以直接回答

背景是企业用户问「依据是什么」时，模型自己编一个来源没有价值。我们要让引用能回到具体文档和片段。

常见做法是让模型在文本里随便写链接，或者给每个候选片段一个受控 ID，再校验答案引用的 ID。我选择第二种：检索结果进入上下文前就分配证据 ID，模型只能引用当前这批 ID；生成后服务端校验引用是否存在、关键事实是否被证据覆盖。

如果资料不足，有三种错误做法：假装知道、强行联网拼凑、把低分片段当结论。我的选择是先返回「资料不足」和缺少的条件；只有业务明确允许联网时才补证，且联网结果也要区分外部资料和内部正式知识。

效果是回答的可信度来自证据，不来自模型语气。边界是「有引用」不等于「结论绝对正确」；引用质量仍要用评测集、人工抽检和 Bad Case 持续校正。

## 9．什么情况用 Agent，什么情况不用？

**面试官常问：为什么不用一个万能 Agent？为什么有些任务用状态机？**

### 可以直接回答

背景是 LLM 很适合处理开放问题，但不是所有流程都适合自由推理。比如查一条规则，只需要检索和回答；如果硬塞进多 Agent，会多出延迟、成本和不可预测性。

我会先按任务判断。简单、确定、只读的问题走直接问答；需要多轮检索或调用工具的复杂问答才进入单 Agent；产品、设计、前后端、测试、运营这种有明确依赖和审批节点的任务，才用状态机／DAG。

主流做法有 ReAct 自由循环、Supervisor 多 Agent、固定工作流。我的选择不是默认多 Agent：固定交付流程采用 DAG，因为它知道谁依赖谁、哪里需要审批、失败后从哪里重跑；开放研究问题才允许更自由的 Agent 循环。

效果是复杂度和收益匹配。面试时我会明确说，多 Agent 不是能力越多越好；没有清晰岗位边界和产物契约时，它只会让问题更难排查。

### 面试官追问：你的 Agent 怎么防止死循环？

每一轮都受最大步骤、最大工具调用数、单工具超时和总预算限制。工具失败会按可重试、可降级、不可继续三类处理。到上限时必须返回终止原因和当前已拿到的证据，而不是后台默默继续跑。

## 10．人工审批、Checkpoint 和重试怎么实现？

**面试官常问：用户审批后，Agent 怎样从原位置继续？**

### 可以直接回答

背景是长任务不可能一直保持一个 HTTP 连接。用户可能半小时后才审批，服务也可能重启。如果只把「pending」显示在页面上，实际执行位置和预算就丢了。

常见方案是内存变量、把任务从头重跑、或者持久化状态快照。内存变量重启即丢；从头重跑会重复花模型费用，也可能重复执行写工具。我选择保存 Checkpoint：记录 threadId、当前节点／步骤、状态、工具调用、剩余预算和更新时间；审批时用同一个 threadId 恢复。

关键细节是中断点之前不能先做不可重复的副作用。例如先发奖、再等待审批，恢复时节点重放可能再发一次。正确做法是先中断，审批通过后再进入写操作；写操作本身还要带幂等键。

效果是审批、驳回和局部重跑有明确边界。边界是恢复逻辑必须有版本兼容策略；状态 Schema 改了以后，旧快照不能盲目直接反序列化。

### 面试官追问：重试和重跑有什么区别？

重试是同一个步骤因为临时错误再试一次，例如网络超时；重跑是业务输入或审批意见变化后，从指定节点重新生成。前者要保留幂等键，后者要标记下游产物过期并重新审批，不能混成一个「再试一次」按钮。

## 11．MCP 在你的系统中做什么？

**面试官常问：MCP 和 API／Function Calling 有什么区别？**

### 可以直接回答

MCP 不是替代后端，也不是让模型直接获得服务器权限。它是让 Codex、Claude、Cursor 这类 AI 工具用统一协议发现和调用受控能力。

普通 HTTP API 是服务之间的接口；Function Calling 是模型生成一个工具调用意图；MCP 则把工具描述、参数 Schema 和传输协议标准化，方便不同 AI 客户端接入。

在项目里，MCP 主要暴露只读的 RAG 检索、上下文包、工作流状态和交接物导出。对已完成工作流，MCP 可以返回 Markdown 交接物、低代码 Schema 和 RAG 引用证据，供 AI Coding 工具在当前代码库实现；它不会直接写用户电脑文件，也不会绕过后台的审批／权限。

效果是项目知识可以被多个 AI 编程工具复用，且服务端仍掌控权限、审计和成本。边界是 MCP Server 也必须当成外部入口做认证、限流、Schema 校验和最小权限。

## 12．怎么评测、观测和处理 Bad Case？

**面试官常问：你怎样证明 Agent 或 RAG 做得更好？**

### 可以直接回答

背景是模型输出有随机性，人工看几条「感觉不错」不能证明质量提升。尤其切模型、改 Prompt、改检索策略后，很容易解决一个问题又破坏另一个问题。

主流方案是离线评测集、线上人工抽检、LLM-as-Judge、用户反馈。它们不是互相替代：离线评测适合发布前回归，线上反馈能发现真实场景，LLM Judge 适合规模化辅助但不能当唯一真相。

我的选择是把 Bad Case 结构化记录：原问题、错误类型、期望事实、引用问题、处理状态和是否进入回归集。每次改检索、Prompt 或模型，至少回放这些样本，同时看引用覆盖、检索充分性、工具失败率、耗时和成本。

效果是改动不再只凭感觉。边界是评测集会被「刷题」，所以要按业务主题、版本和时间分桶，保留一部分未参与调优的样本。

### 面试官追问：LLM-as-Judge 能完全代替人工吗？

不能。它适合检查格式、是否引用、是否覆盖预期要点等相对稳定的规则。涉及业务正确性、合规和用户真实满意度，仍要有人审；而且 Judge 本身也要用人工标注样本验证一致性。

## 13．怎样做可观测、降级和成本控制？

**面试官常问：线上模型慢、贵、偶尔失败，你怎么处理？**

### 可以直接回答

背景是 AI 链路比普通 CRUD 多了模型、向量库、重排、外部搜索和工具调用，任何一环慢或挂掉都会影响用户。

我会先让每个请求有 traceId，记录路由、模型、检索数量、工具次数、耗时、错误和是否降级。然后按依赖分层处理：向量库慢时可以回退 BM25／ES；Rerank 失败时用混检结果；模型超时时用同一证据换备用模型或明确失败；没有联网 Key 时跳过联网而不是阻塞主链路。

成本上，简单问题不升级到重 Agent；每轮有限制 token、步骤和工具次数；对长上下文做去重、配额和摘要。这样既能控制钱，也能避免模型在无效循环里浪费时间。

效果是系统失败时仍有可解释结果，而不是白屏。边界是降级有质量下限：如果只剩低质量证据，正确行为是拒答，不是为了「可用率」编一个答案。

## 14．部署和生产稳定性怎么讲？

**面试官常问：你的 AI 应用怎么部署？依赖挂了怎么办？**

### 可以直接回答

我会把应用、PostgreSQL、Redis、向量库、Elasticsearch 等依赖容器化，并给每个服务提供健康检查。配置和密钥只放环境变量或密钥管理，不进 Git、不回传到前端、不写到日志。

但「Docker 能跑」不等于生产就绪。生产还需要关心数据备份、数据库迁移审批、索引重建、限流、日志保留、告警、发布回滚和外部模型依赖的降级策略。

我的选择是先把本地／测试环境的 Compose 和健康检查跑通，再把高风险操作单独列为发布前检查项。例如换 embedding 模型必须验证维度和重建索引；数据库 migration 必须可回滚并有备份；外部 API Key 缺失不能让整个应用起不来。

效果是应用启动问题和业务问题能分开定位。边界是本地验证不能替代真实生产压测、备份恢复演练和安全审计，面试时要诚实区分。

## 15．AI 编程工具怎样使用才算工程能力？

**面试官常问：你使用 Codex／Claude Code／Cursor 吗？会不会被 AI 替代？**

### 可以直接回答

我把 AI 编程工具当成提高分析、编码和测试速度的助手，不把它当成架构决策者。它适合生成重复样板、补测试、查调用链和整理文档；但数据 Schema、权限、密钥、迁移、发布和安全边界必须由工程师判断。

我的工作流是先定位问题和验收标准，再让 AI 协助实现局部代码，然后看 diff、跑测试、做真实接口验证。外部 SDK 或协议问题不能凭感觉试错，要对照官方文档和可运行参考实现。

效果是效率提升，同时变更可追溯。真正的壁垒不是打字速度，而是能否发现 AI 生成代码中的权限泄漏、幂等缺失、错误降级和长期维护问题。

## 16．最后的项目复盘题：你遇到过什么真实问题？

**面试官常问：讲一个你自己定位并修复的问题。**

### 可以直接回答

我遇到过一个很典型的历史兼容问题。后期给产研运工作流增加了 `lowCodeSchemas`，新任务都有这个字段，但 Redis 里已经存在的旧工作流没有。

用户点旧工作流详情时，后端会读取状态并刷新列表索引。索引代码直接对 `result.lowCodeSchemas.map(...)` 调用，没有做兼容判断，于是旧数据是 `undefined`，抛出 TypeError，Node 进程直接退出。表面看是「点详情服务挂了」，实际根因是新增状态字段没有考虑历史快照。

我先通过退出堆栈定位到索引写入，再检查 Redis 中旧工作流确认数据仍在。方案有两个：迁移历史 Redis 数据，或在读取边界做兼容。这里选择读取边界兼容：统一用 `result.lowCodeSchemas ?? []`，并增加回归测试模拟旧工作流详情访问。

效果是旧数据能正常打开，服务不会因单条历史数据退出。这个问题让我在后续做 Checkpoint、Artifact 和 Schema 演进时，都先考虑默认值、版本号、读取兼容和回归样本，而不是只测新建数据。

## 面试最后 30 秒：怎样收口

我做 AI Agent 全栈时，核心不是把模型接进网页，而是让模型进入一条受控的业务链路：前端有好的交互，后端有清晰边界，RAG 有引用和权限，Agent 有工具治理和恢复，运营上能看指标和回归 Bad Case。对于不确定或高风险的事情，系统宁可明确拒答或等待人工，也不把模型输出伪装成事实。

# 扩展题库：第 17～60 题

> 前 16 题是每个知识域的主问题，答案较完整。下面 44 题是同一知识域中最常见的追问与变体。每题都按面试口述写，答案可根据自己的项目替换细节。

## A．前端与全栈交付

### 17．流式消息为什么容易重复或乱序？

**答：**背景是 SSE 会重连，前端也可能同时收到临时片段和最终结果。最简单的做法是收到什么就直接拼字符串，但断线重连后很容易重复。我的做法是给一次回答绑定 `messageId`／`runId`，临时片段只更新同一条消息，最终事件用完整内容收口；重连时按事件序号补缺失片段。这样用户不会看到重复段落。边界是后端必须能提供稳定事件 ID，不能只靠前端猜。

### 18．AI 聊天页面怎样做取消？

**答：**用户停止生成时，前端先用 `AbortController` 断开浏览器连接；后端再把这个请求标记为 cancelled，Agent 每轮工具调用前检查取消状态。只取消前端不够，因为模型和工具可能还在烧钱；只取消后端也不够，因为页面还在等响应。对已经启动的写操作，取消不等于回滚，所以写工具必须幂等并记录执行状态。

### 19．为什么不能把模型输出直接渲染成 HTML？

**答：**因为文档和模型输出都可能带脚本、危险链接或伪造页面。常见做法是直接 `innerHTML`，或者使用 Markdown 渲染器并关闭原始 HTML。我选后者：Markdown 白名单渲染、原始 HTML 转义、外链新窗口打开并标记来源。效果是保留代码块、表格和引用体验，同时避免 XSS；边界是不能只靠前端，上传文档和后端返回也要做内容安全处理。

### 20．前端为什么还要知道检索充分性？

**答：**因为「模型返回了文字」不等于「系统有依据」。我会让后端明确返回 `retrievalSufficient`、引用和原因；前端资料不足时不展示一个像正确答案的高置信度样式，而是提示用户补充版本、地区或场景。这样效果是用户不会把拒答误以为系统故障。边界是这个标志由后端证据门禁决定，不能让前端自己按字数判断。

### 21．BFF 层有什么意义？

**答：**背景是管理后台往往要聚合多套服务，还要处理管理员权限。让浏览器直接调用每个内部服务会泄露拓扑和 Token，也会让权限逻辑分散。BFF 负责从浏览器登录态识别用户、检查权限、再带内部服务凭证访问 RAG 服务。效果是前端接口更稳定，核心服务不暴露内部认证；代价是多一层维护，所以只在多前端或权限复杂时采用。

### 22．接口错误为什么不能只返回 500？

**答：**AI 链路的失败有很多种：资料不足、权限拒绝、模型限流、工具超时、审批未完成。都返回 500，前端和用户都无法知道下一步。我把它们区分成可重试、可降级、需要用户补充、需要管理员处理四类，并返回稳定错误码和 traceId。效果是前端可以给不同提示，运维也能定位；边界是错误信息不能暴露密钥、内部地址或其他用户的数据。

## B．后端、任务与数据一致性

### 23．文档上传为什么要异步？

**答：**上传后的解析、OCR、切片、embedding 和索引可能持续几分钟。把这些都塞进一次 HTTP 请求，网关超时就会导致用户重复提交，还可能重复入库。我的做法是上传先落原文件和任务记录，立即返回 taskId；后台任务完成后更新状态，前端轮询或订阅进度。效果是用户体验稳定，也方便失败重试。边界是任务状态必须持久化，不能只存在内存。

### 24．怎么防止用户重复点「开始生成」？

**答：**前端禁用按钮只能减少误点，不能防并发请求。服务端要接受幂等键，例如 `userId + requestId`，第一次请求创建任务，重复请求返回同一任务结果。对于发奖、发邮件、创建订单这类写操作，还要在数据库或外部系统上做唯一约束。效果是网络重试不产生重复副作用；边界是幂等键要有合理过期时间，不能永久占用。

### 25．Redis 在 Agent 系统中用来做什么？

**答：**我不把 Redis 当数据库替身。它适合短期缓存、分布式锁、限流、会话／任务检查点和队列状态。核心业务事实仍落关系型数据库，方便查询、审计和备份。比如 Agent 的暂停状态可以放 Redis Checkpoint 并设置 TTL，但重要 Artifact 和审批记录需要持久化。这样既快又不会因 Redis 重启丢掉业务事实。

### 26．任务失败后怎样判断该重试还是该人工处理？

**答：**先按失败类型分类。网络抖动、临时限流通常可以有限次数重试；输入缺证据、权限不足、Schema 不合法，重试不会变好，应该直接返回 blocked 或让用户补充；外部写操作未知是否成功时，不能盲重试，要先查幂等记录。效果是避免「自动重试十次」这种假可靠。每次重试也要记录次数、原因和最终状态。

### 27．为什么说数据库 migration 是高风险操作？

**答：**因为它改变的是已经存在的数据结构，不只是代码。常见错误是本地 `synchronize` 看起来没问题，上生产后锁表、数据回填失败或旧服务读不到新字段。我的原则是：先做向后兼容代码，再执行可审查 migration，必要时双写／回填，验证后再删除旧字段。没有备份和回滚方案，不把 migration 当普通发布。

## C．模型与结构化输出

### 28．temperature、max tokens 这些参数怎么调？

**答：**不是越大越好。抽取、分类、路由这类任务需要稳定，所以 temperature 低；创意文案才允许更高随机性。max tokens 按任务上限设置，避免无限输出和成本失控。调参前我会先看失败样本：是遗漏信息、格式不稳还是事实不准，再决定改 Prompt、Schema、检索还是参数。只靠「把 temperature 调低」解决不了检索错误。

### 29．上下文窗口不够时怎么办？

**答：**不能把所有文档硬塞进模型。主流方法是扩大模型、做摘要、按检索结果只放相关片段、或者分阶段处理。我优先做检索、去重、每类证据配额和摘要；真正需要全局理解时再分层汇总。效果是成本和延迟可控。边界是摘要会损失细节，所以规则表、代码和数字类内容要保留原片段作为引用。

### 30．模型路由怎么避免把简单问题做复杂？

**答：**我会先用规则和轻量判断识别是否涉及内部资料、是否需要工具、是否是开放常识。简单公共问题直接回答；涉及私域资料必须检索；多步问题才升级 Agent。主流方案是全部交给一个大模型判断，但成本高且不稳定。我的选择是规则先兜底、模型做补充，最后把路由和原因记录下来，方便回放纠错。

### 31．结构化 Schema 怎么演进？

**答：**新增字段时不能默认所有历史产物都有。做法是给 Schema 加版本，读取时给旧字段默认值或做转换，写入时使用最新版本；删除字段要经历兼容期。项目里新增 `lowCodeSchemas` 后，旧工作流详情曾因直接 `.map` 崩溃，后来改为 `?? []` 并加回归测试。这个例子说明 Schema 演进首先是数据兼容问题，不只是 TypeScript 类型问题。

### 32．工具调用返回错误，应该把原错误给模型吗？

**答：**不能原样塞。数据库报错、HTTP 响应、内部路径可能泄露信息，也可能被模型误用。我会把错误规范成 `code`、`message`、`recoverable`、`retryAfter` 这类安全字段，让模型知道能否换方案；原始错误只进受控日志。效果是模型有足够信息决策，又不扩大泄露面。

## D．RAG 深挖

### 33．表格和代码块为什么不能随便切？

**答：**规则表的表头和一行配置是一个整体；代码块缺前后文也可能改变语义。固定长度切块会把它们拆开，模型拿到半张表就会误判。我在切分时保留标题路径，表格切块重复表头，代码围栏作为原子块。效果是检索到的片段更能独立理解；代价是有少量重复 token，但比答错业务规则便宜。

### 34．embedding 模型怎么选？

**答：**先看语言、领域、维度、成本、延迟和已有索引兼容性，而不是只看榜单。中文企业文档要验证中文专有名词、表格和短查询；选定后用自己的评测集对比 Recall@K 和人工相关性。最重要的是，一旦换 embedding，向量维度和空间变了，不能把新向量和旧向量混用，通常要新建索引并重建。

### 35．RRF 的作用是什么？

**答：**关键词和向量排序的分数不在同一个尺度，不能简单相加。RRF 不直接比原始分数，而是按每个结果在各自榜单里的名次做融合。它简单、稳健，适合先把两路候选合并；之后再交给 Rerank 做更细的语义排序。效果是精确词和语义相近都不容易被一条链路压死。

### 36．Query Rewrite 会不会改坏用户问题？

**答：**会，所以不能让模型任意重写。我的原则是保留项目名、版本号、地区、接口名等实体，只补同义表达或拆成少量检索子问题。重写结果要有限制数量，并能回显到 trace 里。对短事实问题或用户明确原句时，宁可不改写。效果是提高召回同时不把「查 A 版本」改成泛泛的「查产品说明」。

### 37．如何处理文档删除、废弃和新版本？

**答：**不能只删数据库记录。文档生命周期变化要同步关系库、向量库、关键词索引和缓存；查询时仍要按 active／version 过滤，防止向量库残留命中。新版本通常先入库并审核，通过后生效，旧版本标记废弃而不是立刻物理删除。效果是答案能说明引用的是哪个版本，也能避免历史规则混进当前回答。

### 38．怎么排查「检索到了但回答不对」？

**答：**我按三层排：第一层看候选是否真的包含正确证据；第二层看 Rerank 是否把正确片段排掉；第三层看生成是否忽略了证据或引用校验放得太松。不能一看到答案错就改 Prompt。通过 trace 保存 query、候选、排序、最终上下文和回答，才能判断根因。这个过程也是 RAG 与普通搜索最大的工程差别。

## E．Agent 与多 Agent

### 39．Planner 和 Router 有什么区别？

**答：**Router 决定「这类问题走哪条路径」，比如直接回答、RAG、Agent；Planner 决定「在一条复杂路径中先做哪几步」。简单问题只要 Router，不需要 Planner。复杂研究问题可以 Planner 拆检索子问题、安排工具顺序。把两者混成一个万能 Prompt，后期很难知道是选错路径还是计划错了。

### 40．Agent 的长期记忆应该存什么？

**答：**只存跨会话仍有价值、且允许存储的偏好和稳定事实，例如用户的角色、常用项目、长期约束。一次性任务、临时指令、模型自己猜测的事实不能直接写长期记忆。写入前要分类，读取时按用户隔离，并支持查看、纠正、删除。否则记忆会变成长期污染源。

### 41．工具能并行调用吗？

**答：**能，但要先看依赖关系和预算。独立的检索、天气、库存查询可以并行，减少总耗时；后一个工具依赖前一个输出时必须串行。并行还要限制最大数量，避免模型一次发几十个请求。我的做法是把并行能力写进工具策略，而不是让模型随便 Promise.all。

### 42．多 Agent 的岗位 Contract 怎么写？

**答：**每个岗位至少要有输入、输出、可用证据、禁止决策范围、成功条件和下游消费者。例如产品输出规则与验收口径，后端输出接口与幂等策略，测试输出用例和上线门禁。输出最好是 Markdown 交付物加结构化 Schema，而不是一段自由对话。这样下游能消费，审批也知道审什么。

### 43．Agent 反思重试怎么避免自我循环？

**答：**反思不是让模型无限说「我再想想」。只在明确失败信号出现时触发，例如引用校验不通过、工具返回可恢复错误；每次反思必须改变策略，比如补检索、换模型、缩小问题，而不是原样再问一次。次数受预算和步骤限制，到上限返回已知不足。这样反思才是受控修复，不是昂贵循环。

### 44．人工审批应该放在哪一步？

**答：**放在不可逆或业务高风险动作之前，例如发奖、发邮件、修改生产配置、对外发布。只读检索或生成草稿通常不需要审批。审批内容不能只显示「是否同意」，还要给用户看计划、证据、影响范围和风险；审批结果与 feedback 写入任务状态。这样人工是决策者，不是盲点确认按钮。

## F．MCP、评测与观测

### 45．MCP Server 怎么做权限控制？

**答：**把 MCP 当成一个外部客户端，而不是可信本地脚本。它要使用 API Key 或服务 Token，工具按读写和角色分级，参数经过 Schema 校验，调用记录审计。默认只暴露只读检索、上下文和状态查询；写操作要么不提供，要么走同样的审批流程。这样 Codex／Claude 接入时不会自动拥有数据库或文件系统权限。

### 46．为什么要导出 Markdown、Schema 和证据三份交接物？

**答：**Markdown 方便人和 AI Coding 工具读完整业务背景；Schema 方便机器稳定消费页面、接口、埋点和验收规则；证据让实现者知道哪些结论有依据、哪些仍待确认。只给 Markdown 容易被模型自由发挥，只给 JSON 又缺业务语义。三者一起能让 Codex、Claude、Cursor 在实现时既有约束也能追溯来源。

### 47．离线评测集怎么做才有用？

**答：**先收集真实问题，按业务主题、难度、版本、地区和权限分桶；每题定义期待事实、必须引用的来源、不能回答的边界。不要把所有样本都拿来调 Prompt，要留一部分作为盲测。每次改检索、模型或 Agent 都跑同一套集，比较引用正确率、拒答正确率、耗时和成本。这样才能判断改动是否真的改善。

### 48．用户点了差评，下一步是什么？

**答：**差评不是直接喂给知识库。先记录原问题、回答、检索快照、用户评论和错误类型；人工判断是资料缺失、检索错误、生成错误还是用户期望不清。确认后的纠正可以成为 Bad Case 回归样本，正式知识仍要走文档审核。这样不会因为一次情绪化反馈把错误内容永久写入系统。

### 49．Trace 里最少应该记录什么？

**答：**至少有 traceId、用户／租户、请求路由、模型、token／耗时、检索数量、工具调用、降级原因、最终状态和错误码。不要记录明文 API Key、密码或不必要的原文敏感数据。Trace 的价值是把一次「回答不好」拆回每一步，而不是留一条「请求失败」日志。

### 50．LLM-as-Judge 怎样防止自嗨？

**答：**Judge 适合做辅助判定，例如格式是否合规、引用是否存在、是否覆盖预期要点；不适合单独决定复杂业务事实。先用人工标注的一小批样本验证 Judge 和人工的一致性，再决定它能覆盖哪些规则。Judge 的 Prompt、模型版本和评分标准也要版本化，否则今天的 0.8 和明天的 0.8 未必是一回事。

## G．稳定性、部署与业务判断

### 51．怎么控制一次 Agent 请求的成本？

**答：**成本来自模型 token、工具调用和失败重试。我先做路由，简单问题不进重 Agent；再限制最大步骤、最大工具数、每次上下文大小和重试次数；最后记录模型和任务维度的成本。超过预算时返回当前进度与终止原因，不能偷偷继续。这样成本是产品规则，不是月底账单出来才发现。

### 52．模型或向量库整体不可用时，系统应该怎样表现？

**答：**先区分依赖。向量库不可用可以回退关键词检索；Rerank 不可用可以保留混检结果；主模型不可用可以换备用模型；所有可用证据都不足时返回资料不足。最重要的是告诉用户发生了什么级别的降级，并在监控里报警。不能用一个通用「系统繁忙」掩盖所有原因。

### 53．健康检查应该检查什么？

**答：**最基础是服务进程活着；更进一步要检查数据库、Redis、向量库、关键词索引、对象存储和关键外部模型是否可访问。但健康检查不必每次都跑昂贵模型请求，否则会制造成本。我的做法是区分 liveness 和 readiness：前者看进程，后者看是否具备处理核心请求的依赖条件。

### 54．发布新模型或新 Prompt 怎么灰度？

**答：**先离线评测，确认不退化；然后按用户、租户或少量流量灰度，记录旧新版本的答案质量、延迟、成本和错误率；出现异常可切回旧版本。Prompt 和模型配置都需要版本号，不能手改环境变量后不知道线上跑的是什么。对于 embedding，灰度更谨慎，因为它涉及重建索引。

### 55．怎么判断一个业务不该用 Agent？

**答：**如果规则固定、输入结构化、结果可用普通流程引擎或表单完成，就不该为了 AI 强行上 Agent。Agent 适合规则不完整、要理解自然语言、需要按上下文选择工具的场景。我的判断标准是：Agent 带来的决策价值能否覆盖它的不可预测性、延迟、成本和治理成本。不能覆盖就选传统系统。

### 56．业务方只说「做个智能体」，你先问什么？

**答：**我会先问用户是谁、要替他完成什么动作、现有流程多久、输入来自哪里、哪些事实可作为依据、哪些动作不可逆、成功如何衡量、谁负责兜底。拿不到这些信息就先做需求澄清或只读 Demo，不承诺自动执行。这样能避免一开始就造一个泛化 Agent，最后没有业务验收标准。

### 57．如何定义 AI 项目的 MVP？

**答：**MVP 不是把所有能力都砍掉，而是只保留一条能闭环的用户路径。比如先支持一类已审核文档、一个角色、只读 RAG 问答、引用和反馈；验证价值后再加多 Agent、联网、长期记忆和更多数据源。每期都要有输入、输出、失败边界和验收指标。这样两周内就能得到真实反馈。

### 58．遇到一个线上 AI 问题，排障顺序是什么？

**答：**先确认影响范围和 traceId，不急着改 Prompt。然后按输入、权限、检索、排序、上下文、模型、工具、输出校验逐层看。每层问「输入是什么、输出是什么、是否符合契约」。如果是外部协议问题，先对官方文档和可运行样例，不靠猜测反复试。修复后要补回归样本，避免同一类问题再次出现。

### 59．你怎样和产品、算法、测试协作？

**答：**产品负责业务目标和验收口径，算法／AI 负责模型能力边界，工程负责把它变成稳定服务，测试负责把规则、异常和回归固化。我会用 Artifact 或结构化交接物明确每一方的输入输出，而不是在群聊里同步一段模糊描述。争议点回到证据、接口契约和验收案例，不靠谁声音大。

### 60．如果面试官问「你最大的收获是什么」，怎么答？

**答：**我最大的变化是，不再把 AI 应用理解成模型调用。真正困难的部分是：资料是否可信、谁有权限、工具会不会误执行、任务中断后怎样恢复、改动后怎样证明没有退化。模型能力会变化，但这些工程问题长期存在。所以我现在做方案时，会先定边界、证据、状态和验收，再决定用哪个模型或框架。
