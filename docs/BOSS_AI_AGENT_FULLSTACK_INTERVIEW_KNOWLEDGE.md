# AI Agent／AI 应用全栈岗位考察知识点（20K＋）

依据：[BOSS AI Agent／AI 应用全栈岗位（20K＋）要求检索](./BOSS_AI_AGENT_FULLSTACK_20K_PLUS.md)。

适用岗位：AI Agent 全栈开发工程师、智能体全栈开发工程师、AI Agent 应用全栈研发工程师、AI Native 全栈工程师、AI 应用研发工程师（全栈）。

## 一、结论：要掌握到什么程度

20K＋岗位考察的不是「会不会接 OpenAI API」，而是能否把 AI 能力做成有前端体验、有后端边界、有数据与权限、有质量治理、可部署和可复盘的产品。

| 目标薪资带 | 面试预期 | 必须达到的掌握程度 |
| --- | --- | --- |
| 20–30K | 可独立交付一个业务 AI 应用 | 能从需求到上线完成前后端、RAG 或单 Agent，并能解释异常、权限、成本和测试；一条主后端栈＋React／Next.js 熟练。 |
| 30–40K | 可负责核心模块／小型平台 | 能设计 Agent 工作流、工具治理、RAG 质量门禁、任务恢复与观测；能拆模块、带联调并给出权衡。 |
| 40K＋ | 可主导平台或复杂业务方案 | 能设计多租户 AI 平台、模型网关、编排运行时、评测与发布治理；能从业务指标、可靠性、安全、成本四个维度做架构决策。 |

### 掌握等级定义

- **了解**：能说清定义、适用边界和基本流程。
- **熟练**：能在现有项目中独立实现、写测试、排故，并说明替代方案的取舍。
- **可主导**：能从零做设计，拆分风险和里程碑，制定数据／权限／观测契约，并为线上故障负责。

> 20–30K 的最低线是「熟练」；30K＋至少有 2～3 个核心方向达到「可主导」。

## 二、岗位考察知识地图

```text
业务问题与产品指标
        ↓
前端体验 ←→ 后端 API／鉴权／数据
        ↓              ↓
  流式对话／工作流       LLM 网关／模型选择
        ↓              ↓
     Agent 编排 ←→ 工具调用／MCP／权限
        ↓              ↓
      RAG 检索、引用、评测、记忆
        ↓
观测、成本、灰度、部署、Bad Case 回归
```

## 三、必考模块与掌握标准

| 模块 | 知识点 | 20–30K：至少熟练 | 30K＋：至少可主导 | 常见考法 |
| --- | --- | --- | --- | --- |
| 前端 AI 交互 | React／Next.js、TypeScript、状态管理、SSE、流式渲染、Markdown／引用卡片、错误重试 | 能完成聊天、流式 token、取消、引用展示和会话状态；理解 XSS 与渲染安全 | 设计长任务进度、任务恢复、动态表单／工具确认、多端体验和前端性能策略 | 「SSE 断线如何恢复？流式消息怎样避免重复追加？」 |
| 后端服务 | Node.js／NestJS 或 Python／FastAPI；REST／SSE；DTO 校验；数据库；缓存；队列 | 能设计 API、鉴权、参数校验、异步任务、事务边界、错误码 | 服务拆分、幂等、限流、超时、重试、死信／补偿、读写扩展与容量估算 | 「为什么 LLM 长任务不能同步 HTTP 等待？」 |
| 身份与多租户 | JWT、RBAC／ABAC、服务间认证、资源归属、审计 | 所有文档、会话、任务、Artifact 均按用户／租户过滤；不信任前端传来的 ownerId | 设计租户隔离、管理员越权边界、服务 Token、敏感数据脱敏与审计取证 | 「怎样防止 A 用户通过 docId 读取 B 的知识？」 |
| LLM 基础与网关 | Token、上下文窗口、温度、超时、重试、限流、模型能力差异、OpenAI 兼容协议 | 能接入至少两个 Provider，处理流式与非流式失败，记录耗时与 token 成本 | 设计模型路由、Fallback、配额、熔断、灰度和成本预算；不会把密钥暴露给前端 | 「什么时候切便宜模型，什么时候必须升级模型？」 |
| 结构化输出 | JSON Schema／Zod、Function Calling、输出修复与降级 | 用 Schema 约束模型输出，校验失败后重试或降级，拒绝直接信任模型 JSON | 设计版本化 Schema、兼容旧产物、工具输入输出契约与回归样本 | 「模型返回字段缺失／类型错了，系统怎么办？」 |
| RAG 数据链路 | 解析、清洗、切片、embedding、索引、metadata | 能解释 chunk 大小／overlap；实现文档入库、向量检索和基本引用 | 根据文档结构、版本、地区、权限设计切片与元数据契约，并处理删除／重建索引 | 「为什么同一份文档检索到了却仍答错？」 |
| RAG 检索质量 | BM25、向量、混检、RRF、Rerank、召回／精度、拒答、引用 | 能实现或接入混检与 rerank，基于 score／规则做资料不足拒答 | 设计评测集、离线指标、线上质量门禁和 Bad Case 回归；能定位是召回、排序还是生成问题 | 「Rerank 失败要不要让问答整体失败？」 |
| Agent 设计 | ReAct、Router、Planner、状态机／DAG、单 Agent 与多 Agent 的边界 | 能实现单 Agent 工具调用循环，有最大步数、超时与停止条件 | 为有明确依赖的任务设计 DAG、岗位契约、上下文裁剪、并行／汇聚与局部重跑 | 「什么时候不该用多 Agent？」 |
| 工具治理与 MCP | Tool Schema、白名单、权限、确认、幂等、MCP 生命周期与传输 | 工具参数经校验，设置超时／重试；读写工具权限分离 | 设计 Tool Registry、危险操作审批、审计、MCP Server 的最小权限与故障隔离 | 「模型能生成 SQL，是否可以直接执行？」 |
| 长任务恢复 | Checkpoint、状态快照、Human-in-the-loop、重试、预算 | 支持人工审批后继续；知道中断点前不能有不可重放副作用 | 设计 snapshot 版本、幂等键、恢复剩余预算、任务队列、局部重跑和补偿策略 | 「服务重启后，如何从第 4 步继续而不是重跑？」 |
| 记忆与上下文 | 短期会话、长期记忆、召回、更新、遗忘与注入风险 | 区分会话上下文与长期记忆，避免把临时指令永久写入 | 设计记忆抽取／审核／过期／权限与提示注入防线 | 「记忆错了会怎样纠正？」 |
| 评测与观测 | Trace、日志、指标、Eval、Bad Case、成本／延迟／成功率 | 能给关键链路加 traceId、错误日志、延迟与调用次数；写基础回归测试 | 建立 golden set、LLM-as-Judge 的边界、线上采样、告警、版本对比和发布门禁 | 「如何证明新 Prompt／模型切换真的更好？」 |
| 部署与工程质量 | Docker、环境配置、CI、迁移、健康检查、回滚 | 能容器化前后端与依赖，区分配置／密钥，提供 health check 与启动文档 | 设计发布策略、灰度、回滚、依赖可用性降级、备份与灾难恢复 | 「向量库超时，用户请求怎样降级？」 |
| 产品与业务 | 场景拆解、用户路径、指标、验收、风险控制 | 能把业务需求写成接口、状态、验收条件和异常分支 | 从 ROI、风险、合规、人工介入成本选择 Agent 化边界，推动跨团队交付 | 「这个任务为什么适合／不适合做 Agent？」 |
| AI 编程协作 | Codex／Claude Code／Cursor 的正确使用、代码审查、测试、文档 | 用 AI 提效但能验证生成代码、补测试、排错和保护密钥 | 建立团队的 Spec／Review／Eval／安全门禁，不把 AI 输出直接当生产事实 | 「AI 生成了一段能跑的代码，如何判断能否上线？」 |

## 四、面试高频题库（按考察目标）

### A．全栈交付与系统设计

1. 设计一个企业知识助手：前端、后端、RAG、权限、流式、异步入库分别怎样划分？
2. 为什么聊天问答可用 SSE，而文档解析／Agent 长任务更适合任务队列＋轮询／事件？
3. 如何设计一个支持取消、断线重连、继续查看结果的 Agent 任务页面？
4. 怎样给 API 设计幂等键？哪些写操作必须做到幂等？
5. 用户投诉「页面显示回答成功，但引用为空」，如何定位前端、网关、检索和模型链路？

### B．RAG 与可信回答

6. Chunk 如何按 Markdown 标题、表格、代码块、图片 OCR 切分？为什么不能只按固定字符数？
7. BM25、向量检索、RRF、Rerank 各解决什么问题？怎样确定先后顺序？
8. 检索分数高却答错，可能是哪三层的问题？如何逐层验证？
9. 文档有版本、地区和部门权限时，过滤应在检索前、检索后还是生成前？为什么？
10. 如何实现「引用可追溯」与「资料不足时拒答」？
11. 如何构建 RAG 评测集，避免只测模型记住的答案？

### C．Agent、工具与恢复

12. ReAct 自由循环和 LangGraph／DAG 的适用边界是什么？
13. 一个 Agent 反复调用同一个工具，如何止损并给用户可解释结果？
14. Tool Calling 的模型参数为什么必须经过服务端 Schema、权限和审批？
15. MCP 是什么，不是什么？它与普通 HTTP API、Function Calling 的关系是什么？
16. 人工审批中断后怎样恢复？`interrupt` 节点为什么必须可重放？
17. 多 Agent 如何定义岗位输入／输出 Contract，怎样避免上下文污染和互相甩锅？

### D．模型、平台与治理

18. 多模型如何按任务路由？怎样处理模型不可用、超时、限流和预算耗尽？
19. 如何防止 API Key 进入前端、日志、Git 和导出 Artifact？
20. 多租户平台中，向量库和缓存 key 怎样设计才能不串数据？
21. 为什么模型切换不只是改一个环境变量？embedding 维度、索引与历史数据如何处理？
22. 线上怎样度量 Agent 成功率、引用质量、工具失败率、成本和人工介入率？
23. Bad Case 如何从用户反馈进入回归集，并防止错误知识直接污染正式知识库？

### E．业务判断与交付能力

24. 给「自动审批／自动发奖／自动发布」类需求，如何划分可自动化与必须人工确认的边界？
25. 业务方只说「做一个智能体」，你会追问哪些信息后才开始设计？
26. 如何把复杂 AI 项目拆成 2 周内可验收的 MVP，而不是先造一个通用 Agent 平台？

## 五、每个层级的最低验收任务

| 目标 | 可验证任务 | 完成标准 |
| --- | --- | --- |
| 20–30K | 做一个带登录的企业知识助手 | 文档入库 → 混合检索 → 带引用问答；React 流式界面；后端有鉴权、超时、日志与 Docker 启动说明。 |
| 30–40K | 加入受控 Agent 工作流 | 能路由、拆任务、调至少 3 个受控工具；有预算／超时／审批／Checkpoint；有最少一套评测集和 Bad Case 回归。 |
| 40K＋ | 抽象成可运营 AI 平台 | 支持多租户、模型路由、工具／MCP Registry、可观测与权限审计；说明 SLA、成本、灰度、数据迁移与回滚方案。 |

## 六、复习优先级

### P0：必须能写、能讲、能排错

- TypeScript＋React／Next.js、Node.js／NestJS 或 Python／FastAPI。
- SSE、JWT／RBAC、数据库与 Redis、Docker、API 契约和错误处理。
- RAG：切片、混检、Rerank、权限过滤、引用、拒答、评测。
- Agent：工具调用、Schema 校验、超时／预算、状态机、审批与恢复。

### P1：决定能否拿到 30K＋

- 多模型 Provider 与成本／可靠性治理。
- 多 Agent 的边界、DAG、并行、Artifact Contract、局部重跑。
- MCP、工具 Registry、危险操作审批、审计。
- Trace、指标、Bad Case 回归、线上质量门禁。

### P2：平台／架构岗的拉分项

- 消息队列、分布式任务、幂等与补偿事务。
- 多租户隔离、模型网关、向量索引迁移、灰度／回滚。
- SLO／SLI、容量和成本模型、企业安全与合规。

## 七、不能只停在这些层次

- 只会写 Prompt，不能解释 RAG、工具权限与异常恢复。
- 只会调 LangChain／LangGraph API，不能说明状态、预算、幂等和停止条件。
- 只会做聊天页面，不能处理流式断线、会话归属、引用和失败降级。
- 只会列框架名，不能拿出可运行 Demo、测试、观测数据和清晰的架构取舍。
- 把多 Agent 当默认方案；对于固定流程，状态机／DAG 通常比自由 Agent 群聊更可控。
