# 企业级知识库课程与 v1～v9 对照优化建议

> 分析范围：`/Users/monster/Downloads/course` 中 11 份课程 PDF、`/Users/monster/Documents/GitHub/code/knowledge-hub-backend` 的 `origin/v1`～`origin/v9`，以及当前 RAG 项目的实际代码。
>
> 结论口径：只把已在代码中核验的能力记为“已有”；课程描述但当前项目没有实际调用链的能力记为“缺口”；不建议为了技术栈数量直接照搬 MongoDB、RabbitMQ 等组件。

## 一、结论

当前项目整体能力已经明显超过课程 v1～v9，课程中的多格式入库、异步索引、Elasticsearch、Neo4j、JWT、用户管理和后台 RBAC 都已有对应实现，部分能力更完整。

真正值得结合当前项目补强的内容有 5 项：

1. **P0：文档数据权限贯穿全部检索源。** 当前已有 `document_permissions` 和权限缓存，但在线检索主链仍主要按 `userId`、`roleScope` 和业务范围过滤。需要让 PostgreSQL ACL（注：文档访问控制列表）统一约束 Milvus、Elasticsearch、BM25、Karpathy 和 Neo4j，才能形成“后台授权后，问答立即按权限生效”的闭环。
2. **P0：文档审核状态与知识生命周期分离。** 当前有 `draft／confirmed／effective／deprecated` 版本生命周期，但缺少独立的“待审核、通过、驳回、重新提审”状态机和审核记录。不能让上传人直接把未经审核的文档标成 `effective`。
3. **P1：PPTX／Office 结构化解析与降级。** 当前支持的格式比课程更多，但 PPTX 仅抽取文本节点，未保留标题、表格和段落结构，也没有备用解析器。可吸收 v2 的“自研解析优先、通用解析器降级”设计。
4. **P1：Elasticsearch 命中片段高亮。** 当前 ES 已完成 IK 中文分词、BM25 和业务元数据过滤，但没有返回 `highlight`。搜索后台无法直观看出关键词为什么命中。
5. **P1：异步入库失败任务运营闭环。** 当前 BullMQ 已有 3 次指数退避重试和失败任务保留，但后台只有队列计数，缺少失败任务列表、错误详情、人工重试和幂等重放入口。

不建议新增 MongoDB，也不建议用 RabbitMQ 替换 BullMQ。当前 PostgreSQL、对象／文件存储、Milvus、Elasticsearch、Neo4j、Redis 的职责已经清晰；再增加正文 MongoDB 会引入跨库事务、版本一致性和运维成本。BullMQ 也已经复用项目现有 Redis，满足当前异步文档任务需要。

## 四、建议一：统一文档 ACL 到所有检索源（P0）

### 当前问题

`DocumentPermissionService` 可以保存用户、角色、部门和公开授权，但当前权限解析只读取公开、用户和角色授权，尚未解析部门成员关系；`KarpathyRagService` 的主检索主要按 `userId` 和 `roleScope` 过滤，Elasticsearch 也主要用 `userId` 和业务 Scope（注：项目、活动、地区、角色等查询范围）过滤。

这会产生两个风险：

- 管理员把文档授权给另一个用户或角色后，对方未必能从所有检索源召回该文档。
- 某个召回源若只校验业务字段而遗漏 ACL，可能形成跨权限引用风险。

### 推荐用户流程

```text
管理员进入文档管理
→ 打开“权限设置”
→ 选择用户／角色／部门／公开范围
→ 保存授权
→ 被授权用户重新提问时可以召回该文档
→ 未授权用户在 Simple／Auto／Agentic 中均无法看到该文档及引用
```

### 推荐数据／状态流程

```text
保存权限
→ PostgreSQL 更新 document_permissions
→ Redis 失效 doc-acl:* 权限缓存
→ 根据用户、角色和部门成员关系计算 allowedDocIds（注：当前用户可读取的文档 ID 集合）
→ 同一个 allowedDocIds 传给 BM25、Elasticsearch、Milvus、Karpathy 和 GraphRAG
→ RRF 融合后再次执行统一 ACL 终检
→ 只允许通过终检的 Chunk 进入 Rerank、Prompt 和引用列表
```

### 验收标准

- 同一文档对“拥有者、被授权角色、无权限用户”产生三组可重复的检索结果。
- Simple、Auto、Chat Agentic、MCP `rag_search／rag_ask` 的权限结果一致。
- 权限撤销后不需要重建向量即可立即失效。

## 五、建议二：文档审核与版本生命周期分离（P0）

### 当前问题

当前 `lifecycleStatus` 同时承担“版本是否生效”和部分“内容是否可用”的语义，但它不是审核记录。版本状态与审核状态应分开：

- `lifecycleStatus`：`draft／effective／deprecated`，回答“哪个版本在线生效”。
- `reviewStatus`：`draft／pending_review／approved／rejected`，回答“内容是否经过人工审核”。

`confirmed` 可以逐步收敛为审核结果或兼容状态，避免与 `approved` 重复表达。

### 推荐用户流程

```text
上传人上传或创建新版本
→ 系统完成解析、质量检查和索引预构建，状态保持草稿
→ 上传人点击“提交审核”
→ 审核人在文档管理查看正文、解析质量、来源、权限和版本 Diff
→ 审核通过：允许设为生效
→ 审核驳回：填写原因，上传人修改后重新提审
```

### 推荐数据／状态流程

```text
上传成功
→ lifecycleStatus=draft，reviewStatus=draft
→ 提交审核：reviewStatus=pending_review，记录 submittedBy／submittedAt
→ 审核通过：写入审核记录，reviewStatus=approved
→ 人工点击“设为生效”
→ PostgreSQL 事务切换版本链：目标版本 effective，旧版本 deprecated
→ 同步更新 Elasticsearch／Karpathy 生命周期；Milvus 查询依赖终检立即生效

审核驳回
→ reviewStatus=rejected，保存 reviewer／reason／reviewedAt
→ 不进入在线回答
→ 修改后生成新修订并重新提交
```

### 实施边界

该项需要新增或调整数据库字段／审核记录表，属于数据库 Schema 变更。按项目红线，真正实施前需要主人单独确认迁移方案；本轮只记录建议，不执行迁移。

## 六、建议三：PPTX／Office 解析质量增强（P1）

### 当前问题

当前 PPTX 解析只从 `slideN.xml` 提取 `<a:t>` 文本并按页拼接，可能丢失：

- 标题和正文层级。
- 表格的行列结构。
- 显式换行和段落边界。
- 自研解析失败后的备用路径。

### 推荐实现

保留当前零额外服务的快速解析，在其上吸收 v2 的设计：

```text
PPTX 上传
→ 主解析器：按 Slide 顺序读取 OOXML
→ 识别 title／ctrTitle 占位符并输出 Markdown 标题
→ 识别 a:tbl 并输出 Markdown 表格
→ 保留段落和换行，避免表格文字重复进入正文
→ 主解析失败或结果为空：调用通用 Office Parser 降级
→ 质量门禁检查标题数、乱码率、重复 Chunk 和正文长度
```

不建议直接复制课程实现，应抽取为当前 `document-parser.util.ts` 的内部策略，并补充 PPTX 表格、标题、空文档和损坏文件测试。

## 七、建议四：Elasticsearch 搜索高亮（P1）

### 当前问题

`ElasticsearchProvider.search()` 返回完整 Chunk 和分数，但没有请求或返回 Elasticsearch `highlight` 字段。管理后台只能看到命中文档，无法快速解释命中位置。

### 推荐用户流程

```text
用户进入智能搜索
→ 输入活动 ID、接口名、埋点字段或规则关键词
→ 结果列表显示标题、来源、分数和高亮片段
→ 点击结果打开原文对应 Chunk／父块
```

### 推荐数据流程

```text
Query 标准化
→ Elasticsearch BM25 检索
→ highlight.content 生成带安全标记的命中片段
→ 服务端只保留允许的高亮标签并限制片段长度
→ 返回 highlightFragments
→ 管理后台安全渲染，不直接注入任意 HTML
```

高亮只用于展示和可解释性，不参与 RRF 或 Rerank 分数，避免把展示字段误当成检索证据。

## 八、建议五：失败队列运营与幂等重放（P1）

### 当前问题

BullMQ 已有：

- `attempts=3`。
- `backoff=exponential`，初始 2 秒。
- 完成和失败任务保留 24 小时。
- Redis 不可用时同步降级。

缺少的是管理闭环，而不是再换一种消息队列。

### 推荐用户流程

```text
管理员进入“文档任务／失败队列”
→ 查看 waiting／active／completed／failed
→ 展开失败任务，查看失败阶段、错误、已重试次数和文档版本
→ 修复配置或补充资料
→ 点击“从失败节点重试”
→ 查看新任务状态和索引结果
```

### 推荐数据／状态流程

```text
任务进入 BullMQ
→ Worker 执行解析、质量门禁、切块和多索引写入
→ 可重试错误：最多 3 次指数退避
→ 最终失败：DocumentTask=failed，并保留 BullMQ failed job 24 小时
→ 人工重试前生成 idempotencyKey（注：防止同一文档版本重复写入的幂等键）
→ 已完成的安全步骤复用结果，失败步骤局部重跑
→ 成功后统一更新 PostgreSQL、外部索引状态和审计日志
```

## 九、暂不建议实施的课程方案

### 1. PostgreSQL＋MongoDB 双库正文存储

不建议。当前项目已经用 PostgreSQL 保存结构化文档和 Chunk、用文件／Obsidian 保存来源快照、用 Milvus／ES／Neo4j 保存检索派生数据。再加 MongoDB 不会直接提升召回质量，反而增加：

- PostgreSQL 元数据与 MongoDB 正文的跨库一致性。
- 删除、版本切换和回滚时的补偿逻辑。
- 备份、监控和本地启动成本。

若未来出现超大正文，应优先把原始文件／规范化 Markdown 放对象存储，PostgreSQL 只保存 URI、Hash、版本和审核状态。

### 2. 用 RabbitMQ 替换 BullMQ

不建议。当前文档任务与 Redis、Checkpoint、缓存共用基础设施，BullMQ 已覆盖重试、退避、任务状态和并发 Worker。只有在出现跨语言消费者、独立消息平台、复杂交换机路由或企业统一 RabbitMQ 基础设施时，才值得重新评估。

### 3. 重写 JWT、用户和后台 RBAC

不建议。当前管理后台已有角色、权限码、菜单过滤、按钮权限和接口守卫。课程 v7～v9 更适合作为核对清单，而不是替换现有实现。

## 十、推荐实施顺序

| 顺序 | 优化项 | 原因 | 是否涉及 Schema |
| --- | --- | --- | --- |
| 1 | 文档 ACL 统一检索门禁 | 直接关系企业知识安全和授权闭环 | 预计不需要，优先复用现有表 |
| 2 | 文档审核状态机 | 防止未经审核知识直接生效 | 需要，实施前单独确认 |
| 3 | PPTX 结构化解析与降级 | 提升真实业务资料入库质量 | 通常不需要；可能增加依赖，需先评估 |
| 4 | Elasticsearch 高亮 | 提升搜索后台可解释性和运营效率 | 不需要 |
| 5 | 失败任务列表与幂等重放 | 完成异步入库运营闭环 | 先复用现有任务表，通常不需要 |

建议第一批只做“ACL 统一门禁＋ES 高亮＋失败任务运营”，它们可复用现有数据结构，改动风险较低。文档审核状态机单独作为第二批，因为它涉及数据库迁移和现有 `confirmed` 语义调整。PPTX 解析增强应先用当前项目真实 PPTX 样本做基线测试，再决定是否引入通用 Office Parser。
