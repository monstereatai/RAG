## 服务边界问答：RAG 服务与后管是否该放一起（只读分析，未改代码）

结论：同仓库（pnpm workspace 纳管 backend / admin / admin-backend / frontend / rag-cli）合适；同进程、同部署单元不合适。现状已按 `docs/architecture/SERVICE_BOUNDARIES.md` 拆成两个 NestJS 服务，admin-backend 经 `modules/rag-client/` + `rag-service-token.ts` 以 HTTP 调 backend 的 `/api/v1/rag/admin/*`，不 import 内部 service —— 这个方向是对的。

已发现的 3 处边界泄漏（后续若要治理按此入手）：
1. **两份 `users` 表且不兼容**：`backend/src/providers/db/entities/user.entity.ts:15` vs `admin-backend/src/database/entities/user.entity.ts:4`，都叫 `@Entity('users')`，但前者主键 `varchar(64)` + `passwordHash` + 预留 `tenantId`，后者自增 `int` + `password` + `email` + `isActive`；默认库也不同（backend Postgres `rag` vs admin-backend MySQL `nestjs_enterprise`，见 `admin-backend/src/database/data-source.ts:33-39`）。管理员身份与知识库用户身份是两套，口径难对齐。
2. **运营接口两边各长一份**：`backend/src/modules/rag-admin|rag-ops-api|rag-gateway|agent-ops-admin|qa-ops` 与 `admin-backend/src/modules/rag-ops|qa-ops|rag-client` 并存。
3. **无共享包**：两个服务的 common（filters/interceptors/guards）、config、tracing、logger、circuit-breaker 各复制一份，文档也明说「当前不抽共享包」。

守则：可合仓库，不可共表、不可互相 import service；只走 `/api/v1` HTTP 契约 + service token。

## 追加：RRF 融合实现细节（追问核实）

- **手写实现，未调库**。全库无 `EnsembleRetriever` / `reciprocal_rank`，`langchain@1.4.5` 与 `@langchain/community` 均未用于融合。BM25（`bm25.util.ts`）与 RRF 都是自研。
- 排名依据 = **各通道的数组下标（名次）**，与原始分数无关。公式为加权 RRF：`totalScore = Σ w_c × 61/(61+rank_c)`，参数硬编码在 `karpathy-rag.service.ts:315-317`（`bm25Weight=0.3`、`cosineWeight=0.7`、`rrfK=60`，**不可用环境变量调**）。
- `fuseByRrf:2561-2610` **本身不排序**，只按 chunk id 累加；真正的降序排序在 `:718-720`（`applySourceAuthority → matchesScope → sort by totalScore desc`）。
- 存入的 `bm25Score` / `cosineScore` 是归一化原始分，**只用于诊断展示和标记 `retrievalSource`（hybrid/vector/bm25，`:727-732`），不参与排名**。
- 第 1 路 BM25 实际是 `mergeRankedHits` 合并后的单通道（ES + 本地，`:628`），所以不是"三路 RRF"。

### 两个疑似空转的配置（值得复核，非确证 bug）

1. `RAG_MIN_TOP_SCORE=0.05`（`.env.example:216`、`configuration.ts:200`）在 RRF 归一化下**几乎必然通过**：候选名次 ∈ [0, 20]，单通道最低贡献 `0.3×61/(61+20)≈0.229`，要跌破 0.05 需要名次 > 305。即只要召回非空，这道门禁就通过，真正卡"资料不足"的是 `RAG_MIN_RERANK_SCORE=0.65` 和词面重叠兜底（`assessRetrievalQuality:2948`）。
2. `RAG_SOURCE_AUTHORITY_RULES=` 默认为空（`.env.example:225`），`resolveSourceAuthorityWeight:2629` 直接返回 1，`applySourceAuthorityToChunk:2614` 命中 `weight === 1` 提前返回 —— L4 的"来源权威加权"默认是 **no-op**。

## 追加：现成 RRF 方案调研（"RRF 不是有专门的包吗"）

结论：有，且**本地依赖里已经躺了两个**，但都不适合直接替换当前手写实现。

**本地已有的两个：**

1. `@langchain/classic@1.0.38`（transitive 依赖，非直接声明）的 `EnsembleRetriever`，路径 `@langchain/classic/retrievers/ensemble`。实现见其 `dist/retrievers/ensemble.js:30-48`：`rrfScore[pageContent] += weight / (rank + this.c)`，rank 从 1 起，`c=60`，权重默认均分 `1/n`。**与标准 RRF（Cormack 2009）完全一致**；函数内自己排序返回。
   - 不适用的原因：去重键是 **`pageContent` 文本**（`_uniqueUnion`），不是 chunk id；只返回 `Document`，丢掉 `docId/chunkIndex/headingPath/docVersion/sourceAuthorityWeight` 等元数据；要求输入是 `BaseRetriever` 实例（需把本地 BM25 和 Milvus 包成 retriever）；融合后无法再插入权限/scope/权威过滤。
2. `@zilliz/milvus2-sdk-node@2.4.10` 的 `RRFRanker(k = 60)` / `WeightedRanker(weights)`，实现见 `dist/milvus/utils/Format.js:509/523`，**实测可从包根 import**，返回 `{strategy:'rrf', params:{k:60}}`。
   - 它只是**传给 Milvus 服务端 hybridSearch 的参数对象**，不是 JS 函数；作用域仅限**同一 collection 内多个向量字段**之间的融合（Milvus 2.4+ 多向量特性），Milvus 默认每 collection 4 个向量字段、可调到 10。**管不到 BM25**，除非把 BM25 改造成 sparse vector 字段并改 collection schema（红线）。

**外部引擎原生 RRF：**

- Elasticsearch：`rank.rrf` 自 8.8 起提供（k 默认 60，`window_size` 默认 100）；但 **RRF 属 Enterprise 授权**，Basic/free 调用返回 403 license error。`retriever.rrf` 框架 8.14 才有。本项目跑 ES 8.13.0（`docker/docker-compose.dev.yml:113`）且是免费档 → 原生 RRF 不可用。
- Milvus 2.4+：`RRFRanker` / `WeightedRanker`，服务端执行，同上只覆盖多向量字段。
- 其他：LlamaIndex `QueryFusionRetriever(mode=RECIPROCAL_RERANK)`、Haystack `DocumentJoiner(join_mode="reciprocal_rank_fusion")`、Qdrant `Fusion.RRF`、Weaviate rankedFusion、Vespa reciprocalRankFusion、OpenSearch（Apache 2.0，含 RRF）。

**三个实现的分数量纲对比（重要）：**

| 实现 | 公式 | 与标准的比值 |
|---|---|---|
| 标准 RRF / LangChain / Milvus | `Σ w / (k + rank)`，rank 从 1，k=60 | 1× |
| 本项目 `rankScore:2611` | `Σ w × (k+1)/(k + rank)` | **恰好 61×** |

排序完全等价（纯缩放），但绝对分被放大 61 倍 —— 这正是 `RAG_MIN_TOP_SCORE=0.05` 永不触发的直接原因（标准量纲下 top1 只有 ~0.0167，是能被 0.05 卡住的）。

**结论**：自己写这 ~50 行是合理选择，不是重复造轮子 —— 现有库都做不到"保留完整 chunk 元数据 + 融合后再过权限/scope 门禁"。
