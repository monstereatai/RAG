## 参考答案（先做完再看）

1. **错**。岗位之间只认 SOP——流程结构是数据（plan），运行时不可被模型改写；自由在每个岗位**内部**的受控循环（§3.5、第 1 节"避免模型越权改写工作流"）。
2. **对**。上游产出有错可反查全部被污染下游（§3.2）。
3. **对**。计划与执行分离——改流程改 plan 不动引擎（§3.3）。
4. **B**。A 是它的输入（`brief`），C 是它的工具（§3.1）。
5. **B**。Task Agentic = 每岗位一个受控循环（§二架构图、先修说明）。
6. **B**。质量取决于模型与工具，架构给的是**可控性**：路径可预测、证据链完整、token 成本 = 岗位数 × 各自预算（§3.5 对照表）。
7. 因为契约靠**字符串匹配**（artifact 名是运行时数据，TypeScript 编译器看不见 SOP 表里的字符串关系）——所以说是"编译错误**级别**的失败"（失败确定性同等级），不是编译期检查。弥补：把 artifact 名提取为常量/枚举共享给上下游（坑点 1 的预防）、启动时校验 SOP 的依赖闭合性（每个输入都有上游产出）、CI 里跑 plan 的依赖图测试。
8. 场景例：分析岗位的结论里某个数字翻倍了（模型算错或工具返回异常），下游撰写岗位基于它生成了完美格式的周报。排障时工具调用日志全绿、检索结果正确——错误发生在"岗位如何综合信息做判断"这一步。没有 DecisionRecord，你只能看到输入正确+输出错误，中间是黑盒，无法定位是哪个推理环节编的数。工具调用是可观测的（事件流），中间推理默认不可观测——这正是 DecisionRecord 存在的理由。
9. 参考答案（契约合理即可）：
   ```
   ['data-collect', '数据收集 SOP', ['week_range'], ['rag.search', 'bocha_web_search'], ['weekly_metrics_raw'], []],
   ['analyst', '分析 SOP', ['weekly_metrics_raw'], ['citation_validate'], ['insights_report', 'risk_flags'], []],
   ['writer', '周报撰写 SOP', ['insights_report', 'risk_flags'], [], ['weekly_report'], []],
   ```
   分析岗位 blocked 策略：**撰写岗位不启动，工作流以 blocked 终态上报**，理由——撰写依赖分析结论，缺环产出等于让模型编数字（幻觉直通交付物）；正确动作是把 blocked 原因返回用户，补齐分析岗位的依赖（权限/数据）后重跑。**宁缺毋编**（呼应 RAG 课程第 5 节安全降级）。
