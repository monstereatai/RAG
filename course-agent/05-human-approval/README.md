# 审批、持久化与恢复

前置：工具权限、幂等与循环。先读 [实现边界](../../course/IMPLEMENTATION-NOTES.md)，本章不把事件名称当作调度保证。

## 问题与方案

人工审批需要回答：批准了什么、状态存在哪里、谁能继续、重复审批会怎样、无人处理如何结束。界面出现待审批卡片只证明通知送达，不能证明后续动作停止。

方案有三层：工具执行前授权、工作流批次后审阅、执行引擎的真正暂停与恢复。它们保护的对象不同，应明确审批对象、参数、版本、所有者和状态转换。

## 当前项目的三条路径

| 路径 | 代码事实 | 不能据此推出什么 |
| --- | --- | --- |
| Chat（问答）审批 | `humanApprovalNode` 返回 pending（待审批），但条件边仅 rejected（拒绝）才结束，其他状态进入 reflection（反思） | 不能称图已在此暂停；`resumeGraph` 的带输入 invoke（调用）不能保证前序不重跑 |
| Agent Loop（循环）快照 | 每轮成功后写状态，入口从 initialState（初始状态）和新计数执行 | 不能称已自动加载快照并保留原预算恢复 |
| 生产工作流 | pending_approval（待审批）、revision_required（待修订）、resume（继续）与 revise（修订）有明确分支 | 现有单测不能替代真实服务重启与并发审批验证 |

源码：[问答图](../../backend/src/rag/agentic/agentic-rag.service.ts)、[循环](../../backend/src/modules/agent-loop/agent-loop.service.ts)、[生产工作流](../../backend/src/modules/workflow/production-workflow.service.ts)。

生产工作流审批是在批次产物形成后阻止后续批次；高风险写工具仍应单独走执行前授权。两种审批不能互相冒充。

## 恢复的必要条件

完整状态、执行位置、剩余预算、身份与计划版本都要可恢复；对已执行写动作核对幂等记录和远端结果。恢复前检查审批仍有效，参数变化后不能复用旧批准。

Redis Checkpointer（检查点存储）能持久化图状态，具体从何处继续由执行引擎与调用方式决定。检查点存在或函数名叫 resume，都不足以证明不会重放前序步骤。

TTL（过期时间）删除数据不等于业务自动拒绝。若需要超时拒绝或通知，要有明确状态更新与调度逻辑，并做实验验证。生产工作流实例化检查点时传入 30 天；不要套用循环快照默认 24 小时。

## 两个排障练习

1. 待审批后仍出现后续动作：检查事件之后的条件边和调度，不先归因于前端。
2. 重启后重新执行了写动作：检查是否读取完整状态、预算是否重置、业务幂等是否仍有效；不能直接回放上一个快照。
