## 一、判断题（每题 1 分）

1. 所有工具（包括只读工具）都会生成幂等键并写入 Redis。
2. 执行异常时，幂等键下写入的状态是 `unknown` 而不是 `failed`。
3. `recovered` 状态意味着工具刚成功执行了一次。

## 二、选择题（每题 1 分）

4. 两个相同幂等键的请求并发到达，第二个请求的结局是？
   - A. 排队等待第一个完成后继续

6. 工具输出超过 6000 字符时，审计事件里保留的是？
   - A. 完整输出（审计必须完整）

## 四、代码审查题（2 分）

9. 同学给写工具加的"幂等"实现：

```ts
async function callWithRetry(tool, args, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      return await tool(args);
    } catch (e) {
      if (i === maxRetries - 1) throw e;
      await sleep(1000);  // 等 1 秒重试
    }
  }
}
```

对照本节四态语义，指出至少 3 个问题。

---

## 参考答案（先做完再看）

1. **错**。只有 `sideEffect` 写工具进幂等逻辑；只读工具重复执行无害，不值得付 Redis 成本（§3.2）。
2. **对**。超时 ≠ 未执行——诚实记录"不知道"（§3.3）。
3. **错**。recovered 意味着**检测到相同幂等键此前已成功**，本次未执行、直接恢复历史结果（§3.1）。
4. **B**。`setIfAbsent('running')` 并发防锁，抢不到即 blocked——杜绝双写窗口（§3.2）。
5. **A**。显式授予或策略声明 auto，其余拒绝优先（§3.4）。
6. **B**。审计事件是排障通道不是数据仓库；大结果落 Artifact 定位（§3.5）。
7. 例：发邮件工具，请求超时。盲目重试：若第一封实际已发出（对方服务器慢），用户收两封；扣款场景是双倍扣款。查询确认：先向对方系统查询该操作（按业务单号）是否已生效，已生效→按成功处理，未生效→安全重发。区别在于**把"我不知道"和"它没做"区分开**——前者必须先补认知，后者才允许重试。
8. TTL（过期时间）控制存储和保护窗口，但不能区分新旧业务意图。新操作使用新的业务操作标识，同一操作的迟到重试仍可能在过期后重复执行；需结合远端幂等或结果查询。是否允许重复风险由业务决定，不能默认可接受。
9. ① 无 unknown 语义：异常一律当"没执行"重试——超时时可能双写（坑点 2 原型）；② 无并发防锁：两个请求同到（首个还在路上，重试又发一版），双双执行；③ 无幂等键/Redis：每次重试都是全新执行，"重试 3 次"意味着最坏执行 3 次写操作；④ 对只读和写工具不区分——只读也白白付出重试延迟（可接受但次优）；⑤ 无审计事件：重试了几次、每次结果如何，事后无从追溯。
